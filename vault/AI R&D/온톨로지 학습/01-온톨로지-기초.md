자사 서비스 AX 를 위한 AI R&D 로 업무 도메인별 분석 문서(domain-doc)를 만들고 있고, 최종 목표는 이 문서들을 **온톨로지**로 잇는 것이다. 본격적으로 설계하기 전에 꼭 알아야 할 개념을 8강으로 나눠 공부하기로 했고, 이 글은 그 첫 강이다. 정의와 용어를 정리한 뒤, 우리 서비스의 실제 업무 규칙 하나를 트리플로 쪼개 보면서 자연어가 무엇을 숨기는지 확인한다.

## 학습 순서

| 강 | 주제 | 왜 작업 전에 필요한가 |
|---|---|---|
| **1** | 온톨로지란 무엇이고, 지식그래프와 어떻게 다른가 | 용어가 섞이면 설계 회의가 헛돈다 |

## 온톨로지란

가장 많이 인용되는 정의는 Gruber(1993)의 **"개념화의 명시적 명세(explicit specification of a conceptualization)"**다. 풀어 쓰면 세 가지를 **명시적으로 적어 둔 것**이다.

1. 이 세계에 **어떤 종류의 것**이 있는가 — 클래스
2. 그것들이 **어떤 관계**를 맺을 수 있는가 — 관계(property)
3. 그 관계가 **어떤 규칙**을 지켜야 하는가 — 제약

핵심은 "명시적"이다. 우리 서비스에서 이 셋은 지금 개발자 머릿속과 코드 안에 **암묵적으로** 있다. 온톨로지는 그걸 꺼내 기계가 읽을 수 있게 적는 일이다.

### 비슷한 말들의 사다리

아래로 갈수록 표현력이 커진다.

| 단계 | 무엇을 담나 | 예 |
|---|---|---|
| 용어집 | 낱말과 뜻 | "TBM = 작업 전 안전 교육" |
| 택소노미 | 상하위 분류 | 위험성평가 ⊃ 최초정기 · 상시수시 |
| 시소러스 | + 동의어 · 관련어 | "평가서" = "위험성평가표", 관련: "회의록" |
| **온톨로지** | + 임의의 관계 · 제약 · 규칙 | "평가서는 정확히 하나의 현장에 속한다" |
| **지식그래프** | 온톨로지 + 실제 사실 데이터 | "OTAT 의 화면 X 가 `TSFAS_TBM_NON_EMPHS` 에 쓴다" |

사내 단어 사전(컬럼 별칭을 만드는 데 쓰는 것)은 용어집과 시소러스 사이에 있다. 출발 재료로 쓸 수 있다.

## 틀(TBox)과 사실(ABox)

- **TBox (Terminology)** — 틀 · 스키마. "화면은 SQL문을 호출한다", "SQL문은 테이블을 읽거나 쓴다", "테이블은 하나의 도메인이 소유한다."
- **ABox (Assertions)** — 그 틀에 맞춰 채운 사실. "화면 `SfasPopRegFirstAssmnt` 가 `insertFirstPrvLst` 를 호출한다."

> **온톨로지 = TBox, 지식그래프 = TBox + ABox.**

domain-doc 에 비춰 보면, 분석 결과(`analysis.json`)에는 **ABox 가 이미 수만 건** 있다. 반면 TBox 는 **분석기 코드 안에 암묵적으로만** 있다. `screens` · `chain` · `sql` · `tables` · `outsideUse` 같은 키가 사실상 클래스와 관계인데 따로 적혀 있지 않다. 그래서 첫 작업은 사실을 더 모으는 게 아니라 **이미 있는 사실의 틀을 꺼내 적는 것**이다.

## 트리플 — 사실 하나의 최소 단위

모든 사실은 **주어 – 관계 – 대상** 셋으로 쪼갤 수 있다.

```
(화면 SfasPopRegFirstAssmnt)  ─호출한다→  (SQL문 insertFirstPrvLst)
(SQL문 insertFirstPrvLst)     ─쓴다→     (테이블 TSFAS_FIRST_RISKASMT_DTL_TDP)
(테이블 TSF_TBM_EDU_ATDT)      ─소유자→   (도메인 TBM)
(도메인 TBMB)                 ─쓴다→     (테이블 TSF_TBM_EDU_ATDT)   ← 남의 테이블에 쓴다
```

마지막 줄은 domain-doc 의 경계 지도 조사에서 찾은 "TBM B 타입이 A 타입 테이블에 쓴다"는 간선이다. 경계 지도는 이미 작은 지식그래프였다.

`(타현장회의록가져오기) ─유형→ (팝업)` 처럼 **"무엇의 한 종류다"를 말하는 트리플**을 유형 트리플이라고 부른다(RDF 의 `rdf:type`). 가장 기본적인 꼴이다.

## 함정 — 테이블은 업무 개념이 아니다

`TSFAS_TBM_NON_EMPHS` 와 `TSFAS_TBMB_NON_EMPHS` 는 테이블로는 둘이지만, 업무로는 **같은 개념**("TBM 비중점 위험")을 A · B 타입이 각각 **구현한 것**이다. 그래서 우리 온톨로지는 거의 확실히 **두 층과 그 사이의 다리**가 된다.

```
[업무 층]   TBM교육 ── 갖는다 → 비중점위험
                │                  │
            구현한다            구현한다
                ↓                  ↓
[코드 층]   TSF_TBM_EDU_ATDT    TSFAS_TBM_NON_EMPHS
                                TSFAS_TBMB_NON_EMPHS
```

- 코드 층은 분석기가 자동으로 만든다. 이미 된다.
- 업무 층은 사람이 정하거나, AI 가 서술에서 뽑고 사람이 승인한다.
- **"구현한다" 다리가 온톨로지 가치의 대부분**이다. 이게 있어야 "비중점 위험을 건드리면 어느 테이블과 화면이 영향받나?"에 도메인을 가로질러 답할 수 있다.

## 실습 — 업무 규칙 한 문장을 쪼개 보기

> "회의록의 타현장회의록가져오기 팝업은, 준공 현장의 회의록을 옵션22=T 일 때만 보여 준다."

처음에는 이렇게 쪼갰다.

1. 회의록엔 타현장회의록가져오기가 있다
2. 타현장회의록가져오기는 팝업이다
3. 준공 현장의 회의록은 옵션22가 T 일 때 보여준다

1 · 2는 좋은 트리플이다. 3은 원래 문장을 거의 그대로 옮긴 것이라 트리플이 아니다. 그 안에 접혀 있는 것을 펼쳐 보면 자연어가 무엇을 숨기는지 보인다.

### 숨어 있던 것 ① — 주어가 물건이 아니라 집합이다

"회의록"은 가리키는 물건이 있다. "준공 현장의 회의록"은 **"회의록 중에서, 소속 현장이 준공인 것만"이라는 걸러내기 조건**이 주어 안에 접혀 있는 말이다.

```
"준공 현장의 회의록"  =  회의록  +  [조건: 그 회의록이 속한 현장의 상태 = 준공]
```

트리플의 주어 칸에는 물건 하나만 들어간다. 조건이 접힌 말을 그대로 넣으면 "준공현장의회의록"이라는 물건이 따로 있는 것처럼 된다.

### 숨어 있던 것 ② — 등장인물이 생략돼 있다

이 장면에는 **현장이 둘** 나온다.

| | 누구 | 문장에 나오나 |
|---|---|---|
| **내 현장** | 팝업을 연 현장 (가져오는 쪽) | 안 나옴 — 당연하다고 생략 |
| **타 현장** | 회의록을 가진 현장 (내주는 쪽) | "준공 현장"으로 나옴 |

"준공"도 "옵션22"도 **둘 다 타 현장의 것**이다. 옵션은 보통 "우리 현장 설정"이라, 읽는 사람이 옵션22 를 내 현장 설정으로 상상하기 쉽다. 그러면 틀린다. 사람은 문맥으로 대충 맞게 읽기도 하고 틀리게 읽기도 하지만, AI 와 그래프는 그 대충이 안 된다. **"어느 현장의" 상태 · 옵션인지까지 적어야 한다.**

트리플로 쪼개 보는 것만으로 문서의 모호한 곳이 드러난다는 점이 이 실습의 수확이다.

### 숨어 있던 것 ③ — 문장이 반쪽이다

코드로 확인된 실제 규칙은 두 갈래다.

```
타 현장이 진행 중  →  옵션22 와 무관하게 항상 보임
타 현장이 준공     →  타 현장의 옵션22 = T 일 때만 보임
```

처음 문장은 두 번째 갈래만 말했다. 조건을 말하면 **"그 조건이 아닐 때는?"**이 비어 버린다. 자연어가 흔히 하는 일이고, domain-doc 평가에서 자주 나온 "문장이 범위를 닫거나 반만 말하는" 오류와 같은 뿌리다.

### 현장 넷으로 확인하기

내 현장 A 에서 팝업을 연다고 하자.

| 타 현장 | 상태 | 옵션22 | 회의록 팝업에서 | (비교) 다른 화면의 가져오기에서 |
|---|---|---|---|---|
| B | 진행 중 | F | ✅ 보임 | ❌ 안 보임 |
| C | 준공 | T | ✅ 보임 | ✅ 보임 |
| D | 준공 | F | ❌ 안 보임 | ✅ 보임 |

다른 화면들(상시수시 평가서 가져오기, 공종 복사 등)의 규칙은 "준공은 항상 공개, 진행 중은 옵션22=T 일 때만"이다. **회의록만 거꾸로**라서, 같은 옵션을 꺼도 다른 화면에서는 B 가 숨고 회의록에서는 D 가 숨는다. 이 표를 문장 하나로 말하려다 보니 처음 문장이 꼬였던 것이다.

### 제대로 쪼개기 — 사실과 규칙을 나눈다

**사실(ABox)** — 특정 물건 하나하나에 대한 것. 규칙을 모른다.

```
(타현장회의록가져오기) ─유형→    (팝업)
(회의록작성 화면)      ─연다→    (타현장회의록가져오기)
(회의록 M1)           ─속한다→  (현장 B)
(현장 B)              ─상태→    (진행 중)
(현장 B)              ─옵션22→  (F)
(현장 D)              ─상태→    (준공)
(현장 D)              ─옵션22→  (F)
```

**규칙** — 특정 현장이 아니라 "어떤 타 현장이든 이 조건이면 보인다".

```
보인다  ⇔  (타현장.상태 = 진행 중)
          또는
          (타현장.상태 = 준공  그리고  타현장.옵션22 = T)
```

### 칸 셋으로는 규칙을 못 담는다 — n항 관계

`(팝업) ─보여준다→ (회의록)` 이라고 쓰는 순간 칸 셋이 찬다. 그런데 이 관계에는 더 붙어야 한다.

- 조건이 걸리는 대상이 팝업도 회의록도 아닌 **제3의 물건(타 현장)**이다
- 조건이 **두 갈래(또는)**다
- 근거(어느 SQL 몇째 줄)도 붙어야 한다

이를 **n항 관계(n-ary relation)** 문제라고 한다. 표준 해법은 **규칙 자체를 노드로 만드는 것**이다.

```
                     ┌─ 적용대상 → (타현장회의록가져오기)
                     ├─ 보여줄것 → (회의록)
(규칙: 회의록 타현장 공개) ┼─ 조건갈래1 → [타현장.상태 = 진행 중]
                     ├─ 조건갈래2 → [타현장.상태 = 준공] 그리고 [타현장.옵션22 = T]
                     ├─ 다른화면과 → 반대 (규칙: 타현장 가져오기 공개 — 일반)
                     └─ 근거 → (SQL 파일 : 줄)
```

이렇게 두면 "옵션22 를 읽는 규칙을 전부 보여 줘", "다른 화면과 거꾸로 동작하는 규칙은?" 같은 질문에 그래프만으로 답할 수 있다. 사실과 규칙을 합치면 표의 ✅ ❌ 를 기계가 스스로 계산할 수도 있다. 이걸 **추론**이라고 하고 7강에서 다룬다.

우리 서비스에서 가장 값진 정보(업무 규칙, 옵션 영향, 상태 조건)가 거의 다 이 꼴이다. 그래서 4강에서 다시 깊게 다룬다.

## 한 줄 정리

> 자연어 문장 하나에는 **사실 · 조건 · 규칙**이 접혀 있고, **생략된 등장인물**도 있다. 온톨로지로 옮긴다는 건 이걸 다 펼쳐서 **물건 · 사실 · 규칙 노드**로 따로 적는 일이다.

## 배운 점 (확인 문제에서)

- **값의 범위도 틀에 적는다.** 출제할 때 옵션22 값을 "Y/N"이라 써 놓고 바로 "T"를 써 버렸다(코드는 T). 값 범위가 TBox 에 없으면 사람도 이렇게 헷갈린다.
- **규칙과 사실은 다른 층이다.** "모든 준공 현장에 적용된다"는 문장은 개체 하나에 대한 사실이 아니다. 처음 모범 답안에도 `(현장) ─상태→ (준공)` 처럼 규칙의 조건을 사실처럼 적은 섞임이 있었다.

## 자가진단 — domain-doc 은 1강 개념을 얼마나 다루나

배운 개념에 비춰 지금 스킬을 점검했다. 기준은 스킬 정본 클론의 작업 트리(2026-10-27, 아직 커밋 전 변경 포함)와 10-26 에 만든 분석 결과다. 개념 일곱 가지로 나눠 보면 이렇다.

| 개념 | 판정 |
|---|---|
| TBox(틀) 명시 | 없음 — 분석기 코드 안에만 있음 |
| ABox(사실) 품질 | 일부 |
| 테이블 ≠ 업무 개념 | 일부 — 원형만 있음 |
| 조건 붙은 규칙(n항) | 일부 |
| 주체 명시(어느 현장의) | 데이터는 일부, 규칙은 없음 |
| 반쪽 규칙 · 닫힌 문장 | 일부 |
| 사실과 규칙 분리 | 일부 — 부(절) 단위로만 |

### 1. 잘되고 있는 부분

- **사실이 이미 개체 단위로 식별된다.** 화면 id, `SQL파일#문id`, `테이블.칸`, `SFAS_OPT_xxx` 처럼 안정적인 ID 가 있다. 트리플의 주어 · 대상으로 바로 쓸 수 있는 재료다.
- **조건이 버려지지 않고 남아 있다.** SQL 문마다 `conds{kind, text, scope, tb}` 가 있고, 화면의 막는 조건은 `checks.triggers{when, cond, options, message}` 로 모인다. 1강에서 쪼갠 회의록 규칙도 `SfasPopRegOtherProjMeetingDraftSql#selectOtherProjList` 에 `kind: 옵션` 으로 실제로 들어 있다.
- **서술의 근거를 기계가 검사한다.** 손으로 쓴 서술 블록마다 `근거: 파일:줄 "글"` 주석이 붙고, 검사기(`evidence.js`)가 근거 없는 블록을 막는다. 회의록 도메인의 한 부에만 근거 83개가 달려 있다.
- **업무 개념 층의 싹이 있다.**
  - `site-ref.json` 이 빈도 · 강도 · 등급 같은 개념을 여러 도메인의 `테이블.칸` 에 잇는다. 1강에서 말한 "구현한다" 다리의 원형이다.
  - `options.json` 은 옵션 짧은 이름 60개를 공통 어휘로 둔다.
  - `common.json` 은 도메인을 가로지르는 공통 규칙에 id 를 붙인다.
- **"범위를 닫는 말"을 일부 잡는다.** 검사기가 "뿐 · 전부 · 밖에 없 · 모든 화면" 같은 말에 검색 근거를 요구하고, 감사 에이전트에는 "넓음" 판정이 있다.
- **사실과 규칙이 부(절) 단위로는 나뉜다.** 생성 표는 개체별 사실, "사용 방법"은 규칙 요약, `000. 공통 동작` 문서는 도메인 공통 규칙이다. 계약(`0-contract.md`)이 "사실은 분석기, 서술은 이어 말하기"로 정해 두었다.

### 2. 보완이 필요한 부분

1. **틀(TBox)이 어디에도 적혀 있지 않다.** 클래스와 관계(`opens` · `chain` · `reads` · `writes` …)가 분석기 코드에만 있다. 스키마 표는 스킬 밖의 동결 조사 문서(L-7)에 한 번 있을 뿐이고, 분석 결과에 판 번호(`schemaVersion`)도 없다.
2. **생성된 사실에는 근거 줄과 커밋이 없다.** 서술은 `파일:줄` 근거를 갖는데, 정작 그래프의 몸통이 될 생성 사실(조건 · 막는 조건 · 입력값)에는 줄 번호도 커밋도 없다. 조건 하나하나에 ID 도 없다.
3. **조건이 원문 한 덩어리다.** 이 SQL 의 조건은 `Or` 로 묶인 원문 그대로 한 칸에 들어간다(절차서가 "Or 로 묶인 갈래는 한 칸에"라고 정함). 갈래별로 조건 → 결과가 나뉘지 않고, 결과(보인다 · 막힌다)는 문 종류를 보고 짐작해야 한다.
4. **주체(어느 행 · 어느 현장의 값인지)를 담지 않는다.** `tb` 가 별칭을 테이블 이름으로 풀어 주기는 하지만, 그 테이블 행이 내 현장인지 타 현장인지는 없다. 회의록 문서의 "보여 주는 쪽 현장의 옵션"은 서술 에이전트가 손으로 쓴 것이고, 주체를 쓰라는 규칙은 절차서 · 에이전트 정의 어디에도 없다.
5. **반쪽 규칙과 부정 단정을 잡지 못한다.** "만 · 항상 · 없다 · 않는다" 검사가 없고, "그 조건이 아닐 때 갈래도 적는다"는 규칙도 없다. 일부 규칙은 글로만 있고 검사기가 없다. "규칙마다 검사 하나"라는 스킬 자체의 계약과 어긋난다.
6. **업무 개념 ID 체계가 없다.** TBM A · B 의 비중점 위험 테이블을 한 개념으로 묶는 장치가 없고, 사내 단어 사전과도 이어져 있지 않다. 다만 개념 목록의 주인과 씨앗은 사람이 정할 일로 남겨 두었다.
7. **문장 단위로 사실인지 규칙인지 표시하지 않는다.** 서술 에이전트가 구조화된 주장 목록을 함께 내는 안은 스킬 정제 쪽에서 "이 꼴로는 안 함"으로 결정됐다. 빈 곳이라기보다 정해진 선택이다. 그러니 규칙의 구조화는 서술이 아니라 2 · 3번(생성 쪽)에서 풀어야 한다.

### 2-1. 보완 방향 — 구체적 예시

**① 틀을 파일로 꺼내고 판 번호를 붙인다** (2-1번 대응)

```json
// schema/analysis.schema.md 에 표로, analysis.json 머리에 판 번호로
"meta": { "schemaVersion": "1.0", ... }
```

| 클래스 | ID 꼴 | 예 |
|---|---|---|
| 화면 | 화면 id | `SfasPopRegOtherProjMeetingDraft` |
| SQL문 | `SQL파일#문id` | `SfasPopRegOtherProjMeetingDraftSql#selectOtherProjList` |
| 테이블칸 | `테이블.칸` | `TCC_PROJ_CODE.SFAS_OPT_022` |

| 관계 | 주어 → 대상 | 지금 키 |
|---|---|---|
| 연다 | 화면 → 화면 | `screens.*.opens` |
| 부른다 | 화면 → SQL문 | `screens.*.chain` |
| 읽는다 · 쓴다 | SQL문 → 테이블 | `sql.*.stmts[].reads/writes` |

키를 바꾸지 않고 **이미 있는 키에 이름을 붙여 적기만** 해도 TBox 가 된다.

**② 생성 사실마다 근거를 붙인다** (2-2번 대응)

```json
// 지금
{ "kind": "옵션", "text": "((#{PROJ_END_TF} = 'F' And ...) Or (...))", "scope": "인라인 뷰 m" }

// 보완
{ "id": "MEET.selectOtherProjList.c3", "kind": "옵션", "text": "...", "scope": "인라인 뷰 m",
  "at": "SfasPopRegOtherProjMeetingDraftSql.xml:212", "commit": "64c8717c7" }
```

(줄 번호 `212` 는 꼴을 보이려는 예시 값이다.) `id` 가 있어야 규칙 노드가 이 조건을 가리킬 수 있다. `at` · `commit` 이 있어야 코드가 바뀌었을 때 어느 사실이 낡았는지 안다(6강).

**③ Or 갈래를 행으로 펼치고 주체를 적는다** (2-3 · 2-4번 대응) — 1강 실습을 그대로 기계에 시키는 꼴이다.

실제 조건 원문은 이렇다.

```sql
(#{PROJ_END_TF} = 'F' And TCC_PROJ_CODE.OK_TAG = 'F')
Or
(#{PROJ_END_TF} = 'T' And TCC_PROJ_CODE.OK_TAG = 'T' And TCC_PROJ_CODE.SFAS_OPT_022 = 'T')
```

펼치면 이렇게 된다.

| 갈래 | 화면 조회조건 `PROJ_END_TF` | 타 현장 준공(`OK_TAG`) | 타 현장 옵션22 | 결과 |
|---|---|---|---|---|
| 1 | F (진행 중 보기) | F | 상관없음 | 목록에 나온다 |
| 2 | T (준공 보기) | T | T | 목록에 나온다 |

```json
"branches": [
  { "when": [ {"who": "화면 조회조건", "col": "PROJ_END_TF", "eq": "F"},
              {"who": "타 현장(목록 행)", "col": "TCC_PROJ_CODE.OK_TAG", "eq": "F"} ],
    "then": "목록에 나온다" },
  { "when": [ {"who": "화면 조회조건", "col": "PROJ_END_TF", "eq": "T"},
              {"who": "타 현장(목록 행)", "col": "TCC_PROJ_CODE.OK_TAG", "eq": "T"},
              {"who": "타 현장(목록 행)", "col": "TCC_PROJ_CODE.SFAS_OPT_022", "eq": "T"} ],
    "then": "목록에 나온다" }
]
```

펼쳐 보니 **1강 실습에서도 못 본 셋째 등장인물**이 나왔다. 바로 화면의 조회조건(`PROJ_END_TF`, 사용자가 진행 중을 보느냐 준공을 보느냐)이다. 자연어로 "진행 중이면 항상"이라고 말할 때 이 조건은 다시 생략돼 있었다. 갈래를 기계적으로 펼치면 사람이 놓친 등장인물까지 드러난다는 게 이 방향의 가치다.

`who` 는 처음부터 완벽할 필요가 없다. `FROM` 절에서 그 테이블이 목록의 주 테이블이면 "목록 행", `#{…}` 면 "화면 조회조건", 로그인 세션 값이면 "내 현장"처럼 **세 가지만 기계로 판정**해도 대부분 덮인다.

**④ 닫힌 말 · 반쪽 규칙 검사를 하나씩 더한다** (2-5번 대응)

```js
// evidence.js 의 RANGE 옆에
const CLOSED = /(항상|만 (보|나오|됩|쓴)|않는다|없다|없습니다)/;
// 걸리면: 근거 2개(그렇다 · 아닌 경우) 또는 "아닐 때" 문장을 요구
```

서술 규칙에도 한 줄을 더한다 — **"조건을 말하면 그 조건이 아닐 때도 한 문장으로 적는다."** 1강의 반쪽 문장("준공이면 옵션22=T 일 때만")은 이 한 줄이 있었으면 "진행 중이면 옵션과 무관하게 나온다"까지 적혔을 것이다.

**⑤ 개념 다리는 작게 시작한다** (2-6번 대응) — 사람이 정할 일이지만 꼴은 미리 둘 수 있다.

```json
// concepts.json — site-ref.json 과 같은 꼴로
{ "id": "C.TBM.비중점위험",
  "label": "TBM 비중점 위험",
  "implementedBy": ["TSFAS_TBM_NON_EMPHS", "TSFAS_TBMB_NON_EMPHS"],
  "aliases": ["비중점위험", "일일 비중점 위험"] }
```

이미 굴러가는 `site-ref.json` 의 꼴을 넓히는 쪽이 새 장치를 만드는 것보다 싸다. 처음에는 도메인 사이에 겹치는 개념 몇 개만 손으로 적고, 단어 사전 연계는 그 다음이다.

**우선순위:** ①② → ③ → ④ → ⑤.
- ①② 는 다른 모든 것의 전제다. 스킬 정제 세션에 넘긴 피드백 #2 · #3, 백로그 L-7 · L-16 이다.
- ③ 은 1강의 핵심을 기계에 시키는 일이라 효과가 가장 크다. 바깥 조인을 잘못 읽는 문제(L-20)를 고치는 재생성 때 같이 하는 게 좋아 보인다.
- ④ 는 비용이 가장 작지만, 서술을 다시 쓰기 **전에** 들어가야 효과가 난다.
