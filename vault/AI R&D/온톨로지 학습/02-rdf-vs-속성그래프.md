그래프로 지식을 담는 방식은 크게 두 계열이다. 어느 쪽을 고르느냐보다 **무엇을 정본으로 두느냐**가 더 중요하다는 게 이번 강의의 결론이다. 2강부터는 **강의 → 실제 이슈 사례 → domain-doc 보완 방향** 순서로 진행한다. 사례는 상시/수시 위험성평가 도메인에서 문서만으로 이슈를 따라가다 막힌 경우들이다.

## 1강 남은 문제의 답

> 현장 A 가 자기 옵션22를 F 로 바꾸면, A 의 회의록 가져오기 목록이 달라지나?

**달라지지 않는다.** 목록이 보는 옵션22는 목록에 뜨는 **타 현장의 값**이다(1강 "생략된 등장인물"). A 의 설정은 반대쪽에 영향을 준다. A 가 준공 현장이면, **다른 현장의 목록에서 A 의 회의록이 사라진다.**

## 강의

### RDF / OWL — "모든 것은 트리플이다"

W3C 표준이고 시맨틱 웹에서 나왔다.

- 모든 것이 **트리플**이고, 모든 이름이 **전역 ID(IRI)** 다. 다른 조직의 데이터를 합쳐도 이름이 부딪히지 않게 하려는 설계다.
- **틀(TBox)을 같은 언어로** 적는다(RDFS · OWL).
- **추론기**가 있다. "A 가 B 를 구현하고 B 가 C 의 일종이면 A 는 C 를 구현한다" 같은 결론을 기계가 만든다.
- **표준 어휘**가 많다. 계보는 PROV-O, 용어 사전은 SKOS.
- 질의 언어는 SPARQL. 기본 가정은 **열린 세계**다. 안 적힌 것은 "모름"이다.

### 속성 그래프(LPG) — "노드와 간선에 속성을 단다"

Neo4j 가 대표이고, 2024년에 ISO 표준 질의 언어(GQL)가 나왔다.

- 노드와 간선이 각각 **라벨과 속성(키-값)**을 가진다. **간선에 속성을 바로 붙인다.**
- 틀은 선택이다. 편하지만 틀이 안 적히는 문제가 그대로 생긴다.
- 추론기는 없고, 질의(Cypher · GQL)로 직접 따라간다.
- 개발자에게 익숙하고, GraphRAG 도구 대부분이 이 계열이다. 실무에서는 사실상 **닫힌 세계**처럼 쓴다.

### 비교

| | RDF / OWL | 속성 그래프 |
|---|---|---|
| 사실 단위 | 트리플 | 노드 · 간선 + 속성 |
| 간선에 근거 · 조건 붙이기 | 번거로움 (중간 노드나 RDF-star) | **쉬움** (간선 속성) |
| 틀(TBox) | 같은 언어로 엄격하게 | 선택, 느슨함 |
| 추론 | **기본 제공** | 없음 (질의로 대신) |
| 표준 어휘 재사용 | **풍부함** | 이름만 빌려 씀 |
| 배우는 비용 · 도구 | 높음 | **낮음** |
| 세계 가정 | 열린 세계 | 사실상 닫힌 세계 |

### 1강의 n항 관계는 두 계열에서 어떻게 풀리나

- **조건이 간선 하나에만 걸리면** 속성 그래프가 압승이다. 간선 속성으로 단다.
- **조건이 제3의 물건에 걸리면**("타 현장의 옵션") 두 계열 모두 결국 **규칙 노드**를 만든다. 1강의 결론은 기술 선택과 무관하게 맞다.
- RDF 1.2 의 트리플 항(RDF-star)을 쓰면 트리플에 대한 트리플을 바로 쓸 수 있다.

```turtle
<< :팝업 :보여준다 :회의록 >> :조건 :규칙R1 ; :근거 "x.xml:212" .
```

### 권고 — 정본과 보기를 나눈다

1. **정본은 분석기가 만드는 JSON** 으로 둔다. 그래프 DB 는 거기서 만드는 **보기(view)** 다. 계열을 바꿔도 다시 만들면 끝이다.
2. **보기는 속성 그래프로 시작한다.** 간선마다 근거 · 커밋 · 출처를 붙이기 쉽고, 팀이 배우는 비용이 낮다.
3. **이름은 RDF 표준 어휘에서 빌린다.** 계보는 `wasDerivedFrom` · `wasAttributedTo`(PROV-O), 동의어는 `altLabel`(SKOS). 추론기를 안 써도 이름을 맞춰 두면 뜻이 흔들리지 않는다.
4. **추론이 정말 필요해지면 그때 RDF 로 내보낸다.**

## 사례 실습 — 같은 기능인데 채널마다 값이 다르다

> 같은 "다른 현장에서 가져오기" 기능인데 원청 웹은 **연계 칸**이 비고, 협력 웹 · 모바일은 원본 현장의 연계가 따라왔다. 사실 자체는 문서에 있었지만, 서로 다른 세 표를 직접 나란히 놓아야 보였다.

### 지금 문서는 이 사실을 어떻게 갖고 있나

표 셋이 따로 있고, 표끼리 잇는 선이 없다. 사람이 세 표를 "같은 기능"이라고 알아보고 맞대야 차이가 보인다.

### 속성 그래프로 바꿔 보면

```
(:기능 {id:'F.다른현장가져오기'})
   ↑ :구현한다 {채널:'원청 웹'}   (:SQL문 원청 웹 Insert)
   ↑ :구현한다 {채널:'협력 웹'}   (:SQL문 협력 웹 Insert)
   ↑ :구현한다 {채널:'모바일'}    (:SQL문 모바일 Insert)

(:SQL문 협력 웹 Insert) -[:채운다 {출처:'원본 행', at:'…'}]-> (:칸 연계)
(:SQL문 모바일 Insert)  -[:채운다 {출처:'원본 행', at:'…'}]-> (:칸 연계)
   (원청 웹 Insert 에서는 이 간선이 없다)
```

이슈의 질문이 질의 하나가 된다. **"같은 기능의 구현 중, 어떤 칸을 누구는 채우고 누구는 안 채우나?"**

```cypher
MATCH (f:기능)<-[:구현한다]-(s:SQL문)-[w:채운다]->(c:칸)
WITH f, c, collect(DISTINCT s.id) AS 채우는쪽
MATCH (f)<-[:구현한다]-(all:SQL문)
WITH f, c, 채우는쪽, collect(DISTINCT all.id) AS 전체
WHERE size(채우는쪽) < size(전체)
RETURN f.id, c.id, 채우는쪽, [x IN 전체 WHERE NOT x IN 채우는쪽] AS 안채우는쪽
```

이 질의는 이 사례 하나만 푸는 게 아니라, **모든 기능에 대해 채널 사이 차이를 한 번에** 찾는다. 비슷한 이슈가 터지기 전에 목록으로 받아 볼 수 있다.

### 이 사례에서 배운 것

- 막힌 이유는 정보가 없어서가 아니라 **`구현한다` 간선 하나가 없어서**였다. 1강의 "테이블 ≠ 업무 개념"이 **"SQL ≠ 기능"**으로 다시 나왔다.
- **간선 속성(출처 · 채널 · 근거)이 핵심 정보**를 담는다. RDF 였다면 간선마다 중간 노드가 필요했다. 이 프로젝트에 속성 그래프가 맞는 이유를 실제 사례로 보여 준다.

## 보완 방향 — domain-doc 에 무엇을 더하나

**① Insert 값마다 출처를 붙인다** — 사람 판단 없이 기계로 된다.

```json
"inserts": [ { "col": "<연계 칸>", "from": "원본 행", "expr": "a.<연계 칸>", "at": "…:…" } ]
```

`#{…}` 이면 화면이 보낸 값, SELECT 원본 별칭이면 원본 행, 세션 값 · `SYSDATE` 면 세션으로 판정한다. 작성자 · 작성일이 원본에서 그대로 복사되던 이슈도 이 칸 하나로 문서에 드러난다.

**② 생성 표에 "구현 차이" 절을 더한다** — 그래프 DB 없이 JSON 에서 바로 만든다. **그래프 DB 를 깔기 전에도 그래프식 질문의 효과는 먼저 낼 수 있다.**

| 기능 | 칸 | 원청 웹 | 협력 웹 | 모바일 |
|---|---|---|---|---|
| 다른 현장에서 가져오기 | 연계 | — | 원본 행 | 원본 행 |

처음에는 기능 대신 "같은 테이블에 쓰는 Insert 끼리"로 묶어도 이 사례는 잡힌다.

**③ 기능 노드와 `구현한다` 간선** — 같은 화면 제목 · 버튼 이름 · 쓰는 테이블이 겹치는 SQL 묶음을 분석기가 **기능 후보**로 내고, 사람이 이름을 붙여 확정한다. 1강에서 말한 개념 다리와 같은 꼴의 파일로 둔다.

**우선순위:** ① → ② → ③. ③은 사람이 이름을 붙여야 해서 가장 늦지만, 온톨로지의 업무 층이 여기서 시작된다.

## 확인 문제에서 배운 것

**간선에 근거 · 커밋을 붙여야 한다는 요구가 왜 속성 그래프 쪽으로 기우나?**
속성 그래프는 간선에 속성을 바로 단다. RDF 는 트리플에 속성을 달려면 간선마다 중간 노드(또는 RDF-star)가 필요하다. 간선이 수만 건이면 차이가 크다.
- 덧붙여 짚은 것: 닫힌 세계는 "B2B SaaS 라서"가 아니라 **"분석한 범위 안에서만"** 성립한다. 분석기가 못 따라간 호출이 있으면, 간선이 없다고 "없다"는 뜻이 아니다.
- **틀은 느슨하게가 아니라 엄격하게 적되, OWL 이 아니라 자체 검사로 지킨다.** 느슨한 틀에서 "어떤 칸은 싣고 어떤 칸은 빼는" 불일치가 나왔다.

**질의 결과 원청 웹에서만 빠져 있으면 원청 웹이 버그인가?**
**판단할 수 없다.** 그래프는 차이(사실)를 보여 줄 뿐 의도를 모른다. 실제 결론은 **셋 다 비우기**였다. 다수(2/3)가 채우고 있었지만 다수가 정답이 아니었다. 그래서 의도는 **결정 노드**(누가 · 언제 · 왜 · 어느 백로그 항목)로 따로 남겨야 한다. 그래프는 후보를 내고, 사람이 정한다.

**그래프 DB 를 정본으로 두면 무엇이 곤란한가?**
- 기계가 만든 사실과 사람이 넣은 것(개념 이름 · 결정)이 한 곳에 섞인다. 코드가 바뀌어 다시 생성하면 사람 입력이 지워지거나 **충돌**한다.
- git diff · 리뷰 · 되돌리기가 안 된다.
- 같은 커밋에서 같은 결과가 나온다는 **재현성**이 깨진다. 지워져야 할 간선이 안 지워지고 쌓인다.
- 특정 제품에 묶인다.

원칙은 이렇다. **기계 사실은 통째로 다시 생성하고, 사람 입력은 버전 관리되는 파일에 두고, 그래프는 둘을 합쳐 매번 다시 만든 보기로 둔다.** domain-doc 이 문서에서 이미 지키는 원칙("표는 손으로 고치지 않는다")과 같다.
