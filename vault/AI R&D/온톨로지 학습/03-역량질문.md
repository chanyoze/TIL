온톨로지를 설계할 때 가장 먼저 부딪히는 질문은 "어디까지 담아야 하나"다. 기준이 없으면 필요한 걸 빠뜨리거나 쓸모없는 걸 끝없이 담게 된다. 이 강의는 그 기준인 **역량 질문(Competency Questions, CQ)**을 다룬다. 실습에서는 "가져온 줄의 작성일이 원본 작성일로 찍힌" 이슈를 CQ 로 바꿔 본다. 그리고 문서 정확도 평가는 통과했는데 실제 이슈에서는 막힌 이유를 CQ 관점으로 설명해 본다.

## 강의

### 온톨로지는 언제 "다 됐다"고 하나

> **온톨로지가 답할 수 있어야 하는 질문 목록을 먼저 쓰고, 그 질문에 답하는 데 필요한 것만 담는다. 목록의 질문에 모두 답할 수 있으면 "다 된 것"이다.** (Grüninger & Fox, 1995)

CQ 는 두 가지로 쓰인다.
- **범위 정하기(설계 전)** — 질문마다 필요한 클래스와 관계를 뽑으면 그게 곧 틀(TBox)이다.
- **시험(만든 뒤)** — 질문을 실제 질의로 돌려 답이 나오는지 본다. **CQ 는 온톨로지의 단위 테스트**다.

### 좋은 CQ 의 조건

1. **실제 질문에서 나온다.** 지어낸 질문보다 이슈 · 문의 · 장애에서 나온 질문이 낫다.
2. **틀(템플릿)로 쓴다.** "이전 가져오기로 넣은 행의 작성일은?"이 아니라 "**기능 F** 로 넣은 행의 **칸 C** 에는 **어디서 온 값**이 들어가나?" 빈칸이 있어야 같은 꼴의 질문 수백 개를 한 번에 덮는다.
3. **답의 꼴이 정해져 있다.** 위 질문의 답은 `원본 행 | 화면 | 세션 | 고정값 | 비움` 중 하나다. 답의 꼴이 정해져야 기계가 채점할 수 있다. "수기 입력 또는 일부 가져오기"처럼 뭉갠 답은 꼴이 아니다. 답은 닫힌 목록이어야 한다.
4. **범위 밖도 적는다.** 답하지 **않을** 질문을 적어야 끝없는 확장을 막는다.

### CQ 의 유형

| 유형 | 틀 예시 | 실제 이슈에서 |
|---|---|---|
| 조회 | "화면 S 에서 가져올 수 있는 평가서는?" | 문서가 잘 답했다 (게이트) |
| **계보** | "칸 C 의 값은 어디서 왔고 누가 넣었나?" | 막혔다 — 작성일 · 작성자 · 사본 행 |
| **비교** | "기능 F 의 구현끼리 어느 칸이 다른가?" | 막혔다 — 채널마다 다른 연계 값 |
| 의미 · 범위 | "칸 C 의 값은 어느 범위 안에서만 뜻이 있나?" | 막혔다 — 현장마다 다른 기준표 |
| **부정** | "옵션 O 를 저장 쪽에서도 보나?" | 막혔다 — "안 하나요?" 문의 |
| 영향 | "테이블 T 를 바꾸면 어디가 영향받나?" | 도메인 경계 지도 |
| 규칙 | "어떤 조건에서 버튼 B 가 막히나?" | 1강 회의록 규칙 |

**막힌 이슈는 전부 계보 · 비교 · 의미 · 부정 유형이었고, 문서가 잘 답한 건 조회 유형이었다.**

### CQ 에서 틀을 뽑는 법

질문의 명사는 클래스로, 동사는 관계로, 답의 꼴은 속성으로 옮긴다.

```
CQ: "기능 F 로 넣은 행의 칸 C 에는 어디서 온 값이 들어가나?"

  명사  → 클래스   : 기능, SQL문, 칸
  동사  → 관계     : (SQL문)─구현한다→(기능), (SQL문)─채운다→(칸)
  답의 꼴 → 속성   : 채운다.출처 ∈ {원본 행, 화면, 세션, 고정값, 비움}
```

2강 실습에서 직관으로 그린 그래프와 같은 그래프가, 이번에는 **질문에서 기계적으로** 나왔다.

## 사례 실습 — 가져온 줄의 작성일이 원본 작성일로 찍혔다

> 평가서에서 이전 · 누적 가져오기를 하면, 가져온 줄의 작성일이 원본 작성일(3년 전)로 찍혀 올해 회차 목록에 섞여 보였다. 문서에서 가져오기 경로와 게이트는 찾았지만, "작성자 · 작성시간에 무엇이 들어가나"는 어느 표에도 없었다. 생성 표가 감사 칸(작성자 · 작성일)을 싣지 않았다.

### 이슈를 CQ 틀로

| # | CQ 틀 | 유형 | 답의 꼴 | 지금 문서 |
|---|---|---|---|---|
| CQ-A | 기능 F 로 가져올 수 있는 원본은? | 조회 | 원본 테이블 + 게이트 조건 | ✅ |
| CQ-B | 기능 F 로 넣은 행의 칸 C 는 어디서 온 값인가? | 계보 | 원본 행 / 화면 / 세션 / 고정값 / 비움 | ❌ 감사 칸 없음, 출처 구분 없음 |
| CQ-C | 화면 S 의 열 L 에 보이는 값은 어느 칸에서 오나? | 계보 | `테이블.칸` | 🔶 열 ↔ 칸 연결이 약함 |
| CQ-D | 기능 F 에서 원본 값을 유지할 칸과 새로 채울 칸은? | 규칙 | 칸별 정책 + 결정 근거 | ❌ 정책이 코드에도 없음 |

### 두 CQ 를 이으면 이슈가 통째로 보인다

```
(원본 행.작성일 = 3년 전)
    ─[가져오기 Insert, 출처: 원본 행]→  (새 행.작성일 = 3년 전)
    ─[목록 SELECT]→                    (올해 회차 목록의 "작성일" 열)
```

이 경로가 그래프에 있으면 "왜 올해 회차에 옛 날짜가 보이나?"에 경로 질의 하나로 답한다.

### 감사 칸은 왜 빠졌나

CQ 목록 없이 **"중요해 보이는 칸"을 사람 감각으로 골랐기 때문**이다. CQ-B 가 목록에 있었다면, 감사 칸은 답에 필요한 칸이라 뺄 수 없었다.

## 보완 방향 — domain-doc 에 무엇을 더하나

**① 이슈를 CQ 로 쌓는 장부(`cq.md`)** — 문서로 못 답해 코드를 열어야 했던 이슈는 CQ 로 바꿔 적는다. 틀은 도메인을 가로지르므로 장부는 하나다.

```markdown
| id | CQ 틀 | 유형 | 답의 꼴 | 필요한 키 | 지금 | 출처 이슈 |
|---|---|---|---|---|---|---|
| CQ-007 | 기능 F 로 넣은 행의 칸 C 는 어디서 온 값인가 | 계보 | 원본 행/화면/세션/고정값/비움 | inserts[].from | ❌ | 가져오기 작성일 |
| CQ-008 | 기능 F 의 구현끼리 어느 칸이 다른가 | 비교 | 칸 × 채널 표 | functions, inserts[].from | ❌ | 채널별 연계 |
```

**이슈 → CQ → 틀 보완 → 다시 생성 → CQ 통과.** 운영에서 문서로 돌아오는 피드백 고리가 이것이다.

**② 정확도 평가 출제에 CQ 유형을 섞는다** — 예를 들어 20문항을 계보 4 · 비교 3 · 부정 3 · 규칙 3 · 영향 2 · 조회 5 로 할당한다. 채점표에 "유형" 칸을 더하면 **유형별 정답률**이 나와, 평균에 가려진 약한 유형이 보인다.

**③ CQ 를 구조 검사로** — 장부의 "필요한 키" 칸을 검사기가 읽어, 분석 결과에 그 키가 실제로 있는지 본다. 사람 채점 없이도 "이 질문에 구조적으로 답할 수 있는가"를 매번 확인한다.

**우선순위:** ① → ② → ③. ①은 이미 모은 이슈 사례로 오늘 시작할 수 있다. ②는 효과가 가장 크다. "평가는 통과했는데 실전에서 막히는" 일을 줄인다.

## 확인 문제에서 배운 것

**사례: 협력사 사용자가 검토의견 작성자로 들어가 이름이 안 나온다.** 원청 검토의견을 함께 가져오는 기능을 협력사 사용자가 실행하면, 그 사람이 작성자로 기록된다. 이 값이 다른 도메인으로 그대로 넘어가고, 화면은 이름을 (사용자, 회사) 짝으로 찾는데 회사를 원청으로 고정해 두어서 이름이 빈다.

**① 사실 CQ 와 정책 CQ 를 나눈다.**
처음에 "작성자에 들어갈 수 있는 사용자는? → 원청 사용자에 한정"이라고 썼다. 그런데 이건 **의도(정책)**이지 **코드의 사실**이 아니다. 실제로는 협력사 사용자가 들어갔다. 그래서 질문을 둘로 나눈다.
- 사실(계보): "작성자 칸의 값은 어느 기능 · 도메인을 거쳐 왔고, 단계마다 누가 넣었나?"
- 정책(규칙): "작성자 칸에 들어가도 되는 사용자 역할은?"

**사실이 정책을 벗어나면 그게 결함이다.** 2강의 결정 노드가 정책 쪽 답을 담는다.

**② 역할 명사는 클래스가 아니라 관계다.**
"검토의견 작성자"를 클래스로 잡으면 안 된다. "작성자 · 소유자 · 담당자" 같은 역할 명사는 보통 **관계**다.

| 처음 답 | 고친 답 |
|---|---|
| 클래스: 검토의견 작성자 | 클래스: 사용자 · 회사 · 검토의견 · 기능 · 도메인 |
| 관계: 매핑하다 | 관계: `(검토의견)─작성자→(사용자)` · `(사용자)─실행했다→(기능)` · `(이쪽 검토의견)─파생되었다→(저쪽 검토의견)` |
| 속성: `#{원청 사용자}` | 속성: `채운다.출처 = 원본 행` |

- "매핑하다"는 방향도 뜻도 없다. 관계 이름은 **누가 무엇을 어떻게** 하는지 말해야 한다.
- `#{원청 사용자}` 는 값과 출처를 한 칸에 섞었다. 게다가 실제 출처는 `#{…}`(화면이 보낸 값)가 아니라 **원본 행**이었다. "작성자는 원청이 화면에서 넣는다"고 가정한 답이, 문서가 접어 둔 것을 그대로 되풀이한 셈이다. 출처를 칸으로 강제해야 하는 이유다.

**③ 평가는 통과했는데 실전에서 막힌 이유.**
"틀이 미흡했다"는 둘 다 실패한 뿌리로는 맞다. 하지만 **시험은 통과하고 실전은 막힌 차이**는 다른 데 있다. **시험 문항의 유형 분포가 실제 이슈의 유형 분포와 달랐다.**
- 해당 도메인의 평가 20문항은 상태 · 흐름 · 막힘 규칙과 테이블 · 권한 조회 위주였다.
- 가져오기 관련 문항은 "어떤 평가서를 가져올 수 있나요"(게이트, 조회형) 하나였다.
- 가져온 행의 값 출처 · 작성자를 묻는 계보형은 0 개였다.
- 실제 이슈 6건은 전부 계보 · 비교 · 의미 · 부정형이었다.

**"오답 0" 은 "출제된 유형에서 틀리지 않았다"는 뜻이지 "답할 수 있다"는 뜻이 아니다.** 보완 방향 ②(출제에 유형 할당)가 필요한 이유다.
