8강 중 3강까지 마치고, 뒤의 강의 전부의 바탕이 되는 1~3강을 복습한다. 확인 문제에서 **부분**이 나온 지점을 겨냥해 복습 문제를 냈다. 한 문제씩 풀 때마다 이 글에 답과 해설을 덧붙인다. 문제에 쓴 사례는 [사례 모음](./사례-모음.md)에 정리했다.

## 1~3강 핵심 한 장

**1강 — 무엇을 담나**
- 온톨로지 = 틀(TBox: 클래스 · 관계 · 제약), 지식그래프 = 틀 + 사실(ABox).
- 사실은 트리플(주어 – 관계 – 대상)로 쪼갠다.
- 자연어 한 문장에는 **사실 · 조건 · 규칙**과 **생략된 등장인물**이 접혀 있다. 펼쳐서 물건 · 사실 · 규칙 노드로 따로 적는다.
- 조건이 제3의 물건에 걸리면 칸 셋으로 못 담는다(n항 관계) → **규칙 노드**.
- 테이블 ≠ 업무 개념 → 두 층 + "구현한다" 다리.

**2강 — 어떻게 담나**
- 간선에 근거 · 출처 · 커밋을 붙여야 하니 **속성 그래프**로 시작한다. 이름은 RDF 표준 어휘(PROV-O · SKOS)에서 빌린다.
- **정본은 분석기 JSON**, 그래프는 매번 다시 만드는 보기. 사람 입력(개념 · 기능 · 결정)은 git 으로 관리하는 파일에 둔다.
- 그래프는 **차이**를 보여 줄 뿐 **의도**를 모른다 → 결정 노드.
- 닫힌 세계는 **분석한 범위 안에서만** 성립한다.

**3강 — 어디까지 담나**
- 답해야 할 질문(CQ)을 먼저 쓰고, 그 답에 필요한 것만 담는다. CQ 는 단위 테스트다.
- CQ 는 틀로 쓰고, 답의 꼴은 닫힌 목록으로 정한다.
- 명사 → 클래스, 동사 → 관계, 답의 꼴 → 속성. 단, **역할 명사(작성자 · 담당자)는 관계**다.
- **사실 CQ 와 정책 CQ 를 나눈다.** 사실이 정책을 벗어나면 결함이다.
- 시험을 통과해도 **유형 분포가 실전과 다르면** 실전에서 막힌다.

## R1. "원본"이라는 말 펼치기

> "검토의견 Insert 는 원본 평가서 값을 복사한다."
> 실제로는 같은 SQL 문 안에 행이 두 종류 있었다. 원본 평가서에서 복사하는 행, 그리고 같은 문에서 방금 넣은 접수본 행을 제출본으로 복사하는 행(동기화 사본)이다.

### 처음 답

- (a) "원본"이 접수본인지, 제출본인지, 가져온 대상의 검토의견인지 모호하고 중의적이다.
- (b) `(검토의견) ─가져온다→ (원본 평가서)` + `(동기화 사본) ─아니다→ (원본: 접수본, 제출본 등 받는 쪽)`

### 판정 — (a) 정답, (b) 부분

**(a)** "원본"이 가리킬 수 있는 후보를 나열한 것이 정확히 1강의 "펼치기"다. 실제로 섞인 건 둘이다.
- **원본 평가서의 검토의견** — 가져온 대상
- **같은 문에서 방금 넣은 접수본 행 X**

제출본은 이 사례에서 받는 쪽이라 출처 후보가 아니다.

**(b) 첫째 트리플** — 방향은 맞다. 다듬을 곳은 둘이다.
- **주어가 너무 넓다.** "검토의견"은 클래스다. 말하려는 건 **이번에 새로 생긴 접수본 행 X**(인스턴스)다. → 4강
- **관계 이름**: "가져온다"는 기능 이름이다. 값의 계보는 **"파생되었다"(PROV-O `wasDerivedFrom`)**로 쓴다.

**(b) 둘째 트리플** — 두 가지가 어긋났다.
1. **"아니다"는 간선으로 쓰기 어렵다.** 무엇이 맞는지 말해 주지 않고, 열린 세계에서 부정 사실은 특히 약하다. → 7강. 그래프에는 **무엇에서 왔는지를 긍정형으로** 적는다. 그러면 "원본 평가서에서 온 게 아니다"는 저절로 따라 나온다.
2. **출처와 받는 쪽이 섞였다.** 동기화 사본의 출처는 **접수본 행 X**, 받는 쪽은 **제출본**이다. 1강의 "생략된 등장인물"이 이번에는 **주는 쪽 / 받는 쪽**으로 나왔다.

### 모범 답

```
(접수본 검토의견 행 X) ─파생되었다 {방식: 가져오기}→ (원본 평가서 검토의견 행 O)
(제출본 검토의견 행 Y) ─파생되었다 {방식: 동기화}  → (접수본 검토의견 행 X)
```

2강의 `채운다 {출처}` 꼴로:

```
(SQL문 S) ─채운다 {출처: 원본 평가서 행}→          (접수본 검토의견)
(SQL문 S) ─채운다 {출처: 같은 문에서 앞서 넣은 행}→  (제출본 검토의견)
```

### 하나 더 — 직접 출처와 거슬러 올라간 출처

두 줄을 이으면 **Y → X → O** 사슬이다. 거슬러 올라가면 Y 의 값도 결국 원본 평가서 O 에서 왔고 값도 같다.

감사 에이전트가 틀린 지점이 여기다. **"거슬러 올라가면 O 에서 왔다"를 "직접 O 에서 복사한다"로 줄였다.** 그래서 판정이 "틀림"이 아니라 **"넓음"**이었다.

- 직접 출처(바로 앞 단계)와 거슬러 올라간 출처(사슬의 끝)의 구분은 6강 계보의 핵심이다.
- 그래프는 **직접 출처만 간선으로** 적고, 사슬의 끝은 **질의로 따라가서** 얻는다. 그래야 둘이 섞이지 않는다.

## R2. 클래스냐 관계냐

> 현장, 회사, 평가서, 작성자, 접수자, 원청, 협력사 → 클래스 / 관계

### 처음 답

- 클래스: 현장, 회사, 평가서, 작성자, 접수자 / 관계: 원청, 협력사
- 원청은 현장별로 달라질 수 있어 관계라고 봤다. 작성자 · 접수자도 관계인가 했지만, "작성했다는 불변의 사실"이 있고 접수자도 접수한 사람을 뜻하니 클래스가 맞다고 봤다.

### 판정 — 부분 (7개 중 5개)

| 낱말 | 처음 답 | 맞는 답 | |
|---|---|---|---|
| 현장 · 회사 · 평가서 | 클래스 | 클래스 | ✅ |
| 원청 · 협력사 | 관계 | 관계 | ✅ 이유까지 정확 |
| 작성자 · 접수자 | 클래스 | **관계** | ❌ |

**원청 · 협력사** — "현장에 따라 달라진다"가 정확한 이유다. `(회사 C) ─원청이다→ (현장 P)` 처럼 회사와 현장 사이의 관계다. 참여 자체에 기간 · 계약 같은 속성이 붙으면 **참여 노드**(회사 · 현장 · 역할 · 기간)로 올린다. 1강의 규칙 노드와 같은 n항 해법이다.

**작성자 · 접수자 — "불변"은 기준이 아니다.**
"U 가 이 평가서를 작성했다"는 사실은 바뀌지 않는다. 맞는 말이다. 그런데 그 불변의 사실은 **사용자 U 와 평가서 E 사이의 관계**다. "작성자"라는 종류의 물건이 따로 있는 게 아니다.

가려내는 시험 두 가지:
1. **혼자 설 수 있나?** — U 를 평가서 없이 "작성자"라고 부를 수 있나? 없다. 작성자는 언제나 "**~의** 작성자"다. 대상이 있어야 성립하면 관계다.
2. **그 물건이 존재하는 동안 늘 그런가?** — U 는 언제나 사용자다. 하지만 작성자인지는 어느 평가서를 보느냐에 달렸다. 같은 사람이 이 평가서의 작성자이고, 저 평가서의 접수자이고, 세 번째 평가서와는 아무 관계가 없다. 이처럼 늘 그런 것(사용자)은 클래스, 상대에 따라 달라지는 것(작성자)은 역할이다. 온톨로지 품질 점검법 **OntoClean**(Guarino · Welty)이 쓰는 기준이다. 이 기준을 **강직성(rigidity)**이라고 부른다.

**"불변의 사실"이라는 직관이 가리키는 진짜 클래스.**
직관은 틀리지 않았다. 다만 클래스가 되는 것은 **작성자(사람의 역할)**가 아니라 **작성(일어난 일)**이다.

```
(평가서 E) ─생성되었다(wasGeneratedBy)→ (작성 활동 A {시각: 2026-10-20 14:03})
(작성 활동 A) ─수행자(wasAssociatedWith)→ (사용자 U)
```

계보 표준(PROV-O)이 정확히 이렇게 모델링한다. 활동(Activity)은 클래스이고, 누가 · 언제 · 무엇을이 그 활동에 붙는다. 6강에서 다시 다룬다.

**사례 3 에 대 보면** — 작성자가 클래스라면 "협력사 사용자가 작성자 클래스에 속한다"는 말이 되는데, 뜻이 없다. 관계로 두면 사례 3 의 질문이 정확해진다. **작성자 관계가 가리키는 사용자가 누구이고, 그 값은 어느 활동(배분 내용 가져오기)에서 왔나.**

### R2 보충 — 접수자는 왜 관계인가 (개발자 눈으로)

**DB 로 보면 바로 보인다.** 테이블은 클래스, 다른 행을 가리키는 칸은 관계다.

```
[사용자 테이블]   USER_NO · 이름 · 회사 …          ← 클래스 (사용자)
[평가서 테이블]   평가서번호 · 상태 · … · 접수자 칸  ← 클래스 (평가서)
                                       └──────→ 사용자 테이블의 한 행을 가리킨다
[접수자 테이블]   — 없다 —
```

"접수자"는 따로 테이블이 있는 물건이 아니다. **평가서 행의 칸 하나가 사용자 행을 가리키는 것**이다. 그 칸이 곧 관계 `(평가서) ─접수자→ (사용자)` 다.

**한 사람으로 보면** — 같은 사람이 평가서마다 다른 역할을 한다.

| 평가서 | 작성자 칸 | 접수자 칸 |
|---|---|---|
| 평가서 1 | 김 대리 | 박 과장 |
| 평가서 2 | 이 주임 | **김 대리** |
| 평가서 3 | 이 주임 | 박 과장 |

김 대리는 늘 사용자다. 하지만 평가서 1 에서는 작성자, 평가서 2 에서는 접수자, 평가서 3 과는 아무 관계가 없다. "김 대리는 접수자인가?"라는 질문은 **"어느 평가서의?"**를 붙이지 않으면 답할 수 없다. 이게 관계라는 신호다.

**말로 시험하기** — 정의를 풀어 써 본다.
- 사용자 = "시스템에 계정이 있는 사람" → 다른 물건이 안 나온다 → **클래스**
- 접수자 = "**그 평가서를** 접수한 사용자" → 정의 안에 평가서가 들어간다 → **관계**

"~를 ~한 사람"으로 풀리면 관계다. "접수한 사람을 의미한다"는 처음 답 자체가 이미 "무엇을 접수한"을 품고 있었다.

**억지로 클래스로 두면 생기는 일**
- 김 대리가 사용자 클래스와 접수자 클래스에 동시에 들어간다. 그런데 어느 평가서의 접수자인지는 클래스가 담지 못해 결국 관계가 또 필요하다.
- 접수취소하면 김 대리는 접수자 클래스에서 빠지나? 다른 평가서는 여전히 접수 중이라면? 소속이 평가서마다 엇갈려 정의가 무너진다.

**원청과 같은 논리** — 원청이 "**어느 현장의** 원청"이라 관계였던 것처럼, 접수자는 "**어느 평가서의** 접수자"라 관계다. 바뀌지 않는 사실로 남는 것은 **접수라는 활동**(누가 · 언제 · 어느 평가서를)이고, 클래스가 될 수 있는 것은 그 활동 쪽이다.

**작성자도 같다.** "어느 평가서의?"를 되물어야 하는 것은 작성자도 마찬가지다. 그래서 작성자 · 접수자 둘 다 관계다. 차이가 있다면 작성자는 **생길 때 한 번 정해지고 잘 안 바뀌는** 관계, 접수자는 **접수취소로 바뀔 수 있는** 관계라는 점이다. 이는 관계의 성질일 뿐 클래스가 될 이유가 아니다. 그리고 "안 바뀐다"는 작성자도 **처음 들어간 값이 틀릴 수 있다**. 사례 1 · 3 에서는 원본 행의 작성자가 그대로 복사되거나, 가져오기를 실행한 사람이 들어갔다. 그래서 관계에 출처를 붙인다.

> 헷갈렸던 지점: 작성자와 접수자를 "하나는 클래스, 하나는 관계"로 나눠 이해했다. 실제로는 **작성자 · 접수자 · 원청 · 협력사 모두 관계**다. "어느 ○○의"가 붙어야 성립하기 때문이다.

### R2 모범 답

| 낱말 | 판정 | 이유 |
|---|---|---|
| 현장 · 회사 · 평가서 | 클래스 | 그 자체로 존재 |
| 작성자 · 접수자 | 관계 | "어느 평가서의" — `(평가서) ─작성자/접수자→ (사용자)` |
| 원청 · 협력사 | 관계 | "어느 현장의" — `(회사) ─원청이다/협력사다→ (현장)` |

시험: ① "어느 ○○의?"를 되물어야 하면 관계 ② 풀어 쓴 정의에 다른 물건이 들어가면 관계. 불변 여부는 기준이 아니다. 바뀌지 않는 사실은 활동(작성 · 접수)으로 담는다.

## 남은 문제 — 직접 풀어 보기

1~3강을 다시 읽고 푼다. 답을 적은 뒤 세션에서 채점받고, 해설을 이 아래에 덧붙인다.

### R3. 묻는 것에 정확히 답하기 (2강)

2강 확인 문제 1번에서 "물은 것의 답이 빠졌다"는 판정이 나온 지점을 다시 겨냥한 문제다.

> SQL문 S 가 칸 C 를 채운다. 출처는 원본 행, 근거는 `x.xml:120`, 기준 커밋은 `abc123`.

물건이 둘(S, C), 관계가 하나(채운다)이고, 그 관계에 딸린 정보가 셋(출처 · 근거 · 커밋)이다.

- **(a)** 속성 그래프로 **한 줄**에 적어 보기
- **(b)** RDF(트리플만, RDF-star 없이)로 적으면 **무엇이 더 필요해지는지** 한 줄로

> ✍️ **내 답 (a)**
>
> &nbsp;
>
> ✍️ **내 답 (b)**
>
> &nbsp;

<details>
<summary>힌트 (a)</summary>

2강 실습에서 쓴 줄은 이렇다.

```
(:SQL문 '모바일 Insert') -[:채운다 {출처:'원본 행', at:'…'}]-> (:칸 연계)
```

`( )` 는 물건, `-[ ]->` 는 관계(주어 → 대상), `{ }` 는 그 관계에 붙는 속성이다. 문제의 S · C · 채운다 · 출처 · 근거 · 커밋을 각 자리에 대응시킨다.

| 문제의 말 | 자리 |
|---|---|
| SQL문 S | 왼쪽 `( )` |
| 칸 C | 오른쪽 `( )` |
| 채운다 | `-[ ]->` 안 |
| 출처 · 근거 · 커밋 | `{ }` 안 |

</details>

<details>
<summary>힌트 (b)</summary>

1. RDF 의 칸은 정확히 셋 — `(주어) ─관계→ (대상)`. 관계에 붙는 `{ }` 자리가 **없다.** `(S) ─채운다→ (C)` 를 쓰는 순간 칸이 다 찬다.
2. 출처 · 근거 · 커밋은 S 의 성질도 C 의 성질도 아니다. S 는 다른 칸도 채우고, C 는 다른 SQL 도 채운다. 이 셋은 **"S 가 C 를 채운다"는 그 사건 자체**의 성질이다.
3. 1강에서 칸이 모자랄 때 "보여준다"를 **물건(규칙 노드)으로 만들었다.** "채운다"를 물건으로 만들면 트리플이 어떻게 바뀌나? 무엇이 하나 더 생기고, 트리플이 몇 개가 되나?

</details>

### R4. 사실 CQ 와 정책 CQ (3강)

[사례 5](./사례-모음.md#사례-5-옵션이-꺼져-있으면-연계를-안-채우나요)를 떠올린다. 연계 옵션이 꺼진 현장에서 연계를 저장도 안 하나, 화면에서만 안 보이나?

이 사례를 **사실 CQ 하나 + 정책 CQ 하나** 짝으로 써 본다. 각각 **유형**과 **답의 꼴**도 적는다.

> ✍️ **사실 CQ** — 질문 / 유형 / 답의 꼴
>
> &nbsp;
>
> ✍️ **정책 CQ** — 질문 / 유형 / 답의 꼴
>
> &nbsp;

<details>
<summary>힌트</summary>

- 사실 CQ 는 "코드가 **실제로** 어떻게 하나", 정책 CQ 는 "어떻게 **해야** 하나"를 묻는다(3강 확인 문제 해설).
- 사실 쪽은 옵션을 **읽는 곳**이 어디인지(화면 · 저장 SQL)를 묻게 된다.
- 정책 쪽은 "연계를 **무엇에 쓰나**", "옵션이 꺼지면 저장은 **어때야** 하나"를 묻게 된다. 사례 5 에서는 이 정의가 코드에도 없었다.
- 답의 꼴은 닫힌 목록으로 — 예: `화면만 / 저장만 / 둘 다 / 둘 다 아님`.

</details>
