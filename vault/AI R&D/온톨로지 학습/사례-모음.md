강의 실습에 쓰는 실제 이슈 사례를 모은다. 모두 한 업무 도메인(상시/수시 위험성평가)에서 **코드를 보지 않고 도메인 문서만으로** 이슈를 따라가다 막힌 경우다. 답은 나중에 코드로 확인했다. 회사 내부 내용이라 일반화해서 적었다. 사례가 강의 실습이나 복습 문제에 쓰일 때마다 "쓰인 곳"과 거기서 나온 예시를 덧붙인다.

## 먼저 알아 둘 용어

| 이름 | 뜻 |
|---|---|
| **제출본 · 접수본** | 같은 평가서의 협력사 쪽 사본과 원청 쪽 사본. 내용 · 검토의견 · 위치 · 참석자도 각각 따로 저장된다. 한쪽에 넣으면 다른 쪽을 맞추는 것을 **동기화**라고 한다 |
| **가져오기** | 다른 평가서(이전 회차 · 최초정기 · 다른 현장 등)의 줄을 이 평가서로 끌어오는 기능. 경로가 여럿이다 |
| **게이트** | 가져오기에서 "어떤 원본을 가져올 수 있나"를 정하는 조건(상태 · 옵션 등) |
| **연계** | 평가 항목 줄마다 있는 칸. 현장 내부 메모에 가깝게 쓰인다 |
| **감사 칸** | 작성자 · 작성일처럼 "누가 언제 넣었나"를 남기는 칸 |

## 한눈에

| # | 사례 | 막힘 분류 | 뿌리 개념 | 쓰인 곳 |
|---|---|---|---|---|
| 1 | 가져온 줄의 작성일이 원본 작성일로 찍혔다 | 문서에 없다 + 출처가 접혔다 | 틀 미명시 · 역량 질문 · 계보 | 3강 실습 |
| 2 | 같은 기능인데 채널마다 연계 값이 다르다 | 도메인 · 채널 사이 다리 없음 | "구현한다" 다리(SQL ≠ 기능) | 2강 실습 |
| 3 | 협력사 사용자가 검토의견 작성자로 들어가 이름이 안 나온다 | 도메인 사이 + 주체 생략 | 생략된 등장인물 · n항 · 계보 | 3강 확인 문제 |
| 4 | 다른 현장에서 가져온 빈도 · 강도가 이 현장에선 다른 뜻이다 | 애매함 + 식별자 범위 | 지역 ID vs 전역 ID | (5강 예정) |
| 5 | "옵션이 꺼져 있으면 연계를 안 채우나요?" | "안 하나요?"에 못 답함 | 열린 · 닫힌 세계, 있다/없다/모름 | 복습 1 R4 · R5, (7강 예정) |
| 6 | 감사 에이전트가 동기화 사본 행을 원본으로 읽었다 | 출처가 접혔다 | 계보 — 직접 출처 vs 거슬러 올라간 출처 | 복습 1 R1, (6강 예정) |

**공통점:** 문서는 "어떤 원본을 가져올 수 있나"(게이트)에는 잘 답했다. 막힌 것은 모두 **"가져온 줄에 무엇이 어떤 값으로 들어가나"**였다. 빠진 축은 셋이다. **작성자 · 값의 출처(원본 행 / 화면 / 세션) · 현장 귀속.** 셋 다 결국 "이 값은 어디서 와서 누구 것인가", 곧 **계보**의 질문이다.

## 사례 1. 가져온 줄의 작성일이 원본 작성일로 찍혔다

- **이슈** — 이전 · 누적 · 최초정기 가져오기를 하면, 가져온 줄의 작성일이 원본 작성일(3년 전)로 찍혀 올해 회차 목록에 섞여 보였다.
- **문서** — 가져오기 경로와 게이트는 찾았다. 하지만 "작성자 · 작성시간에 무엇이 들어가나"는 어느 표에도 없었다. 생성 표가 감사 칸을 싣지 않았는데, 회사 칸 하나는 싣고 있어 빠진 방식도 일관되지 않았다.
- **코드** — 가져오기 Insert 가 원본 행의 작성일 · 작성자를 그대로 복사했다. 세션 사용자와 현재 시각으로 고쳤다. 단, 검토의견은 원작성자를 유지해야 해서 별도 칸에 원본 값을 남긴다.
- **쓰인 곳 — 3강 실습.** 이슈를 CQ 틀로 바꿨다.

| CQ | 유형 | 지금 문서 |
|---|---|---|
| 기능 F 로 가져올 수 있는 원본은? | 조회 | ✅ |
| 기능 F 로 넣은 행의 칸 C 는 어디서 온 값인가? | 계보 | ❌ |
| 화면 S 의 열 L 에 보이는 값은 어느 칸에서 오나? | 계보 | 🔶 |
| 원본 값을 유지할 칸과 새로 채울 칸은? | 규칙 | ❌ |

```
(원본 행.작성일 = 3년 전)
    ─[가져오기 Insert, 출처: 원본 행]→  (새 행.작성일 = 3년 전)
    ─[목록 SELECT]→                    (올해 회차 목록의 "작성일" 열)
```

감사 칸이 빠진 이유: CQ 목록 없이 "중요해 보이는 칸"을 사람 감각으로 골랐기 때문이다.

## 사례 2. 같은 기능인데 채널마다 연계 값이 다르다

- **이슈** — 같은 "다른 현장에서 가져오기"인데 원청 웹은 연계가 비고, 협력 웹 · 모바일은 원본 현장의 연계가 따라왔다.
- **문서** — 사실은 있었다. 하지만 서로 다른 세 표를 직접 나란히 놓아야 보였다. "같은 기능의 구현끼리 차이"를 보여 주는 곳이 없었다.
- **코드** — 문서 그대로였다. 연계는 현장 내부 메모라서 다른 현장 가져오기에서는 셋 다 비우기로 **결정**했다.
- **쓰인 곳 — 2강 실습.**

```
(:기능 다른현장가져오기)
   ↑ :구현한다 {채널:'원청 웹'}  (:SQL문 …)
   ↑ :구현한다 {채널:'협력 웹'}  (:SQL문 …) -[:채운다 {출처:'원본 행'}]-> (:칸 연계)
   ↑ :구현한다 {채널:'모바일'}   (:SQL문 …) -[:채운다 {출처:'원본 행'}]-> (:칸 연계)
```

배운 것: 막힌 이유는 `구현한다` 간선 하나가 없어서였다. 차이가 보여도 버그인지는 판단할 수 없다. **셋 중 둘이 채우고 있었지만 다수가 정답이 아니었다.** 의도는 결정 노드로 남긴다.

## 사례 3. 협력사 사용자가 검토의견 작성자로 들어가 이름이 안 나온다

- **이슈** — 검토의견 작성자 칸에 원청이 아니라 협력사 사용자가 찍히고, 화면에는 이름이 비었다.
- **문서** — 절반만 보였다. 이웃 도메인 문서에서 "배분 내용을 가져올 때 원청 검토의견을 함께 가져온다"와 "검토의견 테이블의 작성자 칸은 하나뿐"은 찾았다. 하지만 누가 그 작성자가 되는지, 그 값이 이 도메인으로 넘어오는 연결은 없었다.
- **코드** — 배분 내용 가져오기를 **실행한 협력사 사용자**가 작성자로 기록된다. 이 도메인이 그 행을 가져오면서 작성자 값을 그대로 옮긴다. 이름은 (사용자, 회사) 짝으로 찾는데, 회사를 원청으로 고정한 화면에서는 이름이 빈다.
- **쓰인 곳 — 3강 확인 문제.**

| CQ | 유형 | 답의 꼴 |
|---|---|---|
| 작성자 칸의 값은 어느 기능 · 도메인을 거쳐 왔고 단계마다 누가 넣었나? | 계보 (사실) | `[(단계, 기능, 출처, 실행 주체)]` |
| 작성자 칸에 들어가도 되는 사용자 역할은? | 규칙 (정책) | 역할 집합 + 결정 근거 |
| 작성자 이름 열은 어떤 키로 이름을 찾나? | 조회 (표시) | `(사용자, 회사)` |

배운 것: **사실이 정책을 벗어나면 결함이다.** "작성자"는 클래스가 아니라 관계다. 출처를 `#{화면 값}` 으로 가정한 답이 실제(원본 행)와 달랐다. 사람도 문서가 접어 둔 방향으로 접어 읽는다.

## 사례 4. 다른 현장에서 가져온 빈도 · 강도가 이 현장에선 다른 뜻이다

- **이슈** — 다른 현장 가져오기를 하면 빈도 · 강도 · 등급 값이 그대로 복사된다. 그런데 이 값은 **현장마다 다른 기준표의 순번**이라, 같은 숫자가 현장에 따라 다른 등급을 뜻할 수 있다.
- **문서** — 기준표는 "참조하는 남의 테이블" 목록에 이름만 있었다. "기준표가 현장마다 따로 있다"는 말이 없었다. 공종명 · 인원을 비운다는 사실은 보였지만, 왜 비우는지와 빈도 · 강도는 왜 안 비우는지를 물을 실마리가 없었다.
- **코드** — 원본 값을 그대로 복사한다. 등급도 무조건 채운다. 방침을 정하려고 백로그로 넘겼다.
- **뿌리** — 값이 **현장 범위 안에서만 뜻이 있는 지역 ID** 인데 범위를 넘어 복사됐다. (5강에서 실습 예정)

## 사례 5. "옵션이 꺼져 있으면 연계를 안 채우나요?"

- **이슈** — 모바일에서 가져오기를 하면 연계가 안 채워진다는 문의가 왔다. 확인할 질문은 "연계 옵션이 꺼진 현장에서는 **저장도 안 하나**, 아니면 **화면에서만 안 보이나**"였다.
- **문서** — 옵션 설명은 "연계 칸을 보이게 한다"뿐이었다. "저장 쪽은 옵션을 보지 않는다"는 문장이 없어 어느 쪽으로도 답할 수 없었다. 연계의 용도도 정의가 없었고, **"정의 없음"이라고 적어 둘 자리조차 없었다.**
- **코드** — 저장 SQL 은 옵션을 읽지 않는다. 옵션은 화면 표시에만 쓰인다. 최초정기 가져오기는 고정값이 들어가도록 웹과 모바일을 맞췄다.

```
                   연계 옵션
                     │
                     ▼ (읽는다)
   [화면] 연계 칸 보이기/숨기기

   [저장 SQL] 연계 칸 채우기  ← 옵션을 읽지 않는다
                               (문서에는 이 "읽지 않는다"가 없었다)
```

- **쓰인 곳 — 복습 1 R4 · R5** (풀이 중). 지식에는 **있다 / 없다 / 모름** 세 값이 있는데 문서는 "적혀 있음 / 안 적혀 있음" 두 값뿐이었다. (7강에서 다시 다룸)

## 사례 6. 감사 에이전트가 동기화 사본 행을 원본으로 읽었다

- **이슈** — 사람이 아니라 **AI 가 문서를 읽다 헷갈린 사례**다. 문서를 다시 만들며 사실 감사를 돌렸는데, 검토의견 Insert 의 일부 행이 "원본 평가서 값을 복사한다"로 읽혀 4행 모두 **"넓음"** 판정을 받았다.
- **상황** — 가져오기 한 번에 검토의견이 두 번 들어간다.

```
① 원본 평가서의 검토의견  ──복사──▶  접수본 검토의견   (새 행 X)
② 접수본 검토의견 행 X    ──복사──▶  제출본 검토의견   (동기화 사본)
```

- **문서** — 생성 표가 두 종류의 행에 같은 말("원본에서 복사")을 붙였다. 이전 판에 있던 "동기화 사본" 표시가 재구성 때 빠졌다.
- **조치** — "원본: 같은 문에서 방금 넣은 X 줄(동기화 사본 — 원본 평가서 줄이 아니다)" 표시를 다시 넣었다. **결론 11개가 모두 "맞음"**이 됐다.
- **쓰인 곳 — 복습 1 R1.**

```
(접수본 검토의견 행 X) ─파생되었다 {방식: 가져오기}→ (원본 평가서 검토의견 행 O)
(제출본 검토의견 행 Y) ─파생되었다 {방식: 동기화}  → (접수본 검토의견 행 X)
```

배운 것: Y → X → O 사슬에서 **직접 출처(X)**와 **거슬러 올라간 출처(O)**를 섞으면 "넓음"이 된다. 그래프는 직접 출처만 간선으로 적고, 사슬의 끝은 질의로 따라간다. 부정형 간선("원본이 아니다") 대신 긍정형으로 출처를 적는다.
