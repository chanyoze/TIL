AI 를 일에 쓰는 방법을 다섯 단계로 나눠 배웠다 — 프롬프트, 컨텍스트, 워크플로 자동화, 에이전트, 하네스. 앞 단계의 한계가 다음 단계를 부른다는 흐름으로 정리하면 기억하기 쉽다. 당시 메모에는 Claude Code 의 훅 · 스킬 · CLAUDE.md 를 잘못 이해한 부분이 있어서, 이 글에서는 그 부분을 바로잡아 다시 적었다(아래 "바로잡은 것").

## 한눈에

| 단계 | 한 줄 | 한계 → 다음 단계 |
|---|---|---|
| 프롬프트 엔지니어링 | 지시문을 잘 쓴다 | 매번 사람이 쓰고 고쳐야 한다 |
| 컨텍스트 엔지니어링 | 필요한 정보만 골라 넣는다 | 작업을 시작하고 도구를 잇는 건 여전히 사람 |
| 워크플로 자동화 | 반복 작업을 도구로 잇는다 | 정해진 흐름 밖의 일은 못 한다 |
| 에이전틱 엔지니어링 | AI 가 계획 · 실행 · 점검을 스스로 돈다 | 길어지면 맥락이 무너지고, 자기 결과를 객관적으로 평가하지 못한다 |
| 하네스 엔지니어링 | AI 를 둘러싼 규칙 · 도구 · 강제 장치를 설계한다 | — |

## 1. 프롬프트 엔지니어링

모델이 의도를 정확히 알아듣도록 지시문을 다듬는 기술이다.

- **Chain of Thought** — 단계별로 생각하게 유도한다. 수학 · 논리 · 추론에서 정확도가 오르지만 토큰과 시간이 는다.
- **Role Prompting** — "20년 차 코드 리뷰어로서" 같은 역할을 준다. 결과의 일관성을 잡는 데 쓰되, 과한 역할 설정은 피한다.
- **Few-shot** — 예시 몇 개를 먼저 보여 주고 같은 패턴으로 답하게 한다. 형식이나 말투를 맞출 때 특히 효과가 있다.

한계는 분명하다. 매번 사람이 쓰고, 여러 단계짜리 일에는 효과가 작고, 지시문이 길어질수록 오히려 흐려질 수 있다.

## 2. 컨텍스트 엔지니어링

**컨텍스트 창(모델이 한 번에 볼 수 있는 토큰 한도) 안에 필요한 정보만 정확히 넣는 기술**이다. 정보를 많이 넣는다고 좋아지지 않는다. 관련 없는 내용이 섞이면 결과가 흐려진다(컨텍스트 오염).

```
나쁜 예: 파일 200개 전부 + 문서 100개 + 전체 대화 기록
좋은 예: 지금 필요한 파일 3개 + 관련 문서 2개 + 최근 메시지 몇 개
```

방법은 세 가지 — 거르기(필요한 것만), 구조화(마크다운 섹션 · 계층), 요약(긴 것은 요약본과 참조 링크로).

도구를 하나씩 손으로 잇는 문제는 **MCP(Model Context Protocol)** 가 푼다. 파일 시스템 · API · DB 같은 외부 도구를 AI 에 연결하는 표준 규약이다.

## 3. 워크플로 자동화

반복 작업을 도구로 이어 사람 개입 없이 돌리는 단계다. n8n 같은 노드 기반 도구로 "입력 → DB 조회 → AI 처리 → 응답 → 로그 저장" 같은 흐름을 코딩 없이 만든다. 여러 자동화를 조합해 큰 업무 흐름을 관리하는 것을 오케스트레이션이라고 부른다. 정해진 흐름은 잘 돌지만, 흐름 밖의 판단은 하지 못한다.

## 4. 에이전틱 엔지니어링

AI 가 목표를 받아 **계획(Plan) → 실행(Act) → 점검(Reflect)** 을 스스로 반복한다. 계획은 목표를 작은 단계로 쪼개고, 실행은 코드 실행 · 검색 · 파일 조작 · API 호출을 하고, 점검은 결과를 보고 다음 행동을 정한다.

새로 생기는 문제가 세 가지다.

| 문제 | 증상 | 대응 |
|---|---|---|
| 컨텍스트 불안정 | 컨텍스트 한도에 닿으면 작업이 갑자기 멈추고 진행 중이던 것을 잃는다 | 주기적으로 체크포인트를 저장하고, 오래된 컨텍스트를 정리하고, 작업을 나눈다 |
| 자기평가 편향 | 자기 결과를 객관적으로 평가하지 못한다. 같은 모델이 쓴 코드를 같은 모델이 검증하면 오류를 놓칠 수 있다 | 다른 모델로 검증하고, 외부 테스트 도구를 쓰고, 사람의 리뷰를 넣는다(아래) |
| 장시간 작업 불일치 | 세션이 길어지면 초반 지시와 후반 행동이 모순된다. 앞의 정보가 밀려나고 지시가 희석되기 때문이다 | 핵심 지시를 시스템 프롬프트로 고정하고, 정기적으로 목표를 다시 확인하고, 작업 로그를 남긴다 |

**Generator-Evaluator 패턴** — 한 모델이 만들고(생성) 다른 모델이 평가해 피드백을 주면, 만든 쪽이 그 피드백으로 고친다. 빠르고 싼 모델로 만들고 강한 모델로 검증하면 비용도 아낄 수 있다.

## 5. 하네스 엔지니어링

AI 의 자유도를 적절히 묶어 효율을 올리는 단계다. Claude Code 기준으로 세 가지 장치가 있다.

| 장치 | 성격 | 어디에 |
|---|---|---|
| **CLAUDE.md** | 지침. 모델이 읽고 따르려 하지만 **강제는 아니다** | 전역 `~/.claude/CLAUDE.md`, 프로젝트 루트 `CLAUDE.md`, 개인용 `CLAUDE.local.md` |
| **훅(Hook)** | 강제. 도구 실행 전후에 **하네스가 스크립트를 돌려** 막거나 바꾼다. 모델이 어길 수 없다 | `settings.json` 의 `hooks` |
| **스킬(Skill)** | 절차 묶음. 특정 일을 할 때 불러 쓰는 지침 + 스크립트 | `.claude/skills/<이름>/SKILL.md` |

"절대 자동으로 push 하지 말 것"을 CLAUDE.md 에 적으면 부탁이고, 훅으로 걸면 규칙이다. 반드시 지켜야 하는 것은 훅으로 건다.

CLAUDE.md 를 쓸 때 지킬 것:

- **구체적으로** — "좋은 코드" 대신 "함수 50줄 이하".
- **누가 읽어도 같은 뜻으로** — "내가 좋아하는 스타일" 대신 "ESLint airbnb 설정".
- **잘 안 변하는 것만** — 자주 바뀌는 값(환경 변수 목록 등)은 넣지 않는다.
- **짧게** — 매번 컨텍스트에 실리므로 길수록 비용이 들고 지시가 흐려진다.

모델은 일의 무게에 맞춰 고른다. 가볍고 빠른 일은 작은 모델(Haiku), 주된 작업은 중간 모델(Sonnet), 어려운 추론과 최종 검증은 큰 모델(Opus)에 맡기는 식으로 섞어 쓸 수 있다.

## 바로잡은 것

당시 메모에서 나중에 다시 보니 틀렸거나 확인이 필요한 것들이다.

| 당시 메모 | 실제 |
|---|---|
| 훅은 `Skill.md` 에 적는다 | 훅은 `settings.json` 에 등록하고 하네스가 실행한다. 스킬과는 별개다 |
| 스킬마다 "src 폴더만 읽기" 같은 폴더 단위 권한을 줄 수 있다 | 스킬은 쓸 수 있는 도구를 지정하는 정도다. 파일 · 경로 단위 제어는 권한 설정(`permissions`)이나 훅으로 한다 |
| 전역 CLAUDE.md 는 회사 공유 문서, 로컬은 `.env` · `.claude` | 전역은 사용자 홈의 `~/.claude/CLAUDE.md`, 로컬은 `CLAUDE.local.md` 다. `.env` 는 비밀값 파일이지 지침 파일이 아니다 |
| CLAUDE.md 는 200줄 이하가 필수 | 짧게 유지하라는 권고로 알고 있지만, "필수" 상한인지는 확인 필요 |
| 스킬이 다른 스킬을 정해진 순서로 호출해 파이프라인을 만든다 | 정해진 순서를 강제하는 기능인지, 지침으로 모델이 따르게 하는 방식인지 확인 필요 |

## 배운 것

- 프롬프트 → 컨텍스트 → 에이전트로 갈수록 점점 더 자동화되는 방향이다. 그래도 사람의 판단이 필요한 영역은 남고, 에이전트도 결국 사람의 감시 아래서 동작한다.
- **제약이 곧 자유다.** 지침 문서와 훅으로 경계를 분명히 하면 AI 가 그 안에서 최선을 다한다. 지침은 부탁이고 훅은 강제다.
- **컨텍스트는 유한한 자원이다.** 필요한 정보만 골라 넣고, 구조를 잡는 것이 곧 성능이다.
