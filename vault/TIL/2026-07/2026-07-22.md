프론트엔드 E2E(End-to-End) 테스트를 16개에서 46개로 늘리면서 배운 것들을 정리한다. 핵심 주제는 **"백엔드가 없어도 프론트 화면의 동작을 어떻게 검증하나"**였고, 여기서 API 모킹·접근성·시각 회귀·CI까지 여러 갈래로 배움이 이어졌다.

## 백엔드 없이 프론트 단독 E2E — API 모킹

백엔드 서버가 안 떠 있어도 프론트 화면의 "동작"을 검증하고 싶었다. 답은 **API 모킹**이었다.

- Playwright의 `page.route()`로 REST 요청을 가로채 **가짜 응답**을 돌려준다.
- 서버 상태를 테스트 안의 배열로 들고 있으면서 생성·수정·삭제를 반영하면, **"항목을 만들었더니 목록에 실제로 뜬다"**까지 검증할 수 있다.
- 이렇게 짠 시나리오는 나중에 실제 백엔드가 붙으면 **모킹만 걷어내 실제 연동으로 승격**할 수 있다.

한 가지 함정: 모킹 응답은 **네트워크 응답의 원형**을 흉내내야 한다. 앱에 HTTP 인터셉터가 있어 응답 래퍼(`{ data, dataType, totalDataCnt }` 같은)를 벗겨내는 경우, 모킹도 그 **래퍼 형태 그대로** 만들어야 앱이 제대로 받는다. 앱이 최종적으로 쓰는 형태가 아니라 "서버가 보내는 형태"를 흉내내야 한다는 것.

인증이 걸린 페이지는 `addInitScript`로 **sessionStorage 로그인 상태를 미리 주입**해 우회했다.

## 디버깅에서 얻은 교훈 — seed 필드를 컴포넌트에 맞춰라

목록이 안 떠서 한참 추적했더니, 카드 컴포넌트가 `post.views.toLocaleString()`을 부르는데 내 모킹 seed에 `views` 필드가 없어서 `undefined.toLocaleString()`으로 **렌더가 통째로 크래시**하고 있었다.

> 모킹 데이터의 필드는 **실제로 화면을 그리는 컴포넌트가 읽는 필드**에 맞춰야 한다. 하나만 빠져도 조용히 죽는다.

## 병렬 실행과 시각 회귀

- **병렬 부하**: 46개 테스트를 16워커로 돌리니 단일 dev 서버(vite 하나)가 과부하돼서 접근성·시각 테스트가 타이밍으로 실패했다. `--workers=4`로 낮추니 안정. 테스트 개수보다 **서버 처리량이 병목**이었다.
- **시각 회귀(visual regression) baseline**: 화면을 고치면(예: 공통 레이아웃에 요소 추가) 스냅샷 기준이 낡아서 실패한다. `--update-snapshots`로 갱신하면 된다. **"실패"가 항상 회귀는 아니다** — 정당한 변경일 수 있으니 눈으로 확인하고 갱신.

## 접근성 테스트 — axe의 wcag2aa는 생각보다 좁다

접근성 검사에 `axe`를 쓰면서 `withTags(['wcag2aa'])`로 걸었더니, 검사되는 규칙이 **딱 2종**(색 대비 `color-contrast`, `meta-viewport`)뿐이었다.

이유는 `image-alt`·`label`·`link-name` 같은 흔한 규칙들이 사실 **A 레벨(`wcag2a` 태그)**이라 AA 필터에 안 걸리기 때문이다. WCAG는 A < AA < AAA 등급인데, `wcag2aa` 태그는 **AA 전용 규칙**만 가리킨다.

- 게이트를 "색 대비 하나만 강제"로 **좁히려면** `wcag2aa`만
- **전체 접근성**을 보려면 `withTags(['wcag2a','wcag2aa','best-practice'])` → 43종·수백 노드까지 검사

## Playwright UI 모드가 리포트보다 낫다

테스트 결과를 보여줄 때 정적 HTML 리포트보다 **UI 모드(`--ui`)**가 훨씬 변별력 있었다.

- **액션 리스트 + 그 순간의 실제 화면 스냅샷 + 테스트 트리**를 한 화면에 동시에 보여준다.
- 하단 타임라인을 문지르면 화면이 단계별로 바뀐다.
- "테스트가 이렇게 클릭하고 입력하고 확인한다"가 눈에 들어와서, 시연이나 캡처에 유리하다.

## 셀렉터 안정성은 UI 프레임워크에 달렸다

E2E 자동화가 얼마나 쉬운지는 결국 **화면 요소를 얼마나 안정적으로 지목할 수 있나**로 갈린다.

- **표준 DOM + 시맨틱 셀렉터**(`getByRole`, `aria-label`)를 쓰는 프레임워크(Vue 등)는 셀렉터가 안정적이라 E2E가 잘 붙는다.
- 반면 **자체 위젯 · 런타임 자동생성 id · iframe 중첩**을 쓰는 레거시 엔터프라이즈 UI 프레임워크는 셀렉터가 흔들려서, 접근은 되더라도 안정적인 E2E는 어렵다(유지보수 부담 → 사실상 도입 전 검증 필요).

## CI에서 자동으로 돌려야 완성

테스트와 게이트를 로컬에서만 돌리면 반쪽이다. **CI(GitHub Actions 등)에서 PR마다 자동 실행**해야 한다.

```
코드 규칙 게이트 → 빌드 → E2E·접근성 테스트
 → 하나라도 실패하면 머지 차단 (required check)
```

핵심은 "내 PC에서만 통과"가 아니라 **"팀 누구의 코드든 같은 게이트를 통과해야 머지된다"**는 것.

### 곁가지 — 문서 이중 관리

발표 슬라이드를 MD(정본)와 HTML(실물)로 이중 관리할 때, 한쪽을 고치면 **다른 쪽도 동기화**해야 어긋나지 않는다. 슬라이드 번호 재정렬 같은 반복 작업은 **정규식 스크립트로 일괄** 처리하는 게 수동보다 안전했다(수동 번호는 실수가 남는다).
