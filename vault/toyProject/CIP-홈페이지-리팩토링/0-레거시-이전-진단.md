회사 홈페이지를 리팩토링하면서 처음 한 일은 코드를 바꾸지 않고 **지금 어떤 상태인지 진단하는 것**이었다. 목적은 두 가지였다 — 당장은 상단 메뉴와 게시판 몇 개의 디자인을 새로 하고, 길게는 프런트 분리와 DB 전환을 문서로 남기는 것. 이 글은 2026-06-02 에 쓴 구조 분석 · 단계별 가이드 일곱 편을 한 편의 회고로 다시 쓴 것이다. 원문은 비공개 보관함에 있다.

## 진단 — 마크업은 옮겼고, 기능은 아직이다

| 본 것 | 상태 |
|---|---|
| 백엔드 | Spring Boot + Thymeleaf(서버에서 HTML 을 그리는 템플릿 엔진). 사내 공통모듈에 보안 · 설정을 기댄다 |
| 데이터 계층 | MyBatis 의존성은 있는데 **매퍼 · 서비스 · 도메인 계층이 하나도 없다** |
| 컨트롤러 | 전부 정적 템플릿 이름만 돌려준다. DB 를 읽는 곳이 0 곳 |
| 템플릿 | 옛 classic ASP 화면을 1:1 로 옮긴 `<table>` 레이아웃, 고정폭, 인라인 스타일, 반응형 없음 |
| 게시판 | 글 하나에 **컨트롤러 메서드 하나 + 템플릿 하나**. 게시판 컨트롤러 한 개에 메서드가 28개 |

한 줄로 줄이면 **"ASP → Thymeleaf 껍데기 이전" 단계**였다. 화면은 옮겨 왔지만 글 목록과 상세가 모두 HTML 에 박혀 있었다. 게시판이 데이터가 아니라 **페이지로 존재**했고, 글이 늘면 컨트롤러와 템플릿을 계속 더해야 하는 구조였다.

템플릿에는 시대가 다른 흔적이 겹겹이 남아 있었다.

- 드림위버 시절의 메뉴 토글 함수가 템플릿마다 중복 정의돼 있었다.
- ASP 스크립틀릿 `<%= ... %>` 가 옮기다 남은 채로 있어서, 실제로 **브라우저까지 그대로 전송**되고 있었다.
- 공통 조각(top · footer · 메뉴)은 나눠져 있었지만 공통 레이아웃이 없어 페이지마다 `<head>` 와 `<body>` 를 통째로 들고 있었다.
- 버튼이 전부 이미지였다.

## 먼저 띄워 보고, 진단을 확인했다

무엇이든 바꾸기 전에 지금 화면이 뜨는지부터 확인했다(Phase 0). 로컬에서 기동하고 주요 페이지 다섯 개가 모두 정상 응답하는 것을 확인했다. 기동 로그에 "매퍼를 찾지 못했다"는 메시지가 찍혀 **데이터 계층이 없다는 진단이 확정**됐고, 게시판 응답 HTML 에서 ASP 잔재가 그대로 나가는 것도 확인했다.

## 단계 나누기

| 단계 | 무엇 | 왜 이 순서 |
|---|---|---|
| 0 | 빌드 · 실행, 변경 전 화면 캡처 | 비교 기준점이 있어야 고친 게 맞는지 안다 |
| 1 | 공통 레이아웃 도입 + 상단 메뉴 현대화 | 모든 페이지가 공유하니 한 번 고치면 전체에 반영된다 |
| 2 | 게시판 세 종 디자인, 템플릿 통합(28 → 2~3) | 구조가 같은 게시판 셋을 골라 한 패턴을 재사용한다 |
| 3 | 게시판 백엔드 동적화 | "보이는 것" 다음이 "동작하는 것". 당시엔 문서화만 |
| 4 | 프런트 분리 · DB 전환 설계 | 지금 코드를 바꾸는 게 아니라 어디로 갈지 적어 두는 단계 |

몇 가지는 처음부터 정해 두었다.

- **게시판 템플릿 통합은 DB 없이 먼저 한다.** 글마다 있던 템플릿을 상세 템플릿 하나 + 글 번호 파라미터로 바꾸고, 데이터는 우선 코드 안의 목록으로 루프를 돌린다. 디자인만 하더라도 게시판은 결국 동적화가 필요하니 최소한의 골격은 이때 잡아 둔다.
- **공개 홈페이지라 SEO 가 중요하다.** 프런트를 분리한다면 클라이언트 렌더링 SPA 보다 서버 렌더링이 되는 쪽이 이 사이트 성격에 맞다고 봤다.
- **전환은 한 화면씩.** 백엔드를 API 서버로 두고 페이지 단위로 새 프런트로 옮기는 스트랭글러(Strangler) 방식을 적었다.
- **DB 전환은 신규 게시판부터.** Oracle 전용 함수와 조인 문법을 바꿔야 할 목록을 먼저 만들고, 레거시는 천천히 옮긴다.

## 건드리지 않기로 한 것

- **옛 ASP 원본 폴더** — 게시판 CRUD 가 어떻게 동작했는지 알 수 있는 유일한 근거라 참조용으로만 둔다.
- **사내 공통모듈 의존** — 보안 설정이 거기 있어 빌드에 사내 패키지 인증이 필요하지만, 사내 표준이라 우회하지 않는다.
- **죽은 코드와 산 코드를 가른다.** ASP 잔재나 주석 처리된 버튼은 지워도 되지만, 공통 조각 호출과 보안 경로 설정은 건드리지 않는다.
- **DB 가 연동되지 않은 건 버그가 아니다.** 아직 안 만든 것이다.

이후 실제 작업은 이 계획과 다르게 흘렀다. 디자인을 전면 새로 하기로 했고, 최종적으로는 Thymeleaf 를 고치는 대신 **Vue 3 SPA 로 옮겼다**([7. 남은 디벨롭](./7-남은디벨롭.md)).

## 돌아보면

- 이전이 "끝난 것처럼 보이는" 레거시 사이트에서 가장 먼저 확인할 것은 **마크업 이전과 기능 이전을 구분하는 것**이었다. 화면이 다 뜬다고 기능이 옮겨진 게 아니었다.
- 진단은 코드를 읽는 것만으로 끝내지 않고 **띄워서 로그와 응답으로 확인**했다. "매퍼 없음"과 "ASP 잔재가 브라우저로 나감"은 둘 다 실행해 보고서야 확정됐다.
- 계획을 단계로 나눌 때 기준은 **한 번 고쳐서 가장 넓게 반영되는 곳부터**였다. 공통 레이아웃이 첫 번째였던 이유다.
