# AI 세션 합동 발표 — 준비 기록 (2026-08-19)

8주간의 CIP 홈페이지 마이그레이션을 사내 AI 세션에서 발표하기 위해 만든 덱과 대본, 그리고 **그것을 어떻게 구성했는지**의 기록. 발표 자체보다 **"무엇을 증명했다고 말할 수 있는가"** 를 정하는 데 시간을 더 썼다.

- 덱: 본편 26장 + 부록 1장 · 대본: 축자(逐字) 대본 + 부록 A(시간)·B(예상질문)·C(강점·약점)
- 대본 원문은 [9. 발표 대본 원문](./9-발표대본-원문)에 그대로 두었다.

## 프로젝트 규모

커밋 이력에서 실측한 값이다. 발표에서 "몇 달짜리였나"를 물으면 답할 수 있어야 해서 정리했다.

| 항목 | 값 |
|---|---|
| 기간 | 2026-06-01 ~ 07-27 — **약 8주** |
| 프론트엔드 | 라우트 29개 · Vue 컴포넌트 46개 |
| 백엔드 | API 15개 · Java 154개 · DDD 4계층 |
| 자동 테스트 | FE 46 + BE 173 = **219개** |
| 레거시 정리 | table 592회 제거 · 뉴스 상세 HTML 20→1 · 솔루션 템플릿 18→1 + 데이터 13종 |
| 커밋 | 186개 |

## 초점을 옮긴 이유

처음 덱의 주제는 "AI를 어떻게 활용했나"였다. 그런데 이 프레임에는 답하기 어려운 질문이 하나 붙는다 — **"그래서 얼마나 빨라졌는데?"**

같은 프로젝트를 사람 손으로만 해 본 대조군이 없다. 배수를 말하는 순간 근거를 요구받고, 근거가 없으면 그 다음 주장까지 같이 무너진다. 그래서 초점을 이렇게 옮겼다.

> **레거시를 현대 스택으로 옮기는 게 실제로 가능하고, 그 결과를 믿을 수 있게 만들 수 있다는 것의 증명**

이 프레임에서는 세 가지가 성과가 된다.

1. **결과물** — 20년 된 정적 화면이 지금 동작하는 상태가 됐다
2. **경험** — 어디가 막히고 무엇을 먼저 정해야 하는지를 실제로 겪었다
3. **재사용 자산** — 스킬과 테스트 관문은 다음 프로젝트에 그대로 붙는다. 특히 백엔드 테스트 체계는 스택을 가리지 않는다

부수적으로 "운영에 바로 올릴 수 있냐"는 질문의 무게도 달라진다. 운영 배포는 이번 목표가 아니었고, **관리자 기능이 원래 없던 것에서 등록·수정·삭제가 되는 형태까지 온 것**이 확인하려던 바다.

## Playwright를 AI와 어떻게 묶었나

덱에서 가장 크게 손본 부분이다. 원래는 같은 "Playwright"라는 단어가 두 가지 뜻으로 흩어져 있었다 — AI가 브라우저를 조종한 개발 도구(카드 1개)와, 산출물인 E2E 테스트 46개(슬라이드 3장). 듣는 쪽에서는 "AI가 테스트를 짠 건가, AI가 화면을 본 건가"가 섞인다. 한 장으로 묶어 세 갈래로 정리했다.

| 갈래 | 무엇 |
|---|---|
| ① **만들 때 — AI의 눈** | MCP로 AI가 브라우저를 직접 조종. 목업 3안 스크린샷 비교, 라우트 29개 자동 클릭 + 콘솔 에러 수집. "이 화면 어때?"를 말로 설명할 필요가 없다 |
| ② **짤 때 — AI가 테스트 저자** | E2E 46개를 AI가 작성. 대신 셀렉터를 규약으로 못 박음 — `getByRole`·`aria-label` 같은 **사람 기준 이름**만 허용, 자동 생성 ID·CSS 클래스 금지 |
| ③ **깨졌을 때 — AI가 판독** | 실패 시 단계별 스크린샷·트레이스로 원인 특정 → 수정 → 재실행 |

②가 핵심이다. 마지막 장에서 "46개를 차세대 Vue에 그대로 옮길 수 있다"고 주장하는데, **그게 성립하는 이유가 바로 이 셀렉터 규약**이다. 디자인이 바뀌어도, 프레임워크가 바뀌어도 "가입 버튼"은 여전히 "가입 버튼"이니까. 기존 덱에는 이 연결 고리가 없어서 주장만 떠 있었다.

> **MCP** — Model Context Protocol. AI가 외부 도구(여기서는 브라우저)를 직접 조작할 수 있게 연결해 주는 규약.

## WebSquare는 왜 본편이 아니라 부록인가

"레거시 마이그레이션이 된다"고 말하면 반드시 따라오는 질문이 있다 — **"그럼 우리 메인도 되냐?"** 회사 메인은 WebSquare 기반이다.

여기서 정직해야 할 지점이 있다. 이번에 증명한 것은 **정적 HTML → Vue**이지 **WebSquare → Vue가 아니다.** WebSquare 화면 하나로 PoC조차 해보지 않았다. 그래서 이 내용을 본편에 넣지 않고 부록 1장으로 뺐다.

- 본편에 박으면 논지(마이그레이션 증명)가 흐려진다
- 게다가 "메인 스택을 갈아엎자"는 주장으로 읽힌다 — 발표자 권한 밖의 이야기다
- 질문이 나오면 꺼내고, 안 나오면 안 꺼낸다

부록 장은 5축 비교표로 만들었다: **테스트 자동화 / AI 활용도 / 접근성 / 화면 증가 대응 / 생태계·조달.** 각 축마다 이번 프로젝트에서 실제로 확인된 근거를 붙이고, 하단에 "전면 교체 주장이 아니며 WebSquare PoC는 미실측"이라는 방어 문구를 달았다.

WebSquare가 어려울 것으로 보는 이유(요소 이름의 런타임 자동 생성, iframe 중첩, 커스텀 위젯, 자체 렌더 시점)는 **근거 있는 예상이지 실측이 아니다.** 표에도 그렇게 표시했다.

## 근거 수치 — 전수 대조 결과

발표에 들어간 백엔드 A/B 실험 수치를 원본 실험 문서와 하나씩 맞춰봤다. 같은 시작 상태(테스트 전량 삭제)에서 절차(test-gate) 유무만 바꾼 대조 실험이다.

| 지표 | 그냥 시켰을 때 | 절차 적용 |
|---|---|---|
| JaCoCo 라인 커버리지 | 52.36% (577/1102) | **96.91%** (1068/1102) |
| PIT 뮤테이션 (동일 157변이) | 119/157 = 76% | **157/157 = 100%** |
| `@Test` 메서드 | 108개 | **173개** |
| 통합 테스트 | 0 | **48** (TestContainers 실 PostgreSQL) |
| 작업 시간 | 13분 02초 | 34분 55초 (2.7배) |
| 토큰 | 176,964 | 300,848 (1.7배) |
| **테스트 1개당 토큰** | 1,639 | 1,739 (**약 6% 차**) |

마지막 줄이 이 실험의 핵심이다. 비용이 1.7배로 늘었지만 **단가는 같다.** 늘어난 비용의 대부분은 루프 재시도가 아니라 **테스트를 더 많이 작성한 값**이다. "비싸졌다"가 아니라 "더 많이, 제대로 만들었다"로 읽어야 한다.

> **JaCoCo** — 테스트가 코드를 몇 퍼센트나 실행했는지 재는 커버리지 측정 도구.
> **PIT (뮤테이션 테스팅)** — 코드에 일부러 작은 버그를 심고, 테스트가 그걸 잡아내는지 보는 도구. 커버리지만으로는 "실행만 하고 검증은 안 하는 무늬만 테스트"를 걸러낼 수 없어서 함께 쓴다.

### 대조하다 찾은 오류 2건

수치를 맞춰보는 김에 덱 전체를 훑었더니 실제 오류가 나왔다.

1. **빌드 명령이 `mvnw clean verify`로 적혀 있었다** — 이 프로젝트는 Gradle이다. Maven은 2026-07-02에 은퇴했고 실험 base 커밋은 07-08이라 실험 당시에도 Gradle이었다. 게다가 바로 다음 장이 "Gradle — gradlew 포함"이라 **같은 덱 안에서 모순**이었다 → `gradlew clean build`로 수정
2. **대본은 "시간 두 배 반, 비용 한 배 반"인데 덱과 원본은 2.7배 / 1.7배** → 대본을 실측치로 수정

수치를 인용할 때는 원본까지 내려가서 맞춰봐야 한다는 걸 다시 확인했다.

## 강점과 약점을 대본에 적어둔 이유

무엇이 잘 되어 있고 어디가 뚫려 있는지 **알고 들어가는 것**과 모르고 들어가는 것은 다르다. 강점은 시간을 쓸 곳, 약점은 먼저 밝히거나 방어할 곳이다.

**강점**

1. 논지가 하나로 관통한다 — 표지부터 마지막 장까지 "AI가 만든 걸 어떻게 믿나"로 이어진다
2. A/B 대조 실험이 결정적 무기다 — 의견이 아니라 데이터라 반박이 어렵다
3. "됐다"를 실물로 보여준다 — 시연 + 테스트가 자동 캡처한 화면
4. **일부러 AI를 안 쓴 판단**이 있다 — 색 검사를 정규식으로 만들어 토큰 0으로 상시 실행. "AI를 무조건 쓰는 사람"이 아니라 "적재적소에 쓰는 사람"으로 보인다
5. 과장이 없어서 나머지 주장의 신뢰도가 올라간다

**약점** — 초점을 옮기면서 순위가 바뀌었다

| 위험 | 약점 |
|---|---|
| ★★★ | 증명한 건 정적 HTML→Vue이지 **WebSquare→Vue가 아니다** |
| ★★★ | "가능하다"의 범위가 **정형 페이지에 한정**된다 |
| ★★ | 백엔드 8장이 본인 작업분이 아니다 |
| ★★ | 신설 장의 미검증 주장 2건 |
| ★ | 속도 이득을 숫자로 못 낸다 (대조군 없음) |
| ★ | "46개 전부 자동"의 정확한 범위 — CI에서 상시 도는 건 36개 |

마지막 항목은 시각 회귀 테스트 10개가 OS별 폰트 렌더 차이 때문에 로컬 전용이기 때문이다. 이건 **빼지 않고 문구만 정확하게** 고쳤다. 옛 화면과 새 화면을 픽셀로 대조하는 테스트는 마이그레이션 정확성의 직접 증거라, 빼면 오히려 증명이 약해진다.

## 정리

준비하면서 가장 많이 한 일은 슬라이드를 늘리는 게 아니라 **"이건 증명했고 저건 아직 아니다"의 경계를 긋는 것**이었다. 경계가 흐리면 강한 주장 하나가 약한 주장 하나에 같이 무너진다. 반대로 경계가 선명하면 나머지 25장이 전부 근거로 작동한다.

- 증명한 것: 정형 패턴 레거시 → Vue 마이그레이션, 그리고 그 결과를 검증하는 자동화 체계
- 증명하지 않은 것: WebSquare → Vue, 비정형 화면 일괄 이식, 전체 속도 이득
