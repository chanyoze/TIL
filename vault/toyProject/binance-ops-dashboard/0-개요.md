# Binance 운영 대시보드 — 개요

> 작성: 2026-08-19 / 대상: [chanyoze/binance-ops-dashboard](https://github.com/chanyoze/binance-ops-dashboard)
> 기간: 2026-08 · TypeScript 모노레포 · PostgreSQL 16 · Next.js

BTCUSDT·ETHUSDT 시세를 WebSocket 으로 상시 수집하고, **어떤 이유로든 데이터에 구멍이 생기면
스스로 감지해 REST 로 메우는** 파이프라인. 대시보드는 시장 지표와 함께 **파이프라인 자체의
건강 상태**를 보여준다.

---

## 1. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 언어 | TypeScript (npm workspaces 모노레포) |
| 수집기 | Node.js **독립 워커** — WS 수집 · 백필 · 무결성 스캐너 |
| 웹 | Next.js (App Router) + React |
| DB | PostgreSQL 16 · Drizzle ORM |
| 실시간 전송 | Postgres `LISTEN/NOTIFY` → SSE |
| 실행 | Docker Compose (postgres → migrate → collector → web) |
| 테스트 | 228건 (단위 195 + 통합 33) + **변이 검증 17건** |

```bash
cp .env.example .env && docker compose up     # → http://localhost:3000
```

## 2. 이 시스템이 푸는 문제는 하나다

시스템이 다루는 문제는 결국 하나 — **데이터에 구멍이 생기는 순간들.**
최초 실행 시(과거 데이터가 없음), 서버가 죽었다 살아났을 때, 네트워크가 잠깐 끊겼을 때.

이 셋은 사실 같은 문제다. *"내가 가진 마지막 봉이 언제인가"*를 묻고 거기서부터 채우면 된다.

```ts
const last = await db.maxOpenTime(symbol, '1m')

const from = last ?? (now - BACKFILL_DAYS * DAY)
//           ↑ 이 한 줄이 "최초 백필"과 "재시작 갭 백필"을 가른다

await ensureRange(symbol, '1m', from, now)
connectWebSocket()
```

**같은 함수가 네 가지 상황을 처리한다.**

| 상황 | from | to | 호출 주체 |
|---|---|---|---|
| 최초 실행 | `now - 7d` | `now` | 부팅 시퀀스 |
| 서버 재시작 | DB 마지막 봉 | `now` | 부팅 시퀀스 |
| WS 재연결 직후 | 끊긴 시각 | `now` | 재연결 핸들러 |
| 중간 구멍 발견 | 구멍 시작 | 구멍 끝 | 무결성 스캐너 |

성립하는 이유는 **멱등성**이다. `(symbol, interval, open_time)` 을 기본키로 두고
`ON CONFLICT DO UPDATE` 로 쓰기 때문에 같은 구간을 몇 번 다시 긁어도 안전하다.
그래서 **구간을 일부러 겹치게 잡아도 된다.**

## 3. 시스템 구조

```
   Binance                  ┌─────────────┐
   ├─ WebSocket  ──실시간──▶ │             │
   └─ REST API   ──백필───▶ │  collector  │ ──▶ ┌──────────┐
                            │   (워커)     │     │ Postgres │
                            └─────────────┘     └────┬─────┘
                                                     │ LISTEN/NOTIFY
                                              ┌──────▼──────┐
                                    브라우저 ◀─│   Next.js   │
                                        SSE   │   (웹)      │
                                              └─────────────┘
```

수집기와 웹 서버는 **별도 프로세스**다. 생명주기가 다르기 때문 — 웹은 배포마다 재시작되고
트래픽에 따라 복제되지만, 수집기는 무중단으로 살아 있어야 하고 복제되면 중복 수집이 발생한다.
합쳐두면 *대시보드 CSS 한 줄 수정이 데이터에 구멍을 낸다.*

두 프로세스는 서로를 직접 호출하지 않는다. **Postgres 만이 유일한 접점**이다.

## 4. 실동작 검증 결과

| 시나리오 | 결과 |
|---|---|
| 최초 실행 | `reason=initial` → 심볼당 **10,081봉**(7일) 백필 후 WS 연결 |
| 수집기 2분 중단 후 재개 | `reason=restart` → 갭 감지·복구, **남은 구멍 0** |
| **16시간 정지 후 재시작** | `gapMinutes=663` → 심볼당 664봉 자동 복구 |
| 연속성 검사 / 커버리지 | `gap_count = 0` / `100.00%` |
| DB 2분 정지 후 복구 | 수집기 **재시작 없음** · 구멍 6봉을 스캐너가 회수 |
| **4일 정지 후 재시작** (2026-08-19 실측) | `gapMinutes=5866` → 심볼당 **5,866봉 · 6페이지 · 1.1~1.6초** |

16시간 건은 만든 시나리오가 아니다. 개발 중 Docker 를 꺼 둔 사이 실제로 생긴 공백이고,
재시작하자 부팅 시퀀스가 그대로 메웠다. 마지막 줄도 마찬가지로 PC 를 끈 사이 생긴 것이다.

`source` 컬럼이 복구 과정을 데이터로 남긴다.

```
13:14  ws    ← 죽기 전 실시간 수집
13:15  rest  ← 죽는 순간 미완성이던 봉을 백필이 확정본으로 덮음
13:16  rest  ┐
13:17  rest  ├ 죽어 있던 구간을 백필이 메움
13:18  rest  ┘
13:19  ws    ← 재시작 후 실시간 재개
```

## 5. 가장 위험한 장애는 "끊긴 걸 모르는 것"

| 장애 | 대응 |
|---|---|
| WS 연결 끊김 | 지수 백오프 재연결 (1s → 최대 30s, jitter) |
| Binance 24h 강제 종료 | 위 재연결 로직이 동일하게 흡수 |
| **좀비 연결** (끊김 미감지) | `lastMessageAt` watchdog — 10초 무소식이면 강제 재접속 |
| 재연결 동안의 누락 | 재연결 직후 갭 백필 자동 호출 |
| 원인 불명의 누락 | 무결성 스캐너가 주기적 연속성 검사 후 자가 치유 |
| REST rate limit | weight 카운터 + 응답 헤더 보정 + `Retry-After` 존중 |
| 프로세스 크래시 | `restart: unless-stopped` → 재시작 시 갭 백필 |
| DB 장애 | **버퍼를 두지 않음** — 수집기는 살아남고 구멍은 스캐너가 회수 |

TCP 연결이 살아 있는데 데이터만 안 오면 `onclose` 가 호출되지 않아 재연결이 영영 발동하지
않고, **대시보드는 멀쩡한 얼굴로 몇 시간 전 값을 띄운다.** watchdog 이 이 조용한 실패를 잡는다.
