# 설계 결정 — 왜 그렇게 만들었는가

각 결정을 **"이게 좋아서"가 아니라 "이걸 안 골랐을 때의 대가"** 로 적는다.
원문 근거는 [docs/ARCHITECTURE.md](https://github.com/chanyoze/binance-ops-dashboard/blob/main/docs/ARCHITECTURE.md).

---

## 1. 수집기와 웹을 별도 프로세스로 나눴다

**생명주기가 다르기 때문.** 웹은 배포마다 재시작되고 트래픽에 따라 복제되지만, 수집기는
무중단으로 살아 있어야 하고 복제되면 중복 수집이 발생한다.

합쳐두면 **대시보드 CSS 한 줄 수정이 데이터에 구멍을 낸다.**

- **대가**: 프로세스가 둘이라 실행·배포·로그가 각각이다. Docker Compose 로 묶어 상쇄했다.
- 두 프로세스는 서로를 직접 호출하지 않는다. **Postgres 만이 유일한 접점**이다.

---

## 2. 쓰기 버퍼도, 재시도 큐도, Kafka 도 두지 않았다

> **원본이 Binance 에 남아 있다. Binance API 자체가 우리의 백업 저장소다.**

복구 가능한 원본이 외부에 있는데 자체 버퍼를 만드는 것은 **이미 해결된 문제를 다시 만드는 일**이다.
버퍼를 두면 크기·만료·순서·중복을 관리해야 하고, 그 코드가 새로운 장애 지점이 된다.

DB 쓰기가 실패하면 그냥 로그를 남기고 넘어간다. 그 구간은 구멍으로 남고 **스캐너가 다음
주기에 회수**한다. 이미 있는 장치가 처리한다.

- **성립하지 않는 경우(한계까지 같이 말한다)**
  - 원본이 외부에 없다면 성립하지 않는다. 우리가 유일한 사본이면 버퍼가 필요하다.
  - Binance 의 kline 조회 가능 기간을 넘겨 장애가 지속되면 그 구간은 복구할 수 없다.
  - 초 단위 체결 원본을 보존해야 하는 요구가 생기면 재검토 대상이다.

---

## 3. 1분봉만 수집하고 상위 인터벌은 SQL 집계로 만든다

5분봉·1시간봉을 각각 수집하지 않는다. 1분봉만 저장하고 나머지는 `date_bin` 으로 접는다.

인터벌마다 수집하면 무결성 검증을 인터벌 수만큼 해야 하고, 같은 시각의 1분봉 5개와
5분봉 1개가 어긋나는 정합성 문제가 새로 생긴다. 원본 해상도를 하나로 두면
**검증할 진실이 하나**다.

```sql
date_bin('5 minutes', open_time, timestamptz 'epoch')
```

기준점을 **epoch 로 잡아야** Binance 의 봉 경계(:00, :05, …)와 어긋나지 않는다.
데이터의 첫 시각을 기준으로 접으면 봉 경계가 *수집 시작 시각에 따라 달라진다.*

- **대가**: 조회 시 집계 부하. 인덱스 `(symbol, interval, open_time DESC)` 로 커버되고
  24시간치가 심볼당 1,440행이라 문제되는 규모가 아니다.

---

## 4. 지표를 애플리케이션이 아니라 SQL 에서 계산한다

VWAP·이동평균·Taker 비율·커버리지·지수화 상대강도를 전부 SQL 에서 낸다.

**대역폭 때문만이 아니다.** 1시간봉 24개를 보려고 1,440행을 내려보내는 것도 낭비지만,
더 나쁜 것은 **같은 지표가 화면마다 다르게 계산될 수 있다**는 점이다.
정의를 SQL 한 곳에 두면 정의가 하나로 유지된다.

읽기 경로는 `AnalyticsRepository` 로 **쓰기 경로와 파일을 나눴다.** 쓰기는 멱등성과 정확한
한 행이 관심사고, 읽기는 집계와 응답 크기가 관심사다. 한 클래스에 두면 *"차트가 필요해서"*
수집 경로의 메서드를 고치는 일이 생긴다.

---

## 5. aggTrade(개별 체결)를 저장하지 않는다

Taker 매수 비율은 개별 체결을 모아야 나올 것 같지만, **Binance 가 kline 안에
`takerBuyBaseVolume` 으로 이미 집계해서 준다.**

저장하지 않는 결정적 이유는 따로 있다 — aggTrade 는 `fromId` 기반 페이지네이션이라
**시간 기반 복구 모델과 맞지 않는다.** 저장하면 *"구멍을 시간으로 찾아 시간으로 메운다"* 는
모델 밖에 있는 복구 경로가 하나 더 생긴다.

받기는 받는다. 틱 최신가를 `collector_state.last_price` 에 갱신하는 데 쓴다
(1분봉보다 최대 60초 앞선 가격). **받아서 쓰고 버린다.**

---

## 6. 시계열 DB(InfluxDB) 가 아니라 PostgreSQL

시세 데이터라 시계열 DB 가 먼저 떠오르는 게 자연스럽다. 검토했고 쓰지 않기로 했다.
무게 순으로:

1. **핵심이 쓰기 성능이 아니라 멱등성이다.** 설계의 척추가 `ON CONFLICT DO UPDATE` 다.
   InfluxDB 도 같은 키에 쓰면 값이 덮이지만 그건 *last write wins* 이지 **명시적 upsert
   의미론이 아니다.** 이 프로젝트엔 *"키를 안 주면 유지, 명시적 null 이면 삭제"* 라는
   **부분 갱신**이 필요했고 그건 `SET` 절이 있어야 표현된다.
   실제로 그 구분을 뭉갰다가 uptime 지표가 통째로 죽은 적이 있다.
2. **집계를 SQL 에서 한다는 결정과 한 몸이다.** 윈도우 함수·`date_bin`·`count(*) filter`.
3. **규모가 요구하지 않는다.** 2심볼·1분봉·7일 = 약 2만 행, 5MB 대.
   압축·다운샘플링·보존 정책이라는 이점이 발동할 스케일이 아니다.
   **이점이 없는 도구를 들이면 남는 건 운영 비용뿐이다.**
4. **인프라를 늘리지 않는다.** 컨테이너가 하나 늘면 채점자가 실행에 실패할 지점도 하나 는다.
5. **운영 지표와 시세가 한 DB 에 있다.** 저장소를 나누면 그 조인이 애플리케이션으로 올라온다.
6. (후순위지만 실제로 작용) **회사가 쓰는 스택이다.** 기술적 우열이 갈리지 않는 지점이라면
   읽는 사람이 이미 아는 도구를 고르는 편이 낫다고 판단했다.

**언제 시계열 DB 가 맞는가** — 초당 수만 포인트를 쓰거나, 원본 tick 을 장기 보관하며 자동
다운샘플링이 필요하거나, 수년치를 압축할 때. 이 과제는 셋 다 아니다.

**확장 경로는 TimescaleDB.** PostgreSQL 확장이라 같은 SQL 로 하이퍼테이블을 얻는다.
저장소를 갈아타는 **마이그레이션이 아니라 확장**이라는 게 요점 — 지금의 선택이 나중의
선택지를 좁히지 않는다.

---

## 7. 실시간 전송은 Redis 가 아니라 `LISTEN/NOTIFY` → SSE

인프라를 늘리지 않는다는 논리(6-4)와 같다. 그리고 **어댑터 뒤에 숨겼다** — `RealtimeBus`
인터페이스로 두었으므로 서버리스처럼 `LISTEN/NOTIFY` 를 못 쓰는 환경에서는 Redis Pub/Sub
구현으로 갈아끼우면 된다.

---

## 8. 의도적으로 하지 않은 것

| 하지 않은 것 | 이유 |
|---|---|
| aggTrade 원본 저장 | 필요 없고, 복구 모델과 맞지 않는다 |
| 쓰기 버퍼 · 재시도 큐 · Kafka | 원본이 Binance 에 있다 |
| 여러 인터벌 각각 수집 | 검증할 진실이 늘어난다 |
| 이중 축 차트 | 눈금 설정만으로 착시를 만들 수 있다. 지수화로 단일 축 |
| 초록/빨강만으로 등락 표현 | 적록색약에서 두 색의 거리가 **ΔE 4.1**. 부호와 아이콘 병기 |
| 오더북(depth) 수집 | 요구사항이 아니며 복잡도만 는다 |
| 심볼 하드코딩 | `SYMBOLS` 환경변수로 처리 |

---

## 9. 알려진 한계 — 넘는 방법까지

몰라서 남은 게 아니라 **과제 범위에서 의도적으로 멈춘 지점**이고, 넘을 자리는 설계에 미리 냈다.

- **수집기는 단일 인스턴스 전제다.** 복제하면 같은 심볼을 두 번 받는다.
  → 확장의 축을 **심볼**로 잡아 두었다. 심볼은 코드에 박히지 않고 `SYMBOLS` 환경변수로만
  들어오므로 워커마다 다른 묶음을 주면 그대로 수평 확장된다. 자동 재분배가 필요한 규모라면
  그때 조정 계층(리스 기반 파티션 할당)을 얹는다.
- **`LISTEN/NOTIFY` 는 서버리스에서 못 쓴다.** → `RealtimeBus` 인터페이스 뒤에 두었다.
