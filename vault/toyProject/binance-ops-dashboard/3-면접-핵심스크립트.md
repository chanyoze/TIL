# 핵심 스크립트 — 입으로 나와야 하는 것

> **읽는 법**: 길이별 설명 → 척추 문장 → 버린 선택지. 막히면 **척추 문장**으로 돌아온다.
> 원칙 — **"이게 좋아서"가 아니라 "이걸 안 골랐을 때의 대가"** 를 말한다.

---

## 1. 30초 (엘리베이터)

> Binance 실시간 시세를 WebSocket 으로 상시 수집하고, 어떤 이유로든 데이터에 구멍이
> 생기면 **스스로 감지해 REST 로 메우는** 파이프라인입니다. 대시보드는 시세만이 아니라
> **파이프라인 자체의 건강 상태**를 함께 보여줍니다.
> 과제 제목이 "운영 대시보드"였고 Part 1 이 요구한 것이 수집의 안정성과 백필이었기
> 때문에, 그 둘을 하나의 서사로 이었습니다.

---

## 2. 2분 (설계 요약)

30초 버전에 아래를 덧붙인다.

> 요구사항이 세 줄로 보였지만 사실 하나였습니다 — **데이터에 구멍이 생기는 순간들.**
> 구멍은 네 경로로 생깁니다. 최초 실행(과거 데이터 없음), 프로세스 크래시,
> WS 연결 끊김, DB 일시 장애.
>
> 네 경우 모두 묻는 질문이 같습니다. **"내가 가진 마지막 봉이 언제인가."**
> 그래서 복구 코드를 `ensureRange(symbol, interval, from, to)` **하나로 통합**했습니다.
>
> 이게 성립하는 전제는 **멱등성**입니다. `(symbol, interval, open_time)` 을 기본키로 두고
> `ON CONFLICT DO UPDATE` 로만 쓰기 때문에, 같은 구간을 몇 번을 다시 긁어도 안전합니다.
> 그래서 구간을 **일부러 겹치게** 잡을 수 있고, 백필과 실시간 수집이 같은 봉을 동시에 써도
> 되고, WS 가 저장한 미완성 봉이 REST 의 확정 봉으로 자연히 덮입니다.
>
> 수집기와 웹은 별도 프로세스입니다. 생명주기가 다르기 때문입니다 —
> 웹은 배포마다 재시작되고 트래픽에 따라 복제되지만, 수집기는 무중단이어야 하고
> 복제되면 중복 수집이 됩니다. 합치면 **대시보드 CSS 한 줄 수정이 데이터에 구멍을 냅니다.**

---

## 3. 5분 (구조까지)

2분 버전에 아래를 덧붙인다.

> 두 프로세스는 서로를 직접 호출하지 않습니다. **Postgres 가 유일한 접점**이고
> 수집기는 웹의 존재를 모릅니다. 실시간 전송은 Postgres `LISTEN/NOTIFY` → 서버에서
> 팬아웃 → 브라우저로 SSE 입니다.
>
> 지표는 전부 SQL 에서 계산합니다. 애플리케이션 메모리에 누적 상태를 두면 웹을
> 재시작할 때 리셋되고 인스턴스를 늘리면 값이 갈립니다. 지표 정의가 한 곳에만 있어야
> 화면이 **조용히 거짓말하지 않습니다.**
>
> 캔들은 **1분봉만** 수집하고 5m·1h 는 SQL 롤업으로 만듭니다. 인터벌마다 수집하면
> 무결성 검증을 인터벌 수만큼 해야 하고 정합성 불일치가 생깁니다.
>
> 검증은 두 갈래입니다. 판단(재연결 간격·watchdog 임계·갭 계산)은 가짜 소켓과 가짜
> 타이머로 결정적으로 테스트하고, 실제 네트워크를 타는 경로는 `npm run demo:chaos` 로
> 확인합니다. 수집기를 실제로 죽였다 살려서 복구를 검증하고 PASS/FAIL 을 냅니다.

## 4. 척추 — 이 한 문장이 전부다

> ### **"데이터에 구멍이 생기는 순간들"이 하나의 문제이고, 그것을 하나의 함수로 푼다.**
> ### **그걸 가능하게 하는 전제가 UPSERT 멱등성이다.**

여기서 모든 것이 파생된다. **막히면 이 문장으로 돌아온다.**

| 구멍이 생기는 경로 | from | to | 누가 부르나 |
|---|---|---|---|
| 최초 실행 (과거 없음) | `now - 7d` | `now` | 부팅 시퀀스 |
| 프로세스 재시작 | DB 의 마지막 봉 | `now` | 부팅 시퀀스 |
| WS 재연결 직후 | 끊긴 시각 | `now` | 재연결 핸들러 |
| 중간 구멍 발견 | 구멍 시작 | 구멍 끝 | 무결성 스캐너 |

```ts
const last = await db.maxOpenTime(symbol, '1m')
const from = last ?? (now - BACKFILL_DAYS * DAY)   // ← 이 한 줄이 최초/재시작을 가른다
await ensureRange(symbol, '1m', from, now)
connectWebSocket()
```

### 꼭 같이 외울 것

재시작 시 `last + interval` 이 아니라 **`last` 자체부터** 다시 긁는다.
마지막 봉은 **미완성 상태로 저장돼 있을 수 있기 때문**이다.
*"중복이니 건너뛰자"* 가 틀린 최적화인 이유이고, **멱등성이 없으면 할 수 없는 선택**이다.

### 증거로 쓸 것 — `source` 컬럼이 복구를 데이터로 남긴다

```
13:14  ws    ← 죽기 전 실시간 수집
13:15  rest  ← 죽는 순간 미완성이던 봉을 백필이 확정본으로 덮었다
13:16  rest  ┐
13:17  rest  ├ 죽어 있던 4분을 백필이 메웠다
13:18  rest  ┘
13:19  ws    ← 재시작 후 실시간 재개
```

## 5. 버린 것을 외운다 — 질문은 대개 버린 쪽에서 온다

| # | 결정 | **버린 것과 그 이유** |
|---|---|---|
| D-01 | 수집기·웹을 **별도 프로세스**로 | 한 프로세스 통합 — 배포마다 수집이 끊기고, 웹을 복제하면 중복 수집 |
| D-02 | 백필은 **`ensureRange` 하나**로 | 최초용·갭용 함수 분리 — 같은 문제를 두 번 푸는 것. 분기 버그가 재시작 때만 터진다 |
| D-03 | **멱등성을 데이터 계층**에서 | 애플리케이션 중복 체크 — 경합에 취약하고, 미완성 봉을 확정 봉으로 덮지 못함 |
| D-04 | 좀비 연결을 **watchdog** 으로 | ping/pong 만 믿기 — 소켓은 OPEN 인데 메시지만 안 오는 상태를 못 잡는다 |
| D-05 | **1분봉만** 수집, 상위는 SQL 롤업 | 인터벌별 수집 — 무결성 검증을 인터벌 수만큼, 정합성 불일치 발생 |
| D-06 | rate limit **능동 관리**(weight 카운터) | 429 맞고 대응 — 이미 늦다. `Retry-After` 존중 백오프 병행 |
| D-07 | 지표는 **SQL 에서** 계산 | 앱 메모리 누적 — 웹 재시작 시 리셋, 인스턴스 늘리면 값이 갈림 |
| D-08 | aggTrade 는 받되 **저장 안 함** | 원본 저장 — Taker 비율은 kline 의 `takerBuyBaseVolume` 로 이미 나온다. aggTrade 는 `fromId` 페이지네이션이라 **시간 기반 복구 모델과 안 맞고**, 저장하면 복구 경로가 하나 더 생긴다 |
| D-09 | 실시간은 **LISTEN/NOTIFY → SSE** | Redis 추가 — 컨테이너 하나 늘고 실패 지점 하나 는다. 대신 `RealtimeBus` 인터페이스로 감싸 교체 가능하게 |
| D-12 | **쓰기 버퍼·재시도 큐 없음** | 버퍼/Kafka — **원본이 Binance REST 에 남아 있다. Binance API 자체가 우리의 백업 저장소다.** 복구 가능한 원본이 외부에 있는데 자체 버퍼를 만드는 건 해결된 문제를 다시 만드는 일 |
| — | DB 는 **PostgreSQL** (시계열 DB 아님) | InfluxDB — 핵심이 쓰기 성능이 아니라 **멱등성**. last-write-wins 로는 '키 미제공=유지 / 명시적 null=삭제' 부분 갱신을 표현 못 한다. 2만 행 규모에서 압축·다운샘플링 이점은 발동 안 하고 컨테이너만 는다. 확장 경로는 TimescaleDB — **마이그레이션이 아니라 확장** |
| D-13 | **npm workspaces** (pnpm 아님) | pnpm — 채점자 환경에 없을 수 있다. 재현성이 이 프로젝트의 약속 |
| — | 가격·수량은 **문자열** | `parseFloat` — JS number 는 배정밀도라 시세를 정확히 표현 못 한다. Postgres `NUMERIC` ↔ TS `string`, 계산은 SQL 에서 |
| — | 스트림이 멎으면 **폴링으로 갱신** | SSE 만 믿기 — `EventSource` 는 헤더만 받아도 `open` 을 내므로, 프록시가 버퍼링하면 화면이 "연결됨"인 채 영원히 멈춘다. **서버 watchdog 과 같은 원칙을 클라이언트에 적용** |
| — | 저장은 UTC, **화면은 KST** | 화면도 UTC — 운영 화면의 첫 질문("얼마나 최신인가")의 기준은 벽시계다. 단 `demo:chaos` 출력까지 함께 맞춰 **절반만 바꾸지 않았다** |

### 특히 자주 물어볼 세 개

**"왜 aggTrade 를 저장 안 했나"**
→ Taker 비율은 kline 이 이미 준다. aggTrade 는 `fromId` 기반이라 시간 범위로 복구하는
이 시스템의 모델과 **축이 다르다.** 저장하면 복구해야 할 데이터 종류가 하나 더 늘고,
그 복구는 `ensureRange` 로 안 된다 — **통합이 깨진다.** 받아서 최신가만 갱신하고 버린다.

**"DB 가 죽으면 그 사이 데이터는?"**
→ 구멍으로 남기고 무결성 스캐너가 회수한다. 버퍼를 두지 않는 이유는 **원본이 Binance 에
있기 때문**이다. 버퍼를 두면 버퍼의 유실·크기·순서를 또 관리해야 한다.

**"수집기를 늘리려면?"**
→ 확장 축을 **심볼**로 잡아 뒀다. 심볼은 코드에 안 박히고 `SYMBOLS` 환경변수로만
들어온다. 워커마다 다른 묶음을 주면 그대로 수평 확장된다. 한 심볼을 두 워커가 잡는
것만 막으면 되고 **그건 배치 구성의 문제**다.

## 6. 의도적으로 하지 않은 것

"안 한 것"을 **먼저** 말할 수 있으면 범위 판단을 했다는 뜻이 된다.

- **오더북(depth) 수집** — 요구사항이 아니고 복잡도만 는다
- **쓰기 버퍼 / 재시도 큐 / Kafka** — 원본이 Binance 에 있다
- **여러 인터벌 각각 수집** — 1m + SQL 롤업으로 충분
- **이중 축 차트** — 눈금 설정만으로 "ETH 가 BTC 를 추월했다"는 착시를 만들 수 있다.
  스케일이 30배 차이라 구간 시작을 100 으로 **지수화**해 단일 축으로 그린다
- **초록/빨강 단독 인코딩** — 정상 ΔE 33.9 / 적록색약 **4.1**(최저선 6). 부호와 ▲▼ 병기
- **라이브 배포를 기본 경로로 삼지 않음** — 데이터센터 IP 차단 리스크 + 유휴 슬립
  호스팅은 상시 수집 전제와 모순. 재현 경로(`docker compose up` + `demo:chaos`)가 **주**
  <br>※ 데모 URL 은 있다. **주·부 관계를 정확히 말할 것** — URL 은 부, 재현 경로가 주.
  *"지금 돌고 있다"* 보다 *"죽여도 복구한다"* 가 이 과제의 요구에 가깝다

## 7. 대시보드 — 지표와 형태의 근거

**전제**: 제목이 "**운영** 대시보드"다. 대부분은 가격 차트만 그린다.
Part 1 이 요구한 것이 안정성과 백필이므로, 대시보드가 **파이프라인 자체의 건강**을
보여줘야 Part 1 과 Part 2 가 하나의 서사가 된다 → **운영 + 시장 2단 구성.**

- **Hero = Data Lag**(58px). *"지금 이 화면이 얼마나 최신인가"* 가 운영의 첫 질문
- **커버리지** — 기대 봉 수 대비 실제 봉 수. 100% 가 곧 "구멍 없음"의 증거
- **갭 복구** — 복구한 봉 수와 백필 횟수. 집계에서 `reason='initial'` 은 **제외**한다.
  안 그러면 최초 백필 1만 봉이 "복구량"으로 잡혀 **숫자가 거짓말을 한다**
- **Taker 매수 비율** — 발산형 막대, 축 **±15%p**. ±100%p 면 실제 값이 중앙 1px 에 뭉갠다
- **상대 강도** — 구간 시작을 100 으로 지수화. 이중 축 금지의 대안

### 색 — 눈으로 고르지 않고 계산했다

검증기를 돌려 나온 수치가 **정상 ΔE 33.9 / 적록색약 4.1**(허용 최저선 6)이다.
**눈으로는 못 보는 결함**이다. 캔들은 몸통 기하학이 2차 인코딩이라 색을 유지하되,
숫자에는 반드시 부호(+/−)와 ▲▼ 를 병기한다.

> 요점은 "색약을 배려했다"가 아니라 **"판단을 AI 에 맡긴 게 아니라 검증을 자동화했다"** 다.
> **그 프레임으로 말한다.**

### 목업을 실데이터로 만든 판단

더미 데이터였다면 *"Taker 비율이 중앙 1px 에 뭉갠다"* 와 *"갭 복구가 2,900봉으로 잡힌다"* 는
**발견되지 않았다.** 둘 다 실제 값의 분포 때문에 드러난 문제다.
육안 검수에서만 잡힌 결함이 **7건** — 검증기는 색만 본다. **축과 레이아웃은 눈으로 봐야 한다.**

## 8. AI 활용의 경계 — 평가 항목이다

한 문장: **판단은 내가, 검증은 자동화, 검수는 다시 내가.**

| 맡긴 것 | 직접 정한 것 |
|---|---|
| 보일러플레이트, Binance 스펙 대조, 문서 초안 | 스키마 설계, 장애 시나리오 도출, 무엇을 배제할지 |
| 색 대비 계산, 코드 리뷰 1차 | 색 결정과 인코딩 방식, 리뷰 지적의 채택 여부 |
| 테스트 뼈대 | **"여기가 깨지면 데이터에 구멍이 난다"는 지점 선정** |

**사례 3개만 외운다.**

1. **색 대비 검증기** — 눈으로 못 보는 결함(ΔE 4.1)을 계산으로 잡았다.
   *"AI 에 판단을 맡긴 게 아니라 검증을 자동화했다."*
2. **가드레일 훅** — 프롬프트만 던지지 않고 `.claude/hooks/` 에 안전장치를 만들었다.
   커밋 가드가 AI 트레일러를 차단한다. **AI 사용을 숨긴 게 아니라 채널을 바꾼 것** —
   트레일러는 "썼다"만 말하고 "어떻게 썼는지"를 못 말하므로 `AI-USAGE.md` 에서 밝힌다.
3. **테스트를 리뷰하자 테스트가 무너졌다** — AI 가 쓴 테스트가 초록불만 켜고 아무것도
   지키지 않고 있었다. *"AI 에게 테스트를 붙이라고 하면 **통과하는** 테스트가 나온다.
   통과하는 테스트와 회귀를 잡는 테스트는 다르다."*
