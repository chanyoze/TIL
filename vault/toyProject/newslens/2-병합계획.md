팀원이 가져온 「AI 미디어 큐레이션 플랫폼」 기획과, 내가 따로 세웠던 「실시간 채팅 + 인프라 풀코스」 계획([1. 기존 계획](./1-기존계획.md))을 하나로 합쳐야 했다. 하나는 8일짜리 2인 프로젝트였고, 하나는 11~13주짜리 혼자 하는 학습 사다리였다. 둘을 그대로 섞으면 8일 안에 끝나지 않는다. 이 글은 **무엇을 본체로 삼고, 무엇을 넣고, 무엇을 미뤘는지**와 그 이유를 정리한 것이다. 병합 계획 원문은 비공개 보관함에 있다.

## 두 기획의 성격

| | 팀원 기획 (베이스) | 내 계획 |
|---|---|---|
| 한 줄 | AI 미디어 큐레이션 **API 플랫폼** | 실시간 채팅 + **인프라 풀코스** |
| 목적 | 이직 포트폴리오 (테크 · AX 어필) | 개발자 기본기 한 바퀴 (학습) |
| 스택 | Spring Boot · PostgreSQL + pgvector · Redis · Gemini · SSE · React | Node.js + Socket.IO · Vue 3 (Spring 대안 가능) |
| 핵심 기술 | LLM · RAG · 벡터 검색 · 캐싱 · SSE · 배치 | WebSocket · 소켓 인증 · 동시성 · Redis Pub/Sub · Docker → AWS → k8s |
| 기간 · 인원 | 8일 · 백엔드 2인 | 11~13주 · 1인 |

팀원 기획은 **넓고 짧고**, 내 계획은 **깊고 길다.** 그래서 팀원 기획을 본체로 두고, 내 계획은 "본체 위에 얹을 수 있는 조각"으로 보기로 했다.

## 겹치는 기술을 하나씩 판정했다

두 기획이 같은 기술을 다른 각도로 만나는 곳이 병합 지점이었다.

| 기술 | 팀원 기획 | 내 계획 | 판정 |
|---|---|---|---|
| Redis | 피드 · 카테고리 캐싱 | 다중 서버 Pub/Sub | 8일엔 **캐싱만**. Pub/Sub 는 시즌2 |
| 실시간 | SSE (단방향 알림) | WebSocket (양방향) | **SSE 유지.** 새 기사 알림은 단방향이라 충분하다 |
| 인증 | 없음 | 소켓 JWT 인증 | **스트레치 목표.** 설계에 자리만 비워 둔다 |
| 배포 | Docker Compose → PaaS | Docker → AWS → k8s | 8일엔 Compose + PaaS. AWS · k8s 는 시즌2 |

결과적으로 8일 본체에 실제로 들어간 것은 **스택 통일(Spring Boot)과 인증 자리 예약** 정도였다. 내 Node + Socket.IO 계획은 접었고, "WebSocket · 인증 · 동시성을 직접 구현해 본다"는 학습 목표만 Spring 위로 옮겼다. 원래 계획에 "Spring 대안 가능"을 적어 두었던 덕에 충돌은 없었다.

## 인증을 스트레치로 둔 이유

인증은 넣을지 뺄지 따로 따져 봤다. 넣으면 얻는 게 많았다.

- 회원 → 토큰 발급 → 보호된 API 흐름이 있어야 "실제 서비스를 만들어 봤다"가 성립한다.
- **SSE 인증에는 함정이 있다.** 브라우저 `EventSource` 는 커스텀 헤더를 실을 수 없어서, 토큰을 쿼리 파라미터나 쿠키로 넘기고 연결 시점에 검증해야 한다. 내 계획의 "소켓 인증 함정"이 SSE 로 바뀌어 그대로 남는 셈이다.
- 사용자를 식별해야 LLM 무료 쿼터를 사용자별로 제한할 근거가 생긴다.

하지만 8일 안에서 인증은 본체인 RAG 시간을 갉아먹는다. 그래서 **구현은 미루되 자리는 비워 두는** 쪽을 골랐다. 첫 이틀에 사용자 테이블 자리와 보호 경로 구조만 설계에 넣고, 실제 검증은 여유가 있으면 마지막 이틀에, 아니면 시즌2 에서 한다. 넣었다 빼는 낭비 없이 양쪽을 열어 두는 선택이었다.

## 일을 나누는 기준 — 데이터 흐름 방향

원래 기획서의 개발자 A · B 구분은 임의였다. 일감 무게와 의존 관계로 다시 나눴다.

| | 개발자 1 — 쓰기 라인 | 개발자 2 — 읽기 라인 |
|---|---|---|
| 핵심 | 데이터를 **만들어 넣는** 쪽 | 데이터를 **꺼내 보여 주는** 쪽 |
| 담당 | 수집 배치 · 중복 제거 · LLM 처리(요약 · 태깅 · 임베딩) · 저장과 이벤트 발행 · 배포 | 조회 API · 캐싱 · 벡터 검색(RAG) · SSE 알림 · API 문서 · (스트레치) 인증 |

- **쓰기 라인과 읽기 라인은 DB 스키마만 합의되면 거의 부딪히지 않는다.** 같은 컨트롤러를 둘이 만지는 일이 없다.
- 스키마 · Docker Compose · LLM 클라이언트 래퍼 · 응답 포맷은 갈라지기 전 첫 이틀에 **둘이 같이** 만든다. 읽기 라인의 RAG 가 쓰기 라인의 LLM 래퍼에 기대므로, 래퍼를 먼저 만들어야 한다.
- 가장 무거운 단일 작업(LLM 통합)이 쓰기 라인에 있어서, 무게를 맞추려고 배포와 데모 보조를 쓰기 라인으로 보냈다.

인증 · 실시간 확장을 시즌2 에서 직접 가져가려면 나는 읽기 라인이 자연스러웠다. 최종 배정은 팀원과 협의로 남겼다.

## 팀에 낸 제안

베이스 기획을 바꾸지 않는 선에서 몇 가지를 제안 후보로 적었다.

- **Spring AI 도입.** LLM 을 직접 HTTP 로 부르고 벡터 SQL 을 직접 다루는 대신 Spring AI 로 RAG 배선을 줄인다. 무료 키로 연동되는 것까지 확인했다. 설정에 클라우드 프로젝트 정보를 넣으면 유료 모드로 바뀐다는 함정도 같이 적었다.
- **벡터 차원을 첫날 못 박는다.** 임베딩 모델을 정하면 벡터 컬럼 차원(768)이 정해진다. 나중에 바꾸면 테이블이 깨진다.
- **도메인은 AI · 테크 동향, 수집은 전문을 주는 영문 뉴스 API.** "AI 로 AI 뉴스를 큐레이션"하는 서사가 목적과 맞는다. 무료 플랜이 로컬호스트에서만 되는 뉴스 API 는 배포에서 막히므로 뺐다.
- **기사 하나에 LLM 호출 두 번.** 번역 · 요약 · 태깅을 구조화 출력 한 번으로 묶고 임베딩을 한 번 더 부른다. 영문을 한국어로 요약하면 그게 곧 번역이다.
- **무료 쿼터의 병목은 토큰이 아니라 요청 수다.** 하루 신규 100건이면 일일 한도의 7% 수준이지만, 분당 한도가 낮아 배치는 큐로 천천히 흘려야 한다.
- 데모 UI 는 RAG 검색 화면 하나에만 공들이고, 버전 관리 · RSS 파싱 · 헬스체크는 거의 공짜인 라이브러리로 채운다.

## 시즌2 로 미룬 것

버린 게 아니라 같은 코드베이스 위에 개인 확장으로 남겼다.

- 인증 본구현 — 예약해 둔 자리에 로그인 · 토큰 · 보호 필터 · SSE 토큰 검증
- SSE 를 서버 두 대로 늘렸을 때 **브로드캐스트가 깨지는 것을 직접 겪고** Redis Pub/Sub 로 푸는 것
- WebSocket 양방향 기능(필요한 기능이 생기면)
- 인프라 사다리: AWS 배포 → 로컬 k8s → 관리형 k8s

## 돌아보면

- 두 계획을 합칠 때 처음 한 일은 **둘의 성격을 한 줄로 비교하는 것**이었다. "넓고 짧다 / 깊고 길다"로 비교한 뒤 본체를 정했다.
- 넣을지 말지 애매한 기능(인증)은 **"자리만 예약"** 이라는 세 번째 선택지가 있었다. 지금 구현하지 않아도 설계에 빈칸을 두면 나중에 넣을 때 구조를 뜯지 않는다.
- 일을 나누는 기준을 사람이 아니라 **데이터가 흐르는 방향**으로 잡았다.
