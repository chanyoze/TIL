군 복무 시절 복지관에서 일하며 혼자 만든 자바 스윙 앱을 다시 꺼냈다. 코로나 시기 어르신 출입 기록을 돕는 앱으로, 자주 쓰는 방문 사유 13개를 버튼으로 만들어 두고 누르면 클립보드에 복사해 출석관리 프로그램 입력 칸에 바로 붙여 넣게 한다. 기능은 단순한데 코드는 `main()` 메서드 하나에 230줄이 몰려 있었다. CI/CD 를 붙이기 전에 먼저 **테스트하고 자동으로 빌드할 수 있는 모양**으로 바꿔야 했다. 그 리팩토링과 이후 v1.1 ~ v1.3 의 변화를 정리한다. 작업 당시의 상세 기록은 비공개 보관함에 있다.

## 원본의 상태

| # | 문제 | 영향 |
|---|---|---|
| 1 | `main()` 하나에 200줄 이상 (God Method) | 읽기 · 테스트 · 수정이 모두 어렵다 |
| 2 | 거의 같은 ActionListener 13개를 복붙 | 키워드 하나 늘리면 여러 곳을 고친다 |
| 3 | 외부 프로그램을 띄우고 `p.waitFor()` | 그 프로그램이 닫힐 때까지 **도우미 창이 안 뜬다.** 주석엔 "동시 실행"이라 적혀 있었는데 정반대로 동작했다 |
| 4 | 외부 프로그램 경로를 코드에 박음 | 설치 위치가 다른 PC 에선 고쳐서 다시 빌드해야 한다 |
| 5 | 좌표 · 크기 매직 넘버 | 레이아웃을 어디서 고칠지 찾기 어렵다 |
| 6 | Swing 화면을 메인 스레드에서 생성(EDT 위반) | 드물게 화면 깨짐 · 교착 |
| 7 | 외부 프로그램 실행 실패를 stderr 로만 출력 | 사용자는 왜 안 되는지 모른다 |
| 8 | 빈 클래스 · 컴파일도 안 되는 폐기 파일 · 죽은 주석 블록 | 노이즈 |

13개 리스너를 복붙한 이유는 주석에 남아 있었다 — "람다식 관련 문제 해결해야 함". 루프 변수를 람다가 캡처하지 못해 일괄 등록을 포기했던 흔적이다.

## 리팩토링 — 다섯 단계

| 단계 | 한 일 |
|---|---|
| 1 정리 | 빈 클래스 · 폐기 파일 · 미사용 import · 죽은 주석 삭제 |
| 2 중복 제거 | 리스너 13개 → 루프 하나 |
| 3 관심사 분리 | `Main.java` 하나 → `app` 패키지 여섯 파일 |
| 4 외부 설정화 | 키워드 목록과 외부 프로그램 경로를 `config.properties` 로 |
| 5 버그 수정 | `waitFor` 제거, EDT 적용, 실패 시 다이얼로그 |

새 구조는 이렇다.

```
src/app/
├── App.java              진입점
├── MainFrame.java        화면 구성
├── UiConstants.java      좌표 · 크기 · 색 · 문구 상수
├── ClipboardService.java 클립보드 복사
├── ProcessLauncher.java  외부 프로그램 실행 (논블로킹 + 오류 다이얼로그)
└── AppConfig.java        설정 파일 읽기
```

핵심 변경 두 개만 옮겨 둔다.

```java
// 리스너 13개 → 루프 하나. 람다 캡처 문제는 final 지역 변수로 푼다
for (int i = 0; i < names.size(); i++) {
    final boolean isCustom = (i == names.size() - 1);
    final String fixedText = isCustom ? null : names.get(i);
    btn.addActionListener(e -> ClipboardService.copy(isCustom ? customField.getText() : fixedText));
}

// 블로킹 실행 → 시작만 시키고 바로 돌아온다
new ProcessBuilder(exePath).start();
```

일부러 남긴 것도 있다. `null` 레이아웃과 `setBounds()` 는 눈으로 확인하기 전까지 바꾸지 않았고, 배경 · 버튼 색과 창 제목도 원본 그대로 뒀다. 동작을 바꾸지 않는 리팩토링과 화면을 바꾸는 개편을 섞지 않기 위해서다.

## 자바 없는 exe — jpackage

원래 exe 는 Launch4j 로 만든 런처일 뿐이라 JRE 를 들고 다니지 못했다. 자바가 없는 PC 에서는 "자바를 설치하라"는 창만 떴다. 목표는 **JRE 를 exe 와 함께 묶어 더블클릭만으로 실행**되게 하는 것이었다.

| 도구 | 판정 |
|---|---|
| **jpackage** | 채택. JDK 14 부터 기본 내장, Swing 과 잘 맞고 결과물 30~50MB |
| jlink + Launch4j | 옛 방식, 손이 많이 간다 |
| GraalVM Native Image | Swing 지원이 사실상 없어 비현실적 |

결과물 형태는 설치 마법사(`exe` · `msi`) 대신 **`app-image`(exe + 내장 JRE 폴더)** 를 골랐다. 마법사는 WiX Toolset 이 추가로 필요하고, 폴더를 zip 으로 묶어 USB 로 전하면 받는 쪽은 풀고 더블클릭만 하면 된다. 어르신이 쓰는 PC 에 무언가를 설치시키지 않는 쪽이 낫다고 봤다.

여기서 한 번 막혔다. "자바 없이 도는 exe 를 만드는데 왜 JDK 를 깔아야 하나?" — **JDK 는 만드는 도구, JRE 는 실행 환경**이다. 만드는 사람 PC 에는 JDK 21 이 있어야 jpackage 를 쓸 수 있고, 그렇게 만든 결과물에는 최소 JRE 가 들어간다.

## v1.1 — 외부 프로그램 연동을 빼고 자동 붙여넣기

실제로 써 보니 두 가지 요청이 나왔다.

1. 출석관리 프로그램이 없는 PC 에서는 실행할 때마다 "외부 프로그램 실행 실패" 창이 떴다. 이 기능을 더는 쓰지 않으니 **통째로 뺐다**(`ProcessLauncher` 삭제).
2. "버튼 클릭 → 창 전환 → Ctrl+V" 에서 한 단계를 더 줄이고 싶었다. 원래 앱을 만들 때부터 하고 싶었지만 못 했던 **좌클릭 자동 붙여넣기**다.

자동 붙여넣기는 JNativeHook(전역 마우스 · 키보드 후킹 라이브러리)으로 만들었다.

```
버튼 클릭 → 클립보드에 복사 + "다음 좌클릭은 붙여넣기" 표시
다른 창을 좌클릭 → 전역 후킹이 감지 → 우리 창 밖이면
  → 포커스가 넘어갈 때까지 잠깐 대기 → Robot 으로 Ctrl+V
```

전역 후킹은 네이티브 DLL 을 내려받아 올리는 방식이라 백신이 키로거로 오인해 막을 수 있다. 그래서 초기화를 `catch (Throwable)` 로 감싸, **어떤 실패가 나도 앱은 뜨고 자동 붙여넣기만 꺼지게** 했다. 이 부분은 CI 자동 테스트로는 확인할 수 없어 손으로 확인하는 영역으로 남겼다.

빌드도 컴파일 → jar → jpackage 를 한 번에 하는 PowerShell 스크립트로 묶었다. 이 스크립트는 뒤에 [Gradle](./gradle.md)로 대체됐다.

## v1.2 — 됐다 안 됐다 하는 붙여넣기

자동 붙여넣기가 간헐적으로 빈 값을 붙이거나 아예 안 붙었다. 원인은 둘이었다.

- **포커스 대기가 너무 짧았다(80ms).** 클릭한 창이 포커스를 다 받기 전에 Ctrl+V 가 나가 무시됐다. 200ms 로 늘렸다.
- **클립보드 비우기와 경합했다.** 붙여넣은 뒤 클립보드를 비웠는데, 붙여넣기가 끝나기 전에 비워지면 빈 값이 들어갔다. 비우는 단계를 뺐다.

같이 미리보기 영역도 붙여넣기 대상으로 허용해, 앱 안에서 바로 동작을 확인할 수 있게 했다.

## v1.3 — UI 개편

리팩토링 때 미뤘던 레이아웃을 이때 바꿨다. `null` 레이아웃을 `BorderLayout` + 버튼 `GridLayout(0, 2)` 로 바꾸자 좌표 매직 넘버가 전부 사라졌고, 버튼이 12개를 넘으면 겹치던 한계도 없어졌다. 디자인은 흰 버튼과 파란 강조색의 플랫한 모양으로 바꿨다.

## Docker 를 쓰지 않은 이유

CI/CD 를 붙이기 전에 처음엔 Docker 를 염두에 뒀지만 뺐다. **Docker 는 CI/CD 의 필수 요소가 아니라 자주 쓰이는 선택지**다.

- 산출물이 사용자가 더블클릭하는 Windows exe 다. 컨테이너로 배포할 서버가 없다.
- 빌드는 GitHub Actions, 배포는 Releases, 다운로드는 Pages 라 상시 구동하는 서버가 없다.
- 빌드 환경의 일관성은 Actions 러너와 Gradle Wrapper 가 이미 맡는다.
- jpackage 는 타깃 OS 에서 빌드해야 한다. Windows exe 는 Windows 러너에서만 나오니 Linux 컨테이너로는 만들 수 없다.

컨테이너 기반 CI/CD 는 별도의 작은 웹 서비스 프로젝트로 따로 배우기로 했다.

## 돌아보면

- 리팩토링 전 원본의 문제를 **번호 붙인 표로 먼저 세운 것**이 단계 계획의 뼈대가 됐다. 표의 각 줄이 그대로 다섯 단계 중 하나로 갔다.
- "동시 실행"이라는 주석과 반대로 동작하던 `waitFor()` 처럼, 주석은 의도를 말할 뿐 동작을 보증하지 않는다.
- 동작을 바꾸지 않는 정리와 화면을 바꾸는 개편을 나눠 했다. 레이아웃 전환을 v1.3 까지 미룬 덕에, 리팩토링 단계에서는 "전과 똑같이 동작하는가"만 확인하면 됐다.
- 실패할 수 있는 네이티브 기능은 **앱 기동과 분리**했다. 자동 붙여넣기가 꺼져도 원래 기능(복사)은 남는다.
