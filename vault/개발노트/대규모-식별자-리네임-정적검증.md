# 대규모 식별자 리네임 — 조용히 깨지는 함정과 정적 검증

> 한 화면의 컬럼·별칭 이름 수십~수백 개를 표준어로 일괄 치환하는 작업을 하며 겪은 것을 일반화한 노트.
> 정적 타입 검사가 없는 스택(동적 SQL + 선언형 UI + JS)에서 특히 위험하다. (내부 코드·도메인 무관)

## 1. 왜 어려운가 — 컴파일러가 안 잡아준다

Java 필드명을 바꾸면 컴파일이 깨져서 바로 안다. 그런데 이런 조합에서는 아무도 안 알려준다.

```
SQL 별칭  →  화면 데이터셋 컬럼 id  →  JS 참조  →  저장 시 바인드 키
```

이 사슬 중 한 곳만 어긋나면 **에러 없이 빈 값**이 된다. 화면은 정상적으로 뜨고, 그 칸만 비어 있다.
게다가 그 칸이 **옵션으로 숨겨진 컬럼**이면 수동 테스트도 통과한다. 실제로 그렇게 통과한 결함을 나중에 발견했다.

## 2. 자동 치환기가 못 넘는 함정

### 2.1 저장소의 이름 vs 표현의 이름

SQL 한 줄에 두 종류의 이름이 섞여 있다.

```sql
Select a.OLD_NAME NEW_ALIAS   -- a.OLD_NAME = 실제 테이블 컬럼(불변)
From   SOME_TABLE a           -- NEW_ALIAS  = 화면으로 나가는 이름(치환 대상)
```

단어경계 치환기는 이걸 구분 못 한다. `INSERT` 컬럼 목록처럼 **앞이 공백뿐인 단독 토큰**도 실제 컬럼이라 건드리면 안 된다.

> 규칙: 후행 별칭으로 인정하려면 **토큰 앞에 식(비공백)** 이 있어야 한다.

### 2.2 남이 정한 이름은 내 것이 아니다 ⚠️ 가장 위험

화면 코드에는 **다른 화면이 정한 이름**이 섞여 있다. 바꾸면 조용히 `undefined`가 된다.

| 형태 | 누가 정한 이름인가 |
|---|---|
| 팝업 호출 시 넘기는 파라미터 **키** | 받는 쪽이 정함 |
| 콜백이 돌려주는 응답 **키** | 보내는 쪽이 정함 |
| 조회 컴포넌트 매핑 `내컬럼=상대컬럼` | 좌·우 소유자가 다름 |

특히 나쁜 건 **받는 쪽이 기본값을 갖고 있을 때**다.

```js
// 받는 쪽
const v = getParam("EXPECTED_KEY");
if (isEmpty(v)) v = "1";     // ← 기본값. 그래서 에러도 안 나고 항상 "1"로 동작
```

키 하나가 어긋난 채 **오랫동안 아무도 모르는** 상태가 된다.

### 2.3 컬럼명과 값이 같은 철자일 때

```js
grid.set("TAG", "APPRV");   // 값 "APPRV"
// 그런데 데이터셋에도 APPRV 라는 컬럼이 있었다
```

단어경계 치환이 **값까지** 바꿔서, 서버 분기가 엉뚱한 else로 떨어졌다.
→ 검사: 백업 대비 **따옴표 안 내용이 바뀐 줄**만 뽑아, 새 이름이 어느 데이터셋에도 컬럼으로 없으면 값 자리로 보고 플래그.

### 2.4 순차 치환은 자기 결과를 다시 문다 (연쇄 치환)

매핑을 하나씩 `replace` 하면 앞 규칙의 산출물이 뒤 규칙에 다시 걸린다.

```
A → A_STS  →(A 규칙 재적용)→  A_STS_STS
```

신규명이 구명을 **접두로 포함**하는 매핑이 하나라도 있으면 발생한다.

> 해결: **단일 패스**. ① 토큰을 먼저 수집 → ② 토큰별 목표명을 1회만 계산(이미 신규명이면 skip) → ③ 콜백으로 한 번에 교체.
> ```js
> s = s.replace(/PREFIX_([A-Z0-9_]+)/g, (m, t) => dict[t] ? 'PREFIX_' + dict[t] : m);
> ```

### 2.5 파서 상태기계가 중첩에서 무너진다

"Select 절 안에서만 별칭을 붙인다"는 상태기계를 만들었는데, 스칼라 서브쿼리를 만나면 깨졌다.

```sql
Select
    COL_A alias_a,
    ( Select X From T Where … ) alias_b,   -- ← 이 안의 From 이 '절 상태'를 꺼버림
    COL_C,                                  -- ← 여기부터 전부 스킵됨
```

`inSelect = false`가 되고 **바깥 절로 복귀하지 못해**, 그 뒤 컬럼이 통째로 처리에서 빠진다.
→ 깊이별 상태 **스택**을 쓰고, 서브쿼리에서 빠져나오면 바깥 상태를 복원한다.

### 2.6 스코프 단위를 틀리면 오탐이 쏟아진다

id 중복 검사는 **유효 스코프** 기준이어야 한다.

- 그리드 헤더 id → 헤더 밴드 안에서만 유일하면 됨 (파일 전체로 세면 오탐)
- 데이터셋·서브미션 id → 파일 전역 유일

## 3. 검증 — 텍스트 검사는 "돈다"를 증명하지 못한다

태그 균형, 잔여 토큰 0, 바인드↔화면 일치… 전부 통과해도 **SQL이 실행된다는 보장은 없다**.

### 3.1 DB에 직접 물어본다

동적 태그·바인드를 제거하고 **행을 안 읽는 형태**로 감싸 실행하면, 컬럼명이 전부 검증된다.

```sql
Select * From ( <원본 쿼리 본문> ) Where Rownum <= 0
```

반환된 컬럼명을 화면 데이터셋 컬럼과 대조한다.

| 결과 | 의미 |
|---|---|
| 데이터셋에만 있음 | **값 소실** — 화면이 기대하는데 SQL이 안 줌 |
| SQL에만 있음 | 죽은 출력 — 뽑지만 아무도 안 받음 |

실제로 이 대조에서 **텍스트 검증을 전부 통과한 별칭 누락 4건**을 뒤늦게 찾았다.

### 3.2 저장 경로는 조회와 공급원이 다르다

조회는 `쿼리 → 데이터셋`이지만, 저장은 **다른 데이터셋**이 소스일 수 있다.

```
화면 표시용 데이터셋   ← 조회 쿼리
변경이력 미러 데이터셋 ← 저장 시 서버로 전송   ← 저장 바인드는 여기서 공급된다
```

둘을 **서로 다른 배치**에서 리네임했다면 반드시 대조해야 한다. 어긋나면 저장이 조용히 `null`이 된다.

### 3.3 기준선을 잘못 잡으면 앞 단계가 깬 걸 계속 통과시킨다

"직전 단계 백업"을 기준선으로 쓰면, **1단계가 깬 것을 "원래 그랬던 것"으로 오분류**한다.
기준선은 반드시 **작업 착수 이전 커밋**이어야 한다.

```bash
git show <착수이전커밋>:<파일> > /tmp/base.ext   # 같은 검사기로 대조
```

이걸 안 지켜서, 앞 단계가 깬 파라미터 키를 여러 회차 내내 "기존 결함"으로 넘겼다.

## 4. 도구도 틀린다 — 도구를 독립 출처로 검증하라

이 작업에서 자체 제작한 검사기 여러 개가 **오탐/누락**을 냈다.

| 증상 | 원인 |
|---|---|
| 정상인데 결함으로 보고 | 부모 요소를 "가장 가까운 것"이 아니라 first-match로 탐색 |
| 검사 대상의 30%만 검사 | 속성 인용부호가 `"`와 `'` 로 섞여 있는데 한쪽만 매칭 |
| 분기 중 하나만 검사 | `if/else` 각 분기의 동명 객체를 하나만 수집 |

그래서 컬럼 추출기는 **DB 실측(53/53 일치)으로 도구 자체를 먼저 검증**한 뒤 전체에 적용했다.

> 결과가 나오면 실물을 열어 확인하고, 가능하면 **독립적인 출처**(DB 카탈로그, 실행 결과)로 도구를 교차검증한다.

## 5. 정리 — 체크리스트

- [ ] 저장소 컬럼과 표현 별칭을 구분했는가 (INSERT 목록 포함)
- [ ] 외부 계약 키(호출 파라미터·콜백 응답·컴포넌트 매핑)를 보호했는가
- [ ] 값으로 쓰인 문자열이 컬럼명과 같은 철자는 아닌가
- [ ] 치환이 단일 패스인가 (연쇄 치환 없음)
- [ ] 파서 상태기계가 중첩에서 복원되는가
- [ ] **DB에 직접 물어 산출 컬럼 ↔ 화면 컬럼을 대조했는가**
- [ ] 저장 경로의 공급원 데이터셋을 따로 대조했는가
- [ ] 기준선이 "작업 착수 이전"인가
- [ ] 검사 도구 자체를 독립 출처로 검증했는가
