# 식별자 리네임 — 어디까지가 한 덩어리이고, 어디서 멈출 것인가

> 이름 하나를 바꾸는 일이 왜 "한 줄 수정"으로 안 끝나는지에 대한 노트.
> [대규모 식별자 리네임과 정적 검증](./대규모-식별자-리네임-정적검증.md)이 **치환 자체의 함정**을 다룬다면,
> 이 글은 **무엇이 같이 움직여야 하고 / 어디서 멈춰야 하는가**를 다룬다. (내부 코드·도메인 무관)

## 1. 이름은 점이 아니라 사슬이다

선언형 UI + 서버 매핑 구조에서 데이터셋 이름 하나는 보통 이런 사슬을 이룬다.

```
화면 데이터셋 선언
   → 서브미션(target)
      → 액션 URL
         → 서버 라우팅(@RequestMapping)
            → 서버 응답 키          ← ★ 여기가 가장 잘 빠진다
               → 서비스 → 매퍼 → SQL statement id
```

이 중 **응답 키**가 특히 위험하다. 서버가 결과를 담을 때 쓰는 문자열인데, 화면 데이터셋 이름과 **문자열로만** 이어져 있다.

```java
result.setData("myDataset", service.selectSomething(param));
//              ^^^^^^^^^  화면의 데이터셋 id 와 일치해야 한다
```

여기만 옛 이름으로 남으면 이렇게 된다.

- 요청은 200으로 성공한다
- 서버 로그도 깨끗하다
- **화면의 그 목록만 텅 빈다**

에러가 없으니 "왜 안 나오지"로 한참 헤맨다. 그래서 리네임 후 첫 확인은 **목록·콤보에 값이 실제로 채워지는지**여야 한다. 저장이나 상세 동작은 그 다음이다.

> 실제로 이 사슬을 한 세트로 옮기지 않으면, 조회가 "성공한 채로" 비어 있는 상태가 만들어진다.

### 검증은 사슬 전 구간을 한 번에

리네임 후엔 각 고리를 개별로 확인하는 스크립트를 두면 좋다. 통과 항목이 곧 사슬 그림이 된다.

```
[ ] 데이터셋 선언        [ ] 서브미션 target      [ ] 액션 URL
[ ] 서버 라우팅          [ ] 응답 키              [ ] 서비스 / 매퍼 / SQL id
```

## 2. 범위 — "우리 것"과 "공용 어휘"를 가른다

같은 이름이 저장소 전체에 퍼져 있을 때, 전부 바꿀지 우리 것만 바꿀지가 진짜 결정이다. 판단 기준은 **개수가 아니라 호출 관계**다.

| 상황 | 판정 |
|---|---|
| 화면마다 **자기 사본**을 갖고 있다 (각자 매퍼·서비스) | 우리 것만 바꿔도 안전 |
| 다른 화면이 **우리 서비스를 직접 호출**한다 | 건드리면 그 화면이 깨진다 → 제외 |

두 번째는 실제로 흔하다. 어떤 조회는 여러 화면이 공유하는데, 겉보기엔 우리 파일 안에만 있는 것처럼 보인다. 그래서 리네임 전에 **역참조를 한 번 확인**한다.

```bash
# 이 메서드를 우리 말고 누가 부르나
grep -rl "someService\.selectSomething" src/main/java | grep -v "우리화면"
```

### 국소 변경이 오히려 불일치를 만들 때

전사 100곳 중 우리 것 10곳만 바꾸면, 저장소 전체로 보면 **두 이름이 공존**한다. 이게 나은지 나쁜지는 변경의 성격에 달렸다.

- **의미가 또렷해지는 개명** (모호한 이름 → 주체가 드러나는 이름) → 국소라도 이득이 있다
- **철자만 짧아지는 개명** → 국소 변경의 이득이 작다. 전사 정리 시점까지 미루는 편이 낫다

## 3. 라벨·주석을 고칠 땐 규약이 다수결보다 먼저

표시용 라벨이 제각각일 때, 가장 많은 표기에 맞추고 싶어진다. 이건 함정이다. **다수가 규약을 어기고 있을 수 있다.**

실제로 겪은 순서 착오:

1. 어떤 필드의 라벨이 두 가지로 섞여 있었다
2. 손대기 전 이미 9곳이 A 표기 → A로 통일했다
3. 나중에 알고 보니 **A가 접미사 규약 위반**이었다 (`_NO`는 "번호", `_SN`은 "순번" 인데 `_NO`에 "순번"을 붙임)
4. 게다가 그 값은 시퀀스가 아니라 `Max(...) + 1` 계산값이라 "순번"이라는 말 자체가 과했다

교훈은 순서다.

> **① 접미사·타입 규약 → ② 실제 생성 방식 → ③ 다수결**

다수결은 마지막이다. 앞의 둘이 답을 주면 다수가 틀린 것이다.

## 4. 구조를 지울 땐 줄이 아니라 블록으로

선언이 여러 줄에 걸친 마크업을 **줄 단위 필터**로 지우면 닫는 태그가 고아로 남는다.

```xml
<!-- 한 줄짜리 -->
<item id="A" label="..."></item>

<!-- 여러 줄짜리 — 여는 줄만 지우면 </item> 가 남는다 -->
<item id="B"
      label="..."
      extra="...">
</item>
```

증상은 태그 수 불균형으로 나타난다. 여는 태그 −23, **닫는 태그 −17** 처럼 숫자가 안 맞으면 다중 줄 선언을 놓친 것이다.

```js
// 여는 태그부터 짝 닫는 태그까지 한 덩어리로
new RegExp('[ \\t]*<item\\s+id="' + name + '"[\\s\\S]*?</item>\\r?\\n', 'g')
```

지운 뒤엔 **여는/닫는 태그 개수 일치**를 반드시 확인한다. 편집 전후를 비교하면 내가 깬 것인지 원래 그랬는지도 갈린다.

## 5. 오탐을 문서에 굳히지 마라

가장 비싼 실수는 코드가 아니라 문서에서 났다.

검사 도구가 낸 오탐 두 건을 "알려진 기존 결함"으로 문서에 적어뒀다. 몇 주 뒤 그 항목을 고치려고 다시 조사했고, **둘 다 결함이 아니었다.**

- 하나는 도구가 부모 요소를 "가장 가까운 것"이 아니라 first-match로 찾아서 생긴 오탐
- 하나는 기준선을 잘못 잡아 앞 단계가 깬 것을 "원래 그랬던 것"으로 오분류한 것

문서에 적히는 순간 오탐은 사실처럼 굳는다. 그래서:

> 결함으로 **기록하기 전에** 실물을 열어 확인한다. 도구 출력을 그대로 옮기지 않는다.
> 정정할 땐 지우지 말고 **"왜 잘못 적혔는지"** 를 남긴다 — 안 그러면 같은 조사를 또 한다.

## 6. 빈 값이 항상 결함은 아니다 — 대체된 설계의 흔적일 수 있다

어떤 코드 컬럼이 상당수 행에서 비어 있었다. 결함처럼 보였지만 아니었다.

- **구세대**: 코드 값으로 "어디서 왔는지"를 표시하고, 그 코드로 중복을 걸렀다
- **신세대**: 별도 연결 테이블에 **원본 키를 통째로** 보관하고, 그 키로 중복을 건다

신세대 경로로 들어온 행은 옛 코드 컬럼을 채우지 않는다. **정상이다.** 오히려 연결 테이블 쪽이 정밀하다 — 같은 유형 안에서 어느 원본인지까지 구분한다.

판정 기준은 "비어 있는가"가 아니라 **"그 값을 읽는 곳이 있는가"** 다.

```
읽는 곳이 있다  +  비어 있다   → 결함
읽는 곳이 없다  +  비어 있다   → 대체된 설계의 잔재 (정상)
```

읽는 지점을 전수로 뽑아 각각 "null이면 어떻게 되는가"를 확인하면 답이 나온다. 이번 경우 읽는 곳이 모두 신세대 경로를 애초에 대상에서 제외하고 있어서, 비어 있어도 아무 영향이 없었다.

## 7. 정리 — 체크리스트

**바꾸기 전**
- [ ] 이 이름이 이루는 사슬을 끝까지 그렸는가 (특히 **서버 응답 키**)
- [ ] 다른 곳에서 우리 서비스를 직접 호출하는가 (역참조 확인)
- [ ] 국소 변경이 오히려 불일치를 만들지는 않는가

**바꾸는 중**
- [ ] 라벨은 **규약 → 생성 방식 → 다수결** 순으로 판정했는가
- [ ] 구조 삭제는 블록 단위인가 (다중 줄 선언 포함)

**바꾼 뒤**
- [ ] 사슬 전 구간을 항목별로 확인했는가
- [ ] 목록·콤보에 값이 **실제로 채워지는지** 눈으로 봤는가
- [ ] 태그·괄호 균형이 편집 전과 같은가
- [ ] 서버 코드가 바뀌었으면 **재기동 후** 확인했는가

**기록할 때**
- [ ] 결함으로 적기 전에 실물을 확인했는가
- [ ] 정정할 때 "왜 잘못 적혔는지"를 남겼는가
