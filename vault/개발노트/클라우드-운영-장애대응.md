# 클라우드 SaaS 운영 — 장애 유형별 1차 대응

AWS 위에 올린 SaaS 서비스를 운영하다 보면 장애 원인은 몇 가지 패턴으로 수렴한다. 대부분 **디스크가 찼거나, CPU/메모리가 한계에 닿았거나, 접근 제어에 막힌** 경우다. 아래는 각 유형을 어떤 화면에서 어떻게 확인하고, 어디까지 손대도 되는지를 일반화해 정리한 운영 메모다.

> 서버 접속은 SSH 키를 뿌리는 대신 **SSM Session Manager**(AWS Systems Manager의 원격 셸 기능)를 쓴다. EC2 인스턴스 → *연결* → *Session Manager*로 브라우저에서 CLI가 열리고, 접속 후 `sudo su`로 권한을 올린다.

## 1. 로그 수집기(ELK)에 최신 로그가 안 보인다

원인은 거의 항상 **디스크 공간 부족**이다. 로그 인덱스가 계속 쌓이는데 정리가 안 되면 신규 색인이 실패하고, 화면에서는 "최신 로그가 안 나온다"로 보인다.

**확인**

```bash
sudo su
df -h      # Use% 확인 — 80% 넘으면 관리 대상
```

**조치** — Kibana에서 햄버거 메뉴 → *Stack Management* → *Data* → *Index Management*로 들어가 인덱스별 용량을 본다. 용량이 큰 인덱스를 선택하고 *Manage index* → *Delete index*.

- 평소에는 **ILM**(Index Lifecycle Management, 인덱스 수명주기 정책)으로 자동 정리되지만, 정책이 멈추거나 적용이 안 된 인덱스가 생기면 수동 개입이 필요하다.
- **로그는 최소 1주일 보관**이 원칙. 지워야 한다면 **가장 오래된 날짜부터** 지운다.

## 2. 리포트 출력 오류

리포트 엔진이 죽는 건 대부분 **순간 요청 폭주로 인한 CPU 과부하**다.

**확인**

```bash
htop       # 상단 CPU / MEM 바 — 100%에 붙어 있으면 과부하
df -h      # 저장 공간도 함께 확인
```

**조치**

```bash
systemctl restart <report-tomcat>.service
```

관리 콘솔에 톰캣 재시작 기능이 있다면 그쪽이 더 빠르다.

디스크가 원인이면 톰캣 로그 디렉터리(`/opt/<tomcat>/logs`)에서 오래된 로그를 지운다.

:::danger catalina.out은 지우지 말 것
`catalina.out`은 **현재 구동 중인 프로세스가 붙잡고 쓰는 로그 파일**이다. 삭제하면 파일 핸들만 남아 공간도 회수되지 않고 로그도 유실된다. 용량이 문제라면 삭제가 아니라 **비우기**(`: > catalina.out`)나 logrotate로 처리한다.
:::

외부에서 도입한 리포트 솔루션은 설치 경로가 표준과 다를 수 있으니, 직접 구축한 서버와 같은 경로를 가정하지 말고 실제 경로를 확인한다.

## 3. DB 로그인 실패 / DB 알람

RDS(Oracle)라면 **Performance Insights**(성능 개선 도우미)로 부하 원인을 좁힌다.

RDS 콘솔 → 대상 인스턴스 → *성능 개선 도우미*

- 우상단 시간대를 **Local timezone**으로 바꿔야 한국 시간 기준으로 보인다.
- 구간을 **최근 5분**으로 좁혀 그 시점에 돌던 쿼리를 본다.
- *상위 사용자(Top users)* 를 보면 어느 계정/애플리케이션이 부하를 만드는지 드러난다.
- *상위 SQL(Top SQL)* 에서 다음 두 지표를 함께 읽는다.

| 지표 | 의미 | 판단 |
|---|---|---|
| `Executions/sec` | 초당 실행 횟수 | 값 자체보다 아래 지표와의 곱이 중요 |
| `Elapsed time (ms)/exec` | 1회 실행당 소요 시간 | `0.0x`대면 정상, **2~3 이상이면 튜닝 대상** |

호출 빈도가 높으면서 1회 소요 시간까지 긴 쿼리가 실질적인 범인이다.

## 4. CloudWatch 알람

CloudWatch는 AWS가 제공하는 지표·알람 서비스로, 인프라 지표 감시 역할을 한다(ELK가 애플리케이션 로그를 본다면 이쪽은 리소스 지표를 본다).

CloudWatch → *EC2* → 해당 지표 상세

- 조회 구간을 **최대한 넓게** 잡아 평소 패턴 대비 얼마나 튀었는지 본다. 순간 스파이크 한 번인지, 추세적으로 올라가는지에 따라 대응이 달라진다.
- 운영 대상 인스턴스만 보면 되므로, 명명 규칙으로 걸러 관리 대상만 확인한다.

## 5. 외부 IP 접근 허용

서비스 앞단에는 **ALB**(Application Load Balancer, 들어온 요청을 뒤쪽 서버로 분배하는 교통정리 역할)가 있고, 접근 제어는 여기 **리스너 규칙**에서 한다.

EC2 → *로드밸런서* → 대상 LB → *리스너* → HTTPS:443 → 규칙 보기

- 개발 서버는 사내망 IP·VPN IP 등 허용된 출발지에서만 접근되도록 규칙이 걸려 있다.
- ⚠️ **규칙 하나에 등록할 수 있는 소스 IP 조건에는 상한이 있다**(운영 중인 구성 기준 4개). 외부 업체 접속 요청처럼 추가가 필요하면 기존 규칙에 욱여넣지 말고 **리스너 규칙을 새로 추가**해 등록한다.

## 6. 배포는 성공했는데 반영이 안 된다

배포 파이프라인이 성공으로 끝났는데 화면이 그대로면, 컨테이너가 이전 이미지를 물고 있는 경우가 많다. 관리 콘솔에서 **재시작**하는 게 가장 빠르다 — 컨테이너를 내리고 새로 띄우므로 새 이미지가 확실히 반영된다.

## 요약 — 어디부터 보나

| 증상 | 첫 확인 | 대표 원인 |
|---|---|---|
| 최신 로그 안 보임 | `df -h` | 디스크 포화, 인덱스 정리 미동작 |
| 리포트 출력 실패 | `htop`, `df -h` | CPU 과부하, 로그 디스크 포화 |
| DB 로그인 실패·알람 | Performance Insights | 특정 쿼리 부하 |
| 지표 알람 | CloudWatch 지표 추이 | 리소스 임계 초과 |
| 특정 대역에서 접속 불가 | ALB 리스너 규칙 | 소스 IP 미등록 |
| 배포 후 미반영 | 컨테이너 상태 | 이전 컨테이너 잔존 |
