# AI 시대에 어떤 개발자가 되고 싶은지

> 작성 팁: AI를 도구로 활용하면서도 대체되지 않는 역량(설계/판단/문제정의)을 어떻게 키울지

## 답변 (2026-08-19)

> 키워드: **AI의 비결정성을 결정론적 시스템으로 통제** — 경계 설계가 곧 명확한 프로토콜 정립
> 출처: 자기소개서 202607 §2(강점 둘째) + Binance 운영 대시보드 실물 증거

저는 AI 시대의 흐름에 맞춰 **AI를 개인적으로 잘 다루는 것을 넘어, AI를 시스템에 안전하게 녹여내어 팀의 협업에 기여하는 개발자**가 되고 싶습니다.

지금은 AI에 단순히 자문을 구하는 데 그치지 않고 **AI 그 자체를 서비스로 활용할 수 있는 시대**라고 봅니다. LLM 의 가능성은 넓지만 본질적으로는 도구입니다. 그래서 쓰는 사람의 역량에 따라 결과가 크게 갈리고, **같은 입력에도 다른 답을 내거나 그럴듯한 거짓을 만들어** 오히려 신뢰도를 떨어뜨릴 수 있습니다.

바로 이 지점이 제가 기여할 수 있는 부분이라고 생각합니다. **AI의 비결정성을 결정론적인 시스템 안에서 통제하는 것**입니다. 어디까지를 AI에 맡기고 어디부터는 검증된 로직과 데이터가 책임질지 **경계를 먼저 정하는 일**이고, 이는 제가 평소 중요하게 여기는 **명확한 프로토콜 정립**이라는 원칙과도 맞닿아 있습니다.

**저는 이 생각을 말로만 갖고 있지 않았습니다.**

사내 AI R&D 에 참여해 **안전보건 도메인에 LLM 을 적용하기 위한 개발 워크플로우를 검증하고 있습니다.** Claude 기반의 **커스텀 Skill 과 MCP 서버를 직접 제작**하고, 자사 홈페이지를 Spring Boot/Thymeleaf 에서 **Vue 3 SPA 로 전환하는 실제 작업에 적용해 검증**하는 중입니다. 매번 프롬프트를 새로 짜는 대신, **반복되는 화면 이식 작업 자체를 규격화해 도구로 만든 것**입니다. 현재 **사내 정식 도입을 목표로 반복 가능한 파이프라인으로 다듬고 있습니다.**

같은 문제의식이 **테스트 체계**로도 이어졌습니다. 검증이 개발자 육안 확인에 머물러 있던 환경에서, R&D 프로젝트에 **JaCoCo** 로 커버리지를 측정하고 **PIT 뮤테이션 테스팅**으로 *그 테스트가 실제 버그를 잡아내는지까지* 확인하는 구성을 직접 도입했습니다. 화면은 **Playwright** 로 E2E 검증합니다. **AI 가 코드를 빨리 만들어 줄수록, 그것이 맞는지 판정할 장치가 먼저 있어야 한다**고 봤기 때문입니다.

개인 프로젝트에서도 같은 방식을 이어갔습니다 — **판단을 AI 에 맡기는 대신 검증을 자동화하는** 쪽입니다.

- **색 대비 검증기** — 눈으로는 판별되지 않는 결함(적록색약 ΔE 4.1, 허용 최저선 6)을 계산으로 잡았습니다. AI 에 "이 색 괜찮나요"를 묻는 대신 **판정 기준을 코드로 고정**한 것입니다.
- **변이 검증** — AI 가 작성한 테스트가 초록불만 켜고 아무것도 지키지 않는 경우를 두 번 겪었습니다. 그래서 **코드를 일부러 망가뜨려 테스트가 실패하는지 확인하는 절차**를 만들었고, CI 가 그것까지 돌립니다.
- **가드레일 훅** — 프롬프트만 던지지 않고 저장소에 안전장치를 뒀습니다. 커밋 가드가 규약을 벗어난 커밋을 차단합니다.

공통점은 **판단은 사람이 하고, 반복 가능한 검증만 기계에 넘겼다**는 것입니다. 설계는 제가 정하고 세부 구현에 AI 를 활용하되, 산출된 코드가 **의도한 설계와 맞는지, 예외와 보안에 틈은 없는지는 끝까지 제가 검증합니다.**

> **도구가 무엇으로 바뀌든 결과에 책임지는 것은 사람입니다.**

적은 인원이 넓은 범위를 감당해야 하는 환경일수록 AI 는 선택이 아니라 전제에 가깝다고 봅니다. **무엇을 맡기고 무엇은 맡기지 않을지의 선을 이미 한 번 그어 본 경험**이 그대로 쓰일 수 있습니다.

정리하면, 제가 지향하는 개발자는 **AI 라는 강력하지만 불확실한 도구를 시스템 안에서 신뢰할 수 있게 제어하는 개발자**입니다.

## 꼬리질문 대비

**"AI 를 어디까지 쓰시나요?"**
→ **판단은 제가, 검증은 자동화, 검수는 다시 제가.** 보일러플레이트·스펙 대조·문서 초안·테스트 뼈대는 맡깁니다. 스키마 설계, 장애 시나리오 도출, 무엇을 배제할지, 그리고 **"여기가 깨지면 데이터에 구멍이 난다"는 지점을 고르는 일**은 직접 합니다.

**"실제로 도입은 하셨나요?"** ← 과장하지 말 것
→ **아직 사내 정식 도입 전입니다.** 커스텀 Skill 과 MCP 서버를 만들어 자사 홈페이지 전환 작업에 적용해 검증하는 단계이고, 반복 가능한 파이프라인으로 다듬는 것이 다음 단계입니다. **부풀리면 바로 드러나는 영역**이라 있는 그대로 말합니다.

**"AI 가 짜준 코드라 버그가 난 것 아닌가요?"**
→ 사람이 짜도 나오는 종류입니다. 중요한 건 **그걸 잡는 장치를 미리 만들어 뒀는가**입니다. 그래서 통과하는 테스트를 다시 검증하는 절차를 만들었습니다.

**"AI 사용을 숨기지 않으시나요?"**
→ 숨기지 않되 **채널을 바꿨습니다.** 커밋 트레일러는 "썼다"만 말하고 "어떻게 썼는지"는 못 말합니다. 그래서 트레일러는 차단하고 **별도 문서에서 경계와 사례를 밝히는** 방식을 택했습니다.

**"할루시네이션은 구체적으로 어떻게 막나요?"**
→ 막는다기보다 **틀려도 시스템이 안 무너지게** 만듭니다. AI 출력이 곧바로 결과가 되는 경로를 없애고 그 사이에 **검증 가능한 관문**을 둡니다. 색 대비 검증기나 변이 검증이 그 관문입니다.

**"AI 때문에 개발자가 대체된다고 보시나요?"**
→ **무엇을 검증할지 정하는 일**은 남는다고 봅니다. 도구는 답을 만들 수 있지만, **그 답이 맞았는지 판정할 기준**은 도메인을 아는 사람이 세워야 합니다. 제가 만든 세 가지 장치가 전부 그 기준을 코드로 고정한 것들입니다.

## 📌 해소됨 — LLM 적용 경험은 이렇게 말한다

**이력서(원티드 검수 확정본 §5-6)의 문구와 톤을 맞췄습니다.** 이력서에 있는 표현은 이것입니다.

> "**안전보건 도메인에 LLM 을 적용하기 위한** 개발 워크플로우를 검증 중"

핵심은 **"적용했다"가 아니라 "적용하기 위한"** 이라는 점입니다. 사실관계는 이렇습니다.

- 지금 만든 것은 **서비스가 아니라 개발 워크플로우**다 (커스텀 Skill · MCP 서버)
- 검증 무대는 **자사 홈페이지 Spring Boot/Thymeleaf → Vue 3 SPA 전환** 작업이다
- 이력서·자소서 둘 다 **"사내 정식 도입 전"** 이라고 명시하고 있다

→ **"도메인에 LLM 을 적용한 경험이 있다"고 단정하면 이력서와 어긋난다.**
"적용하기 위한 워크플로우를 검증 중"이 정확하고, 오히려 이쪽이 더 강합니다.
"프롬프트를 잘 쓴다"가 아니라 **"반복을 도구로 만들었다"** 는 이야기이기 때문입니다.
**Claude Skill·MCP 를 직접 만들어 실제 마이그레이션에 쓴 사람은 흔하지 않습니다.**

> ⚠️ **DDD 를 여기에 엮지 말 것.** 이력서 초안에 *"구형 환경의 도메인 로직을 DDD 기반으로
> 분리·모듈화"* 라는 문구가 있었는데, **사실과 달라 교체된 문장**입니다(원티드 검수 §1-(2)).
> AI R&D 에서 실제로 한 일은 Skill·MCP 제작이지 DDD 도메인 분리가 아닙니다.
> DDD 는 **"애그리거트 경계를 어떻게 나눴나"** 를 물으면 그 자리에서 무너지는 단어입니다.
