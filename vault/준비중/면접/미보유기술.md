# 미보유 기술 — 솔직하게, 다리를 놓아서

> 출처: `cv/이력서/면접_예상질문.md` §1 (2026-07 작성, 회사 무관하게 재사용 가능)
> 원칙: **이력서에 쓰지 않는다. 물으면 그때 정확히 답한다.**
> **"아는 것"과 "겪어본 것"을 구분해서 말한다.** 부풀리면 코드 리뷰·기술 면접에서 바로 드러난다.

## 답변 틀

| 항목 | 답 방향 |
|---|---|
| **MongoDB** | 실무 경험 없음. 단 RDB 단일 구조의 한계를 판단해 **InfluxDB 를 직접 선정·도입하고 2단계 파이프라인을 설계**함 → **저장소 특성에 맞춰 데이터 모델을 다시 잡는 일 자체는 해봤다** |
| **Kotlin** | 없음. Java 기반 Spring Boot 3년 반. 학습 부담이 크지 않다고 보는 근거를 한 문장으로 |
| **DDD** | **운영 경험 없음.** 개념 학습·적용 구상 단계. ⚠️ **AI R&D 와 엮지 말 것** — AI R&D 에서 실제로 한 일은 Claude Skill·MCP 제작이지 DDD 도메인 분리가 아니다 (원티드 검수 §1-(2)) |
| **MSA / 분산 메시징** | 없음. **MQTT 기반 비동기 수신 파이프라인**이 가장 가까운 경험 |
| **이벤트 소싱 / CQRS** | 없음. 다만 데이터 리니지 설계가 *"상태가 아니라 이동 이력을 별도 스키마에 남긴다"* 는 점에서 발상이 닿아 있음 — **억지로 우기지 말고 "닮은 점이 있다고 나중에 알았다" 수준으로만** |
| **Kubernetes** | 없음 (AWS EC2·RDS·S3 운영). **이직 사유와 연결되는 지점**이라 오히려 솔직하게 → [4. 이직 사유](이직사유) |
| **TDD** | 결핍을 느껴 **도구를 도입해 본 단계.** 처음부터 하지 않았고 히스토리에 남아 있음 → [Binance 대시보드 · 검증 방식](/TIL/docs/toy/binance-ops) |

> ⚠️ **`MongoDB · Kotlin · DDD · MSA · CQRS` 는 이력서·자소서에 쓰지 않기로 확정**돼 있다.
> 미보유 기술이라 뺀 것이다. **물으면 위 표대로 답하고, 먼저 꺼내지 않는다.**

## ⭐ 반대로 — 반드시 먼저 꺼낼 것: 테스트 체계

원티드 검수 §4 에 **"차별화 포인트를 통째로 버리고 있다"** 고 지적된 항목이다.
**커버리지를 재는 사람은 많아도 뮤테이션 테스팅까지 하는 사람은 드물다.**

> 검증이 개발자 육안 확인에 머물러 있던 환경에서, R&D 프로젝트에 **JaCoCo** 로 커버리지를
> 측정하고 **PIT 뮤테이션 테스팅**으로 *그 테스트가 실제 버그를 잡아내는지까지* 확인하는
> 구성을 직접 도입했습니다. 화면은 **Playwright** 로 E2E 검증합니다.

**이게 "TDD 경험 없음"의 진짜 답이다.** 방법론을 안 써봤다고만 하면 결핍으로 끝나지만,
*"결핍을 느껴서 무엇을 도입했는가"* 로 답하면 그 자체가 역량이 된다.
개인 프로젝트의 변이 검증(Binance)과 **같은 문제의식이 회사에서 먼저 나왔다**는 순서로 말한다.

---

## 말하는 법

1. **없다고 먼저 말한다.** 에두르면 그 자체가 감점이다.
2. **가장 가까운 경험을 다리로 놓는다.** "해봤다"가 아니라 "이건 해봤고, 그래서 이 부분은 빠르게 붙을 것 같다".
3. **억지로 잇지 않는다.** 닮은 정도가 약하면 "닮은 점이 있다고 나중에 알았다" 선에서 멈춘다.

> **정직한 자기평가 자체가 하나의 답**이 된다.
> *"문제 해결에 필요하다면 자신의 지식과 경험을 내려놓을 수 있는 사람"* 을 찾는 회사가 많다.

## 실패담 — 하나는 반드시 준비한다

*"빠르게 실행하고, 틀리면 회고하며, 더 나은 선택을 반복할 수 있는 분"* 류의 인재상이 있는 경우
**실패담이 없으면 그 항목에서 감점**된다. 준비된 카드 세 개:

| 실패 | 무엇을 배웠나 | 어디에 |
|---|---|---|
| **모바일 API 규격을 소비자와 안 맞춰 전면 재정비** | 구조를 본다면서 **누가 그 구조를 쓰는지는 안 봤다** | [3. 협업](협업_중요사항) (1) |
| **테스트를 몰아서 붙였고, 그 테스트가 아무것도 안 지키고 있었다** | **통과하는 테스트와 회귀를 잡는 테스트는 다르다** | [Binance · 검증 방식](/TIL/docs/toy/binance-ops) |
| **환경 검증이 마지막이었고 발견이 운이었다** | **검증 계층마다 사각이 있고, 마지막 사각은 환경이다** | 〃 |

## 숫자에는 측정 방법을 준비한다

*"왜 그렇게 했나"를 3단계까지 파고드는* 면접(바레이저 등)에서는
**모든 숫자에 측정 방법**이 필요하다. **근거를 못 대면 숫자가 독이 된다.**

| 숫자 | 근거 |
|---|---|
| **140만 건 · 유실 0건** | InfluxDB `wk-hlth` 버킷 전체 count = **1,372,410건** (스크린샷 보유) |
| **34개 테이블** | 추적 17 + 삭제 복구용 백업 17 |
| **약 120개 API** | 현장관리 도메인 9개 메뉴 |
| **월 10만 회** (2026.04 기준) | 해당 핵심 메뉴 사용량 — **기준 시점을 붙여 말한다** |
| **5천 줄** | 리팩토링 대상 JS 스크립트 |
| **4,000기업 · 30,000현장** | 플랫폼 규모 (대외 공개 가능) |
| **2025.02 파트 리더** | 입사 2년차 승격 · 3명 스쿼드 |

> ⚠️ **리팩토링 라인 감소 수치는 쓰지 않는다.** 2026-05-31 판단 — *오해 소지가 있어* 포폴에서도 의도적으로 뺐다.
> 대신 **월 10만 회 사용 · 이전 시도 실패 · 저장 강요 제거**로 말한다.

### 🚨 140만 건 — 계산이 안 맞는 지점이 하나 있다 (원티드 검수 §6, 미해결)

`주당 4~5만 건` 과 `누적 약 140만 건` 을 **나란히 말하면 안 된다.**

```
140만 ÷ 4.5만/주 ≈ 31주 ≈ 7개월
그런데 파이프라인 구축은 2025.05~08 → 최소 12개월 경과
주당 4~5만이 꾸준했다면 누적은 250만~300만이어야 한다
```

셋 중 하나다 — ① 140만이 옛 값이다(2026-07 시점 그대로) ② 주당 4~5만이 디바이스 증설 후 값이다
③ 주당 값이 특정 현장 기준이다. **아직 확인 못 했다.**

- **면접에서는 누적값 하나만 말한다.** 주당 수치는 먼저 꺼내지 않는다
- **"주당 얼마나 들어오나요"를 물으면** → *"현재 확인된 누적은 약 140만 건이고, 주당 유입은
  디바이스 증설 이력이 있어 구간마다 달라 정확한 값은 확인해서 알려드리겠습니다"* 로 답한다
- **숫자 두 개를 나란히 두고 계산이 안 맞는 것이 가장 나쁘다**
