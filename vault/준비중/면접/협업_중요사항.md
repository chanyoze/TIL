# 협업 시 중요시 여기는 사항

> 작성 팁: 가치관 한 줄 → 그렇게 생각하는 이유 → 실제로 그렇게 행동한 사례

## 답변 (2026-08-19)

> 키워드: **모호함 제거 · 명확한 규약** — 시스템 간 연동 사례 + 사람 간 소통 사례 2단 구성

제가 협업에서 가장 중요하게 생각하는 것은 **모호함을 제거하고 명확한 규약을 정립하는 것**입니다. 모호한 소통이 결국 시스템 에러나 잘못된 결과물로 이어지기 때문에, 양측이 오해할 수 없는 기준을 먼저 맞추는 것을 우선합니다.

**먼저 시스템 간 연동 측면입니다.** 외부 스마트 장비 업체와 IoT 데이터 파이프라인을 구축할 때, **수신 데이터의 날짜 포맷이 사전 정의서와 달라** 파싱 에러가 발생한 적이 있습니다. 정의서에는 `yyyy-MM-dd HH:mm:ss` 였는데 실제로 오는 값은 `yyyyMMddHHmmss` 였고, 그 레코드들이 조용히 적재에서 빠지고 있었습니다.

저는 문서 재확인을 요청하는 데 그치지 않고, **ELK 로그에서 실패 패턴을 추출해 어긋나는 구간을 특정**한 뒤 그 실제 데이터를 근거로 업체 개발 담당자와 직접 소통하며 송수신 포맷을 재확립했습니다. 동시에 **파싱 로직을 양쪽 포맷 모두 받도록** 고쳐, 상대 배포를 기다리는 동안에도 데이터가 빠지지 않게 했습니다. 명확한 근거를 두고 양측이 같은 것을 보게 하니 조치가 빠르게 진행됐고, 현재까지 **누적 약 140만 건을 유실 0건으로** 처리하고 있습니다.

**사람 간 소통에서도 같은 원칙을 적용합니다.** 비개발자인 고객사로부터 요구사항을 받을 때는 말로만 합의하지 않습니다. 한화오션 같은 대형 고객사의 요구사항을 받을 때는 **제가 직접 요구사항을 정리하고 목업 화면을 만들어 시연하면서** 의도와 일치하는지 여러 번 확인한 뒤에야 개발에 착수했습니다. 이렇게 하면 개발이 끝난 뒤 방향이 어긋나는 **재작업을 사전에 막을 수 있습니다.**

정리하면, **정의서·기준서·목업처럼 양측이 같은 것을 보게 만드는 장치**로 불확실성을 줄이는 것을 항상 우선합니다.

## 꼬리질문 대비

**"상대(업체)가 안 고쳐주면요?"**
→ 실제로 그 상황을 전제로 움직였습니다. **먼저 우리 쪽 파싱을 양쪽 포맷 호환으로 바꿔** 데이터가 빠지지 않게 막아두고, 그 다음에 규격을 맞췄습니다. 상대의 일정에 우리 데이터가 인질로 잡히지 않게 하는 게 먼저라고 봤습니다.

**"정의서가 있는데 왜 어긋났나요?"**
→ 문서와 실제 송신이 다른 건 흔한 일이라고 생각합니다. 그래서 **문서를 근거로 다투기보다 로그를 근거로** 이야기했습니다. 문서는 합의의 기록이지 동작의 증거가 아니니까요.

**"목업까지 직접 만드는 건 비효율 아닌가요?"**
→ 재작업 비용과 비교하면 아닙니다. 특히 비개발자 고객사는 **말로 들은 요구사항과 화면으로 본 요구사항이 다릅니다.** 개발이 끝난 뒤에 "이게 아니었다"가 나오는 것보다 앞에서 며칠 쓰는 편이 쌉니다.

**"의견이 충돌하면 어떻게 하나요?"**
→ 같은 원칙입니다. **판단이 갈리는 지점을 문서나 화면으로 눈에 보이게 만든 뒤** 이야기합니다. 말로만 오가면 각자 다른 것을 상상한 채 동의하게 되는 경우가 많습니다.

**"코드 리뷰나 팀 내부 협업은요?"**
→ 같은 생각으로 접근합니다. 리뷰에서 "이게 낫다"보다 **"이렇게 하면 이런 경우에 이런 문제가 난다"** 는 형태로 말하려 합니다. 취향 논쟁이 아니라 조건과 결과를 같이 놓고 보게 하는 방식입니다.
