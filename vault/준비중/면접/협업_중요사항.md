# 협업 시 중요시 여기는 사항

> 작성 팁: 가치관 한 줄 → 그렇게 생각하는 이유 → 실제로 그렇게 행동한 사례

## 답변 (2026-08-19)

> 키워드: **모호함 제거 · 명확한 규약**
> 사례는 **이해관계자별 3종** — 개발팀 내부 / 고객·영업 / 사외 협력사.
> (출처: 자기소개서 202607 §4 — 실제 경험 3건이 그대로 정리돼 있음)

제가 협업에서 가장 중요하게 생각하는 것은 **모호함을 없애고 명확한 규약을 먼저 세우는 일**입니다. 모호한 소통은 결국 시스템 오류나 잘못된 결과물로 돌아옵니다. 그래서 저는 **정의서·기준서·목업처럼 양측이 같은 것을 보게 만드는 장치**를 앞에 두고 이야기를 시작합니다.

> 💡 **면접에서는 셋 다 말하지 않는다.** 질문의 결에 따라 하나만 고른다.
> 기술 면접 → (3), 협업·인성 → (1), 임원·리더십 → (2).
> 시간이 있으면 (1) 또는 (2) 하나 + (3) 짧게.

---

### (1) 개발팀 내부 — 제 설계를 버리고 상대 팀 규격에 맞춘 일

현장관리 도메인 **9개 메뉴, 약 120개 API** 를 RESTful 원칙과 DTO 구조로 신규 설계했고, 이를 소비하는 쪽은 모바일팀이었습니다. 그런데 **제가 처음 잡은 규격이 모바일의 소비 패턴과 맞지 않았습니다.** 기존 웹 구조를 그대로 옮긴 탓에 DB 컬럼명이 JSON 키로 노출돼 클라이언트가 서버 테이블 구조에 묶였고, 화면 단위로 쪼개져 있던 처리를 모바일이 여러 번 호출해 조립해야 했습니다.

저는 **제 설계를 방어하는 대신 DTO 구조와 필드 네이밍을 전면 재정비했습니다.** 모바일팀과 용어·규격을 맞추는 합의를 반복하며 응답 필드를 화면이 쓰는 이름으로 다시 정의하고 카멜케이스로 일원화했고, 흩어져 있던 다단계 처리를 **단일 API 트랜잭션으로 통합**했습니다. 이 규격은 두 팀의 합의로 끝나지 않고 **사내 API 네이밍 표준**을 세우는 계기가 됐습니다.

> **"내 설계가 맞다"를 관철하는 것과 "우리 규격을 만든다"는 다른 일**이라는 것을 배웠습니다.

---

### (2) 고객·영업 — 한 고객사의 요구를 플랫폼 표준으로 승격시킨 일 ⭐

> 임원·리더십 면접에서 가장 강한 카드.

주요 고객사가 위험성평가에 **자사 현장 절차에 맞는 승인(결재) 요건**을 요구했습니다. 가장 빠른 방법은 기존 승인 로직을 한 벌 복사해 고치는 것이었고, 고객과 영업 입장에서는 그것으로 충분했습니다. 그러나 그것은 **승인 로직의 사본을 하나 더 만드는 일**이었습니다. 사본이 늘수록 정책이 바뀔 때 고쳐야 할 곳도 늘어납니다. 이번 한 벌로 끝나는 게 아니라 다음 고객사에서 또 한 벌이 되는 구조였습니다.

저는 요구를 반려하거나 "구조가 나빠진다"고 말하는 대신, **고객 요건은 그대로 충족하면서 사본은 늘리지 않는 제3의 안**을 설계해 가져갔습니다.

설명할 때도 중복이 쌓인다고 말하지 않았습니다. **"이번에 이렇게 만들어 두면 다음 고객사 요건은 더 적은 작업으로 받을 수 있다"** 는 쪽으로 말했습니다. 상대가 듣고 싶어 하는 것은 구조의 아름다움이 아니라 **다음번에 드는 시간**이라고 생각했기 때문입니다.

이 안이 받아들여져 **한 고객사의 개별 요구가 플랫폼 공통 표준으로 승격**됐고, 지금 구현 중인 표준 승인 모듈이 여기서 나왔습니다.

> 큰 충돌 없이 통과된 이유는 **선택지를 양자택일로 만들지 않았기 때문**이라고 생각합니다.
> 고객 요구를 들어주느냐 구조를 지키느냐로 놓으면 **개발이 항상 집니다.**
> 둘 다 되는 안을 만들어 가면 설득할 일 자체가 줄어듭니다.

요구사항을 옮길 때도 말로만 합의하지 않았습니다. 제가 직접 요구사항을 정리하고 **목업 화면을 만들어 시연**하며 의도와 일치하는지 확인한 뒤 개발에 착수했습니다. 문장으로 남겨도 서로 다른 그림을 떠올리기 쉽지만, **화면을 같이 보면 그 간극이 그 자리에서 드러납니다.**

---

### (3) 사외 협력사 — 문서가 아니라 데이터로 합의한 일

IoT 파이프라인을 구축하며 장비 제조사와 원격으로 통신 규격을 협의했는데, **수신 데이터의 날짜 포맷이 사전 정의서와 달라** 파싱 오류가 났습니다. 정의서에는 `yyyy-MM-dd HH:mm:ss` 였는데 실제로 오는 값은 `yyyyMMddHHmmss` 였고, 그 레코드들이 **조용히 적재에서 빠지고 있었습니다.**

저는 문서를 다시 확인해 달라고 요청하는 데 그치지 않고, **ELK 로그에서 실패 패턴을 추출해 어긋나는 구간을 특정**한 뒤 그 실제 데이터를 근거로 담당자와 송수신 포맷을 다시 확정했습니다. 양측이 같은 것을 보고 이야기하니 조치가 빠르게 끝났습니다.

**문서로는 잡히지 않는 문제도 있었습니다.** 운영 중 혈압 데이터의 **수축기(SBP)와 이완기(DBP)가 뒤바뀐 채 수신**되는 사례를 발견했는데, 원인은 송신 장비의 설정 오류였지만 **업체 측 수정에는 시간이 걸린다**는 답을 받았습니다. 그동안 잘못된 데이터를 쌓을 수는 없어, 제가 통제할 수 있는 **수신단에 방어 로직(역전 감지 시 경고 로그 + 스왑 보정)** 을 넣어 신뢰성을 먼저 확보한 뒤 장비 수정을 기다렸습니다.

> **상대를 기다려야 할 때에도, 제가 통제 가능한 지점에서 먼저 손을 쓰는 것 역시 소통의 일부**라고 생각합니다.

현재까지 **누적 약 140만 건을 유실 0건**으로 처리하고 있습니다.

## 꼬리질문 대비

**"상대(업체)가 안 고쳐주면요?"**
→ 위 (3) 혈압 역전 건이 정확히 그 사례입니다. **먼저 우리 수신단에서 막아두고** 그다음에 규격을 맞췄습니다. 상대의 일정에 우리 데이터가 인질로 잡히지 않게 하는 게 먼저라고 봤습니다.

**"정의서가 있는데 왜 어긋났나요?"**
→ 문서와 실제 송신이 다른 건 흔한 일이라고 생각합니다. 그래서 **문서를 근거로 다투기보다 로그를 근거로** 이야기했습니다. **문서는 합의의 기록이지 동작의 증거가 아니니까요.**

**"본인 설계가 틀렸다는 걸 어떻게 받아들였나요?"** ← (1) 관련
→ 틀렸다기보다 **소비자를 안 보고 만든 설계**였습니다. RESTful 원칙은 지켰지만 그걸 실제로 쓰는 쪽의 패턴을 안 물어봤습니다. 지금은 API 를 설계할 때 **소비하는 쪽을 먼저 만나는 것**을 순서에 넣습니다.

**"목업까지 직접 만드는 건 비효율 아닌가요?"**
→ 재작업 비용과 비교하면 아닙니다. 비개발자 고객사는 **말로 들은 요구사항과 화면으로 본 요구사항이 다릅니다.** 개발이 끝난 뒤 "이게 아니었다"가 나오는 것보다 앞에서 며칠 쓰는 편이 쌉니다.

**"영업이 일정을 밀어붙이면요?"** ← (2) 관련
→ 그래서 **일정을 놓고 다투지 않고 안을 하나 더 만들어 갔습니다.** "안 된다"는 협상이지만 "이렇게 하면 둘 다 된다"는 제안입니다. 후자는 상대가 거절할 이유가 적습니다.
