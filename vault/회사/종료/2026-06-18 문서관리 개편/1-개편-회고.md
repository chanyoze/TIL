고객사 한 곳이 우리 솔루션으로 옮겨 오면서 문서관리 개선을 다섯 가지 요청했다. 작성주기 관리, 문서 승인, 주기별 모니터링, 삭제 권한 통제, 본사 문서 공유다. 이 메뉴는 이미 쓰고 있는 사용자가 있었기 때문에, 요청을 다 넣되 **기존 사용자의 화면과 동작은 그대로 두는 것**이 이번 설계의 기준이었다. 2026-06-18 에 배포했다.

## 요청과 결정

| 요청 | 고른 것 | 근거 |
|---|---|---|
| 작성주기 관리 | 고정 주기 6종(일 · 주 · 월 · 분기 · 반기 · 연), 공통 코드로 제공 | "매주 둘째 금요일" 같은 가변 캘린더도 검토했으나 모니터링 집계와 시스템이 급격히 복잡해지고 사용자도 쓰기 어렵다 |
| 미작성 알림 | 다음 날 오전 한 번, 현장 사용자 전원 | 잦은 푸시로 인한 피로 |
| 문서 승인 | 이전 프로젝트의 승인 모듈을 시범 차용 — 문서관리를 다른 메뉴로 넓히는 첫 사례로 삼음 | 승인라인 등록이 한 시스템에 묶여 있어 분리가 필요했다 |
| 승인 적용 범위 | 카테고리에 "승인 사용"을 켠 문서만 | 전 문서에 갑자기 승인을 걸면 기존 사용자가 혼란스럽다 |
| 주기별 모니터링 | 현장용(카테고리 × 일자 매트릭스) · 본사용(마스터-디테일) 두 화면, 주기 종류는 동적으로 렌더 | 주기 종류가 영원히 6개라는 보장이 없다 |
| 작성 "완료" 기준 | 승인과 상관없이 **작성 여부** | — |
| 삭제 권한 통제 | 기존 보안등급에 "삭제 가능" 체크를 더하고, 기본값은 지금과 같게 | 전 메뉴 일괄 적용은 무리였고, 사용자-보안등급 매핑이 이미 있어 고칠 곳이 적다 |
| 본사 → 현장 공유 | 안전보건관리체계 구현 때 만든 본사 문서등록 선례를 차용 | — |

삭제 권한 요청은 공유 문서가 뜻하지 않게 지워지는 일을 막자는 것이었다. "작성한 사람도 못 지운다"는 요청 자체는 받아들였고, 그 통제를 **켜고 싶은 고객만 켜도록** 만들었다.

## 남겨 둔 논점

- 주기를 어긴 데 대한 강제성이 더 필요한가 — 오늘 써야 할 문서를 모아 보는 할 일 목록이나 대시보드 위젯 같은 것. 문서관리 모니터링용 대시보드 위젯은 뒤에 [따로 만들었다](../2026-09-30%20고객사%20문서관리%20모니터링/모니터링현장_대시보드위젯.md).
- 본사 공유 문서를 협력사도 봐야 하는가 — 당시 검토 중으로 남겼다(이후 결론은 확인 필요).

설계 다섯 축은 그대로 화면별 차단 조건과 검증 메시지로 떨어졌다. 그 규칙을 모아 둔 가이드는 비공개 저장소에 둔다.

## 배포에서 배운 것

배포 대상은 **개발 DB 에는 있고 운영 DB 에는 없는 객체**를 차집합으로 뽑아 정했다. 새 테이블 몇 개와 시퀀스 하나, 프로그램 · 메뉴 데이터였다. 이 과정에서 기준 하나를 분명히 했다.

- **환경 사이의 객체를 맞출 때 숫자 PK 로 비교하지 않는다.** 시퀀스로 발번되는 숫자 ID 는 개발과 운영이 서로 다르다. 테이블은 이름으로, 프로그램 · 메뉴는 사람이 붙인 고유 코드로 비교했다.
- 차집합을 그대로 쓰지 않고 이력 · 백업 테이블, 임시 테이블, 옵션 테이블을 걸러 냈다. 개발 DB 에는 실험 흔적이 섞여 있다.
- 운영 데이터를 바꾸기 전에 대상 테이블을 먼저 백업했다.

배포 말고도 공지, 개편 요약 메일, 설명 자료 작성이 같이 돌았다. 새 화면 일부는 요청한 회사에만 먼저 열었다. 미룬 일은 백로그에 옮겨 적었다.

## 돌아보면

- 기존 사용자가 있는 메뉴에 기능을 더할 때 가장 먼저 정한 것은 **기본값을 지금과 같게 두는 것**이었다. 승인도, 삭제 통제도 "켜야 동작한다"로 만들어 바꾸고 싶은 고객만 바뀌게 했다.
- 승인 모듈과 본사 문서등록 둘 다 이전 구현을 차용했다. 다만 승인 모듈은 원래 시스템에 묶인 승인라인 등록을 먼저 떼어 내야 했다.
- 환경 차집합으로 배포 대상을 뽑을 때는 **무엇으로 비교하나**부터 정해야 한다. 숫자 PK 로 비교했다면 같은 객체를 다른 것으로 봤을 것이다.
