> OTAT 승인 모듈 회고 4편 중 1편 — 다음 편: [2. 두 엔진을 한 화면에](./2-두-엔진을-한-화면에.md) · [3. 누가 올렸고 누가 고치나](./3-누가-올렸고-누가-고치나.md) · [4. 곁가지에서 내린 구조 판단](./4-곁가지에서-내린-구조-판단.md)

수시위험성평가(메뉴 구분자 OTAT)의 결재는 공사팀장 → 안전팀장 → 현장소장 3단계가 컬럼 세 개(`APPRV_*`)와 상태코드(`STTS_CD` 30~60)에 박혀 있었다. 회사마다 결재 라인이 다른데 칸이 셋으로 고정이라 늘릴 수도 줄일 수도 없었다. 사내에는 이미 승인 라인을 데이터로 관리하는 승인 모듈(SCNT 엔진)이 있었고 문서관리(DCMT) · 장비점검(CESC)이 쓰고 있었다. 문제는 그 두 화면도 요청 · 승인 · 반려 · 취소 로직을 **각자 복붙**해 쓰고 있었다는 점이다. 그래서 질문이 둘이 됐다 — "수시평가를 승인 모듈로 옮기자"와 "옮기는 김에, 다음 모듈은 복붙 없이 붙게 하자". 이 편은 2026년 7월 초, 코드를 한 줄도 쓰기 전에 내린 판단들과 그중 무엇이 착수 직후 뒤집혔는지를 다룬다.

---

### 1. 공통 코어를 고칠까, 옆에 파일을 둘까

**고민.** 복붙을 없애려면 공통 헬퍼가 필요하다. 가장 자연스러운 자리는 모든 화면이 이미 쓰는 `cips.js` 와 전역 설정 `config.xml` 이다. 하지만 이 둘은 공통 파일 관리 책임자가 따로 있는 코어이고, 승인이 필요한 화면은 전체 중 일부뿐이다. 서버 쪽도 마찬가지로 승인 엔진(`CommonSanctionService`)을 고쳐서 공통화할지, 그 위에 한 겹을 얹을지 정해야 했다.

**선택지.**

| | 방식 | 장점 | 걸리는 점 |
|---|---|---|---|
| A | `cips.js` 에 직접 추가 | 어디서나 바로 호출 | 코어 수정 → 전 화면 회귀 범위, 관리 책임자 영역 침범 |
| B | 별 파일 + `config.xml` 전역 등록 | 화면 코드 변경 없음 | 승인 없는 화면도 전부 로드, 결국 코어 설정 수정 |
| C | 별 파일 + 필요한 화면 `<head>` 에서 개별 include | 코어 무수정, 필요한 곳만 로드 | 화면마다 include 한 줄 |

작성 스타일도 ES6 `class`/`module` 과 `cips.js` 식 객체 네임스페이스 사이에서 골라야 했다.

**결정.** C. `js/sanction/cips_sanction.js` 라는 새 폴더 · 새 파일을 두고, 내부는 `cips.sanction = cips.sanction || {}` 식 객체로 짰다. 서버는 엔진을 고치지 않고 그 위에 브리지(Bridge) 한 겹을 얹어, 모듈마다 작은 핸들러 하나만 구현하게 했다.

**이유.**
- 코어를 건드리지 않으면 회귀 범위가 "승인을 붙인 화면"으로 격리된다.
- 공통 파일 관리 책임자와 직접 협의해 위치 · 파일명 · 로드 방식 · 스타일 네 가지를 합의했다. `cips_` 접두는 벤더 파일과 사내 JS 를 이름만 보고 구분하려는 장치다.
- WebSquare 환경에서 `class`/`module` 은 쓰기 어려워 기존 `cips.js` 와 같은 객체 형태로 맞췄다.
- 엔진에는 이미 승인 · 반려를 한 호출로, 취소를 또 한 호출로 처리하는 메서드가 있었다. 참조 화면들이 하던 "엔진 호출 + 자기 상태 갱신" 조합을 공통으로 끌어올리는 리팩토링이지, 새 엔진이 필요한 게 아니었다.

**뒤집혔나.** FE 쪽 결정은 끝까지 유지됐다. 코어 불가침 원칙도 유지됐다. 다만 같은 시기에 정한 **서버 브리지의 위치**(`module/scnt`)는 착수 직후 뒤집혔다(5절). 돌아보면 관리 책임자와 합의한 FE 네 항목은 살았고, 확인 없이 진행하기로 한 BE 위치는 바뀌었다. 인과라고까지 말할 근거는 없지만 눈에 띄는 대비다.

### 2. 핸들러를 무엇으로 식별할까

**고민.** 브리지는 "이 요청이 어느 모듈 것인가"를 보고 해당 핸들러를 불러야 한다. 스프링에 `Map<String, 핸들러>` 를 주입받으면 빈 이름이 키가 되므로 `if/switch` 없이 `handlers.get(코드)` 한 줄로 디스패치된다. 그런데 초안 인터페이스에는 핸들러가 자기 코드를 신고하는 `String tgtCode()` 메서드가 따로 있었다. 코드가 두 군데(빈 이름 · 메서드 반환값)에 적히는 셈이다.

**선택지.**

| | 방식 | 장점 | 걸리는 점 |
|---|---|---|---|
| 유지 | `tgtCode()` 메서드 + 빈 이름 | 코드가 메서드로 명시됨 | 디스패치는 빈 이름만 씀 → 메서드는 중복 선언, 두 값이 어긋날 수 있음 |
| 단일화 | 빈 이름(`@Service("DCMT")`)만 | 한 곳에만 적음, 라우팅 로직 그대로 | 부팅 시 교차검증할 앵커가 사라짐 |
| 상수 | `static final String CODE` + `@Service(CODE)` | 앵커 유지 + 한 곳 정의 | 필요해지면 그때 도입할 탈출구 |

**결정.** 빈 이름 단일화. `tgtCode()` 를 인터페이스에서 지우고 "빈 이름 = 승인사용대상 코드 = 화면이 넘기는 코드" 3자 일치를 규약 주석으로 박았다.

**이유.**
- `tgtCode()` 는 디스패치에 쓰이지 않았다. 호출처를 찾아보니 단위 테스트 한 곳뿐이었다.
- 라우팅 코드를 하나도 고치지 않고 지운 상태로 테스트가 전부 통과했다 — "디스패치는 메서드를 안 쓴다"는 걸 그걸로 실증했다.
- 같이 정한 규약 두 개가 진짜 안전장치다. 이 프로젝트는 루트 · 서블릿 두 컨텍스트가 컴포넌트를 나눠 스캔한다. `@Component` 로 달면 서블릿에도 중복 생성되고, `@Controller` 로 달면 아예 루트의 Map 에서 빠져 **부팅이 아니라 버튼을 누르는 순간** "핸들러 없음"으로 터진다. 그래서 핸들러는 반드시 `@Service`, `@Controller` 는 금지로 못박았다.
- 대가(앵커 상실)는 알고 받아들였다. 빈 이름을 빠뜨리는 실수가 런타임에야 드러난다.

**뒤집혔나.** 아니다. 다만 문서 사이에는 흔들림이 남았다. 같은 시기의 적합성 분석(4절)이 정리한 "v2 인터페이스"에는 `tgtCode()` 가 다시 적혀 있다. 최종 코드의 핸들러 인터페이스에는 "`tgtCode()` 미도입"이라는 주석이 있어, 실제로는 단일화가 지켜졌다.

### 3. 목록 화면의 승인 정보는 어떻게 붙일까

**고민.** 승인 버튼을 누르는 경로는 브리지로 공통화했지만, 일반 목록 화면도 행마다 "지금 승인 상태 · 이 사용자가 누를 수 있는 버튼"을 같이 보여 줘야 한다. 참조 화면(CESC)은 목록을 조회한 뒤 **행마다** 승인 정보를 다시 조회했다. N행이면 N+1 쿼리이고, 키 꺼내기 · null 가드 · 컬럼 열댓 개 옮겨 담기가 메서드마다 복붙돼 있었다. 엔진에는 키를 모아 한 번에 조회하는 벌크 병합 메서드(`mergeSanctionInfo`)가 이미 있었는데, "메뉴마다 컬럼명이 달라 공통화가 어렵다"는 주석과 함께 방치돼 있었다.

**선택지.**

| | 방식 | 쿼리 수 | 개발 · 유지보수 | 결합도 |
|---|---|---|---|---|
| A | 모듈 인라인(현행) | N+1 | 메서드마다 복붙 | 낮음 |
| **B** | 공통 벌크 병합 | 2 (목록 + 벌크 1회) | 호출 한 줄 | 낮음 (키 컬럼만 파라미터) |
| C | 목록 SQL 에 공용 함수 인라인 | 1 | 모듈 SQL 마다 조인 | 높음 (모듈 SQL 이 승인 스키마에 묶임) |

**결정.** 기본은 B, 진짜 무거운 목록만 C. 방치된 벌크 병합을 살리되 입력 키 컬럼 세 개를 파라미터로 받게 하자고 정했다.

**이유.**
- 방치의 진짜 원인을 따져 보니 "출력 컬럼이 제각각"이 아니었다. 출력은 이미 표준이었고, 다른 건 **입력 키 컬럼명 세 개**뿐이었다. 장애물이 생각보다 작았다.
- B 는 순수 데이터 조인이라 핸들러도 필요 없다. 액션은 브리지, 조회는 병합 — 양쪽이 대칭이 돼야 표준이 완결된다고 봤다.
- C 는 쿼리 1개로 가장 빠르지만 모듈 SQL 이 승인 테이블 구조를 알게 된다. 성능이 한계일 때만 쓰는 탈출구로 남겼다.

**뒤집혔나.** 원칙은 지켰고, 방법은 달라졌다. 수시평가 목록은 키를 모아 승인 정보를 **한 번에** 조회한 뒤 메모리에서 붙인다 — N+1 은 피했다. 하지만 그 병합은 수시평가 서비스 안의 전용 메서드로 들어갔고, 공통 `mergeSanctionInfo` 는 지금도 키 파라미터 없이 원래 시그니처 그대로다. "공통으로 살린다"는 부분은 이뤄지지 않았다.

### 4. 실제 모듈에 대 보니 훅이 모자랐다

**고민.** 초안 핸들러는 쓰기 쪽 훅 세 개(요청 전 검증 · 요청 생성 후 · 승인/반려 후)에 코드 신고 메서드 하나, 합쳐 네 개짜리였다. 장난감 예제로는 잘 돌았지만, 이걸로 **이미 승인을 쓰는 실제 화면**(문서관리 승인 팝업 · 문서관리 본화면 · 장비점검)을 정말 다 옮길 수 있는지는 아무도 확인하지 않았다. 표준을 만들어 놓고 첫 이식에서 재설계하게 되는 게 가장 큰 위험이었다.

**선택지.**

| | 방식 | 걸리는 점 |
|---|---|---|
| 그대로 착수 | 초안 4개로 수시평가부터 구현 | 빈틈을 이식 중에 발견 → 표준 자체를 고치며 진행 |
| 실모듈 정적 대조 | 세 화면의 승인 코드를 전수 조사해 표준에 하나씩 매핑 | 착수가 며칠 늦어짐 |

**결정.** 정적 대조. 세 화면을 나눠 조사해 승인 관련 코드를 전부 목록으로 만들고, 각 항목이 표준의 어디로 가는지 매핑했다. 결론은 "조건부 가능" — 구조적 충돌은 없고, 빈틈은 전부 덧붙이면 되는 종류였다.

드러난 것 중 핵심만 추리면 이렇다.

- **읽기 쪽 훅이 없었다.** 문서관리는 보안 등급으로 열람을 막는다. 상태 조회가 엔진을 바로 부르면 이 게이트를 우회해 **상위 등급 문서가 새어 나간다**. 실수가 곧 보안 사고인 유일한 항목이라 `canView`(열람 게이트)와 `onStatusLoaded`(조회 결과 가공)를 새로 넣었다.
- **완료 후속이 없었다.** 장비점검은 최종 승인 뒤 장비 정보에 결과를 전파한다 → `onCompleted` 신설.
- **취소 경로에서 상태 동기화가 빠졌다.** 장비점검은 취소 때도 자기 상태를 갱신한다 → 취소도 승인/반려와 같은 훅을 타게 했다.
- **상태를 두 곳이 소유하고 있었다.** 문서관리 본화면이 자바에서 상태를 직접 되돌리는데, 표준도 상태를 갖게 되면 경합이 난다 → 상태 소유는 표준 한쪽으로.

그 밖에 협력사용 숨김/읽기전용 가드, 승인라인 변경, 묶음 생성 등이 나왔고, 묶음 생성은 "필요한 모듈이 생기면 그때"로 미뤘다.

**이유.** 표준의 가치는 "다음 모듈이 그냥 붙는다"에 있다. 그걸 첫 모듈(수시평가) 하나로 검증하면 수시평가에 맞춘 표준이 된다. 승인을 이미 쓰는 화면들에 먼저 대 보는 게 표준의 일반성을 확인하는 가장 싼 방법이었다.

**뒤집혔나.** 절반쯤. 실측으로 보강한 읽기 · 완료 훅 세 개(`canView` · `onStatusLoaded` · `onCompleted`)는 수시평가에서 **쓸 일이 없었다** — 7월 말에 셋 다 기본 동작 그대로 두기로 확정했다. 다른 모듈을 위한 자리로만 남았다. 반대로 초안에 있던 "요청 전 검증" 훅은 위치가 두 번 바뀌었다. 계획은 서버 훅이었는데, 실제로 그 훅이 "승인 요청" 시점이 아니라 "승인 건 저장" 시점에 불린다는 걸 알고 화면(FE) 게이트로 옮겼고, 9월 초에는 다시 "최종 승인 직전" 서버 훅을 새로 만들어 그쪽으로 옮겼다. 훅 목록도 이후 계속 늘었다. 그 과정은 이어지는 편들에서 다룬다.

### 5. 착수 직후 뒤집힌 여섯 가지

**고민.** 7월 초 인터뷰 열 라운드로 결정을 다 내리고, 7월 7일 구현 착수 문서(핸드오프)를 썼다. 그런데 그 핸드오프의 지시 중 여섯 가지가 실제 구현에서 뒤집혔다. 나중에 두 문서(도입 계획 · 착수 핸드오프)를 아카이브로 내리면서 머리에 "이 결정들은 번복됐다"는 경고를 달았다. 문제는 **무엇으로 바뀌었는지는 적었는데, 왜 바뀌었는지는 대부분 적지 않았다**는 것이다.

| # | 착수 시점 지시 | 실제 | 그 순간의 이유 |
|---|---|---|---|
| 1 | 기존 상태코드 · 결재자 컬럼 **전면 폐기**(clean-slate) | **존치 + 소급 유지** | 기록 있음 ↓ |
| 2 | 상태를 숫자 5단계(10~50)로 번역 | 엔진 상태코드 **문자열을 그대로 복사** | 기록 있음 ↓ |
| 3 | 새 상태 컬럼 이름 `STS_CODE` | `CFM_STS_CODE` | 없음 |
| 4 | 브리지 위치 `module/scnt`, 이름 `SanctionBridge` | `module/common`, `CommonSanctionBridge` | 없음 |
| 5 | 승인사용대상 코드 `SFAS_AT`(잠정) | `OTAT` | 없음 |
| 6 | 적용 범위 원청 + 협력사 **동시** / 승인 패널 wframe **1개** | 원청 먼저(협력사는 뒤로) / wframe **2개** | 일부 ↓ |

(엄밀히는 6번에 두 건이 묶여 있다. 범위와 패널은 같은 "구조를 얼마나 크게 잡나" 판단이라 한 줄로 셌다.)

**1. 폐기 → 존치.** 계획은 "새로 만드는 건만 승인 모듈, 옛 컬럼은 숨김"이었다. 그런데 전환 단위가 **현장별 옵션**이라 한 현장 안에 옛 방식 회차와 새 방식 회차가 같이 산다. 옛 상태 컬럼에 값이 든 건도 천여 건 있었다. 한 컬럼에 둘을 합치면 구분할 방법이 없다. 더 결정적인 건 진행 중이던 회차다. 안전팀장 승인을 기다리던 회차가 옵션 전환 순간 옛 버튼은 사라지고 새 엔진 기준으로는 요청도 안 된 상태가 되면, **승인도 취소도 못 하고 멈춘다**. 승인 이력은 감사 성격이기도 해서, "회차는 자기가 시작한 방식으로 끝까지 간다"를 택했다. 이게 [2편](./2-두-엔진을-한-화면에.md)의 출발점이다.

**2. 숫자 번역 → 코드 복사.** 핸들러가 엔진 상태(`REG/DEM/PROG/REJ/CMPL`)를 숫자로 번역하지 않고 그대로 복사만 하면 틀릴 여지가 없다. 표시명은 공통코드에서 가져오므로 문구가 바뀌어도 SQL 을 고칠 필요가 없다. 문서관리 예제의 숫자(40=반려, 50=완료)를 수시평가가 그대로 베끼면 어휘가 어긋난다는 경고도 이미 핸드오프에 있었다.

**3. 컬럼 이름.**

같은 테이블에 이미 `STS_CODE` 가 있었다. 이름이 겹치지 않게, 그리고 새 엔진 쪽 상태라는 것을 이름만 보고 알 수 있게 `CFM_` 을 붙였다.

**4. 브리지 위치.** 문서끼리 이미 어긋나 있었다. 도입 계획과 제안서는 `module/scnt` 였지만, 7월 초 파트 리더 리뷰 발표 자료와 예시 구현은 처음부터 `module/common` 의 `CommonSanctionBridge` 였다. 착수 핸드오프는 "가제(예시 구현) → 실제(계획)" 번역표를 만들어 `module/scnt` 로 되돌리라고 지시했고, 실제 구현은 다시 `module/common` 으로 갔다.

결정은 디렉터의 의견이었다. 공통 연동 코드를 `module/common` 에 모아 두는 것이 사내 표준이기도 했다. 핸드오프의 `scnt` 는 가제였고, 결국 표준 자리로 돌아온 셈이다.

**5. 승인사용대상 코드.** 계획 안에서도 `SFAS_AT` 와 `SFAS_AT_RISKASMT` 가 섞여 있어, 핸드오프는 "한 곳에 상수로 두고 확정되면 거기만 바꾸라"고 했다. 최종 값은 `OTAT` 다.

`OTAT` 는 상시·수시위험성평가의 메뉴 구분자다. 앞으로 모든 도메인이 자기 메뉴 구분자(4글자 고정)를 승인 사용대상 코드로 쓰게 할 생각이었고, 첫 모듈부터 그 규칙을 따랐다.

**6-a. 적용 범위.** 범위는 한 번이 아니라 세 번 움직였다. 인터뷰 첫 라운드에서는 "원청만", 9라운드에서 "원청 + 협력사 동시"로 넓혔고, 착수 후 다시 "원청만(협력사는 백로그)"으로 좁혔다. 협력사 화면 배선은 결국 9월 초에 끝났다.

처음 "원청만"으로 잡은 건 협력사를 위한 배려였다. 협력사 화면은 기존 프로세스를 그대로 두려 했다 — 가뜩이나 화면 이해도가 낮은 협력사 사용자에게 새 흐름까지 얹고 싶지 않았다. 그러다 원청 · 협력이 모두 승인 모듈을 쓰는 선례(장비안전점검)가 이미 있다는 점을 보고 양쪽으로 넓혔던 것으로 기억한다. 착수 뒤 다시 원청부터로 좁힌 이유는 남아 있지 않다.

**6-b. 패널 수.** 이것도 2 → 1 → 2 로 움직였다. 인터뷰 9라운드는 상태 그리드 + 버튼을 한 wframe 에 담는 패널 1개를 골랐다. 리뷰 발표와 예시 구현은 그리드 · 버튼 2개로 나눴는데, 이유는 기록돼 있다 — **화면마다 버튼 위치가 달라서** 버튼을 그리드에 붙이지 않고 따로 놓을 수 있어야 한다. 그런데 착수 핸드오프는 "스펙은 1개, 2분할 복제 금지"라고 되돌렸고, 실제로는 다시 2개(Grid · Button)로 만들었다.

**뒤집혔나.** 이 절 자체가 뒤집힌 기록이다. 다만 하나 짚어 둘 것은, 여섯 가지가 모두 **이름 · 위치 · 범위 · 데이터 보존 정책**이었다는 점이다. "코어는 고치지 않는다 + 브리지가 오케스트레이션 + 모듈은 핸들러 하나"라는 골격은 한 번도 흔들리지 않았다.

## 돌아보면

- **결정을 바꿀 때 이유를 그 자리에 한 줄 남기지 않으면, 석 달 뒤엔 나도 모른다.** 번복 여섯 건 중 이유가 남은 건 두 건뿐이고, 둘 다 별도 공유 문서를 쓰면서 우연히 남았다. 그래서 이 회고 곳곳에도 이유를 끝내 복원하지 못한 결정이 남았다.
- **문서끼리 이미 어긋나 있으면 "어느 쪽이 정본인가"부터 정해야 한다.** 계획과 리뷰 자료가 같은 시기에 다른 패키지를 말했고, 착수 문서는 그중 하나를 골라 되돌렸다가 다시 뒤집혔다.
- **실모듈 대조는 싸고 효과가 컸다.** 보안 누출 같은 빈틈을 착수 전에 잡았다. 다만 그때 늘린 훅이 첫 모듈에선 쓰이지 않았다 — 일반화는 검증하되, 구현은 실제로 쓰는 모듈이 나올 때 해도 늦지 않았다.
- **세부는 다 바뀌어도 골격이 남으면 설계는 성공한 것이다.** 이름 · 위치 · 범위는 흔들렸지만 "코어 불가침 + 브리지 + 모듈당 핸들러"는 끝까지 그대로였다.
