(주)금도건설 문서관리 모니터링 마일스톤에서 실제로 만든 것을 정리한 글이다. 작업은 두 갈래다. 하나는 **웹 문서설정관리에서 모니터링할 현장을 고르는 기능**이고, 다른 하나는 **웹의 문서 모니터링 화면 두 개를 간소화해 대시보드 위젯으로 옮기는 것**이다. 위젯은 본사용과 현장용 두 개로 나눴고, 본사용은 협업자가, 현장용은 내가 맡았다.

기준: 2026-10-20. 웹 `cip-defg-saas`, 대시보드 `saas-dashboard` · `saas-dashboard-vue` 모두 브랜치 `20261203`.

## 먼저 알아둘 용어

- **카테고리**: 문서를 분류하는 폴더 같은 단위. 회사가 만들어 모든 현장에 똑같이 내려주는 **회사 카테고리**(`TDCMT_CTGRC`)와, 각 현장이 실제로 쓰는 **현장 카테고리**(`TDCMT_CTGRP`)가 따로 있다. 현장은 자기만의 카테고리를 더 만들 수 있다.
- **작성주기**: "매주", "매월"처럼 그 카테고리 문서를 얼마나 자주 올려야 하는지 정한 것. 회사 주기(`TCCMS_DCMT_CTGRP_CYCLE`)와 현장 주기(`TDCMT_CTGRP_CYCLE`)가 따로 있다.
- **회차**: 작성주기를 달력 위에 펼친 한 칸. 예를 들어 "매월" 주기면 9월 한 달이 한 회차다. 그 기간 안에 문서가 하나라도 올라오면 그 회차는 **등록**이다.
- **위젯**: 대시보드 화면에 끼워 넣는 작은 화면 조각. 본사 탭에 두는 것과 현장 탭에 두는 것이 있다.

## 1. 웹 — 문서설정관리 [모니터링현장] 탭

시스템관리 > 문서관리 > 문서설정관리에 탭을 하나 추가했다. 본사 관리자가 **모니터링에서 뺄 현장**을 고른다.

동작 규칙은 세 가지다.

- **기본은 전부 모니터링한다.** 아무것도 설정하지 않은 현장은 모니터링 대상이다. 빼고 싶은 현장만 체크를 해제한다.
- **목록에는 진행 중인 현장만 나온다.** 준공된 현장은 자동으로 모니터링에서 빠진다.
- **해제해도 기록은 지우지 않는다.** 테이블(`TCCMS_DCMT_MON_PROJ`)에 `MON_TF = 'F'`로 남겨서 누가 언제 뺐는지 알 수 있다.

같은 기능이 회사 화면과 시스템관리자 화면 두 곳에 있다. 시스템관리자 화면은 회사를 먼저 고른 뒤 설정한다. 조회 조건으로 전체 · 대상 · 제외를 고를 수 있고, 일괄변경 버튼으로 여러 현장을 한 번에 바꾼다.

**제외한 현장이 빠지는 곳**

- 문서관리 > 모니터링 메뉴 3개: 회사작성주기별문서모니터링 · 회사작성주기별일간문서모니터링 · 회사기준현장카테고리별문서통계
- 대시보드 **본사용** 문서 모니터링 위젯

현장용 위젯에는 적용되지 않는다. 현장용은 그 현장의 탭 안에서 자기 현장만 보기 때문이다. 화면 안내문에는 "대시보드 문서 모니터링 위젯에서 제외"라고만 적혀 있어서, 본사용만이라고 고칠지는 아직 정하지 않았다.

## 2. 대시보드 위젯 두 개

| | 본사용 | 현장용 |
|---|---|---|
| 이름 | 회사작성주기별일간문서모니터링 | 현장 문서 작성주기 모니터링 |
| 원본 웹 화면 | 회사작성주기별일간문서모니터링 | 현장작성주기별문서모니터링 |
| 놓이는 곳 | 본사 탭 | 현장 탭 |
| 보는 것 | 현장별 등록건수 · 등록률 | 한 현장의 카테고리별 회차 등록률 |
| 기준 주기 | 회사 주기 | 현장 주기 |
| 기준 시점 | 기준일 하루가 속한 주기 | 조회기간 안에 끝난 회차들 |
| 담당 · 상태 | 협업자, 목 데이터 샘플 | 나, API 연결 완료 (테스트 탭에만 등록) |

### 본사용 위젯 (협업자 작업, 샘플 단계)

회사 카테고리를 기준으로 접근 권한이 있는 현장마다 문서 등록건수와 등록률을 보여 준다. 카테고리를 하나라도 등록하지 않은 현장은 **미등록 현장**으로 분류된다.

- ① 현장명을 누르면 그 현장의 카테고리별 등록 현황 팝업이 뜬다. 미등록 카테고리에는 마감까지 남은 날이 D-day로 붙는다.
- ② 회사 카테고리 버튼을 누르면 회사 카테고리 구성이 트리로 뜬다. 폴더마다 하위 카테고리 수가, 맨 아래 카테고리에는 작성주기가 표시된다.

### 현장용 위젯 (내 작업)

선택한 현장의 카테고리마다, 조회기간 안에 끝난 회차 중 문서를 올린 회차가 몇 개인지 등록률로 보여 준다. 등록률이 낮은 카테고리가 맨 위에 와서 밀린 문서를 바로 찾을 수 있다.

예를 들어 "안전점검일지"가 매월 주기이고 조회기간이 1월~9월이면, 끝난 회차는 9개다. 그중 6개월에 문서가 있으면 등록률은 6/9(67%)로 표시된다.

- ① 카테고리를 누르면 회차별 등록 여부가 최근 회차부터 카드로 뜬다.
- ② 꼬리말의 「현장 카테고리 N개」를 누르면 상위 카테고리별로 묶은 구성 팝업이 뜬다.
- 조회기간 안에 끝난 회차가 하나도 없는 카테고리는 「–」로 표시되고 맨 아래에 놓인다.

디자인은 본사용 샘플에 맞췄다. 한 줄 도구줄(제목 · 전체/미등록/등록 · 검색 · 기간 버튼)과 표 구성이 같아서, 두 위젯을 나란히 두어도 한 세트로 보인다.

## 3. 현장용 쿼리에서 정한 것

웹 현장 화면(현장작성주기별문서모니터링)과 숫자가 맞도록 다음을 정했다.

- **주기는 현장 주기 테이블을 읽는다.** 현장이 고유한 작성주기를 따로 만들 수 있어서다. 본사용은 회사 주기를 읽는다.
- **카테고리는 현장 카테고리만 본다.** 회사 카테고리에 있는지는 따지지 않는다. 그래서 현장에서만 만든 카테고리도 나온다. 테스트 사용자로 확인했을 때 8개 현장 중 2곳이 카테고리 7개에서 8개로 늘었다.
- **상위 카테고리 전체 경로를 함께 준다.** `본사안전보건관리문서 > … > 그룹웨어 기안문서(본사)`처럼 이어 붙인 문자열이다. 마우스를 올리면 보이고, 검색도 이 경로에서 찾는다.
- **회차는 조회기간 안에 시작해서 끝난 것만, 카테고리당 최대 50개까지** 센다. 진행 중인 회차는 넣지 않는다.

이 차이 때문에 **같은 현장이라도 본사용과 현장용의 카테고리 수가 다를 수 있다.** 버그가 아니라 기준이 다른 것이니 협업자에게 미리 알려 둘 것.

## 4. 저장소에 올라간 것

**백엔드 `saas-dashboard` — `b474950`**

`ModaDashboardWidgetDcmtCycleMonitoring` 이름으로 Controller · Service · Mapper · Model · SQL XML 다섯 파일을 한 세트로 올렸다. 현장용 API 하나(`project/category-histories`)와 본사용 API 넷(`projects`, `project/categories`, `company-categories`, `excluded-project-count`)이 함께 들어 있다.

처음엔 "위젯 하나에 백엔드 한 세트"가 표준인지 고민했다. 확인해 보니 대시보드 저장소는 **같은 주제의 위젯끼리 한 세트를 나눠 쓰는 것**이 관례였다. 예를 들어 RegisterCycleMonitoring 한 세트가 위젯 네 개를 받친다. 그래서 공용 이름 그대로 두고, 나눌지는 협업자가 복귀한 뒤 다시 이야기하기로 했다.

**프론트 `saas-dashboard-vue` — `943be1d`**

현장용 화면 세 파일(본체 · 표 · 기간 선택)과 테스트 탭 등록만 올렸다. **아직 실제 현장 탭에는 등록하지 않았고, 테스트 탭 「이찬호 리더」에서만 보인다.** 실제 탭에 올릴 때는 위젯 명세, 탭 목록 한 줄, 컴포넌트 매핑 한 줄, 새 디자인 썸네일을 더하면 된다.

## 5. 남은 일

- 협업자와 합의: 등록률 분모(회사 카테고리 전체 vs 현장이 가진 카테고리), API 필드 이름, 전체 경로 필드, 기준일 고르는 방식(셀렉트 vs 달력)
- 백엔드 한 세트 유지 vs 분리 결정
- 현장용 위젯을 실제 현장 탭에 등록하고 썸네일 교체
- 문서설정관리 안내문의 "대시보드 위젯" 범위를 본사용으로 좁힐지
- 운영 반영 순서 확인: 본사용 API가 읽는 `TCCMS_DCMT_MON_PROJ` 테이블이 운영 DB에 먼저 있어야 한다. 없으면 `ORA-00942`로 실패한다. 현장용 API는 이 테이블을 쓰지 않는다.

## 6. 겪은 것

- **SQL 매퍼 XML 머리말이 두 번 깨졌다.** `<?xml …?>`가 `< ? xml version = …`처럼 벌어졌다. 에디터에서 언어 모드를 SQL로 바꿔 보다가 정렬 단축키가 SQL 포매터로 돈 것으로 추정한다. XML 파일은 XML 모드로만 연다.
- **주석은 짧게 쓴다.** 처음에는 분석하면서 만든 개인 메모의 규칙 여섯 개를 SQL 머리말에 그대로 옮겼다. 남이 읽기에는 지리멸렬하고 대부분 당연한 내용이라 지우고, 쿼리마다 "…을 조회한다." 한 줄만 남겼다.
- **로컬 실행:** 프론트는 `npm run dev`, 백엔드는 `SPRING_PROFILES_ACTIVE=local ./gradlew bootRun`(포트 10090, 기동 약 2분)으로 띄운다. 매퍼 XML을 바꾸면 백엔드를 다시 띄워야 한다.
