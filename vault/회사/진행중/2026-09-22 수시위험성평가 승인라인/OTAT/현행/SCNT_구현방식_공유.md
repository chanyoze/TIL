# 상시·수시위험성평가 SCNT 표준승인 — 구현 방식 공유

> **마일스톤**: [ATMS26-012] 한화오션(주) 상시·수시위험성평가 승인모듈 기능 추가
> **작성**: 2026-07-20 / 이찬호
> **목적**: 구현 방향 설명용. 대면 설명 전에 훑어보시면 됩니다.
> **상세 스펙**: [SCNT_표준승인_도입계획.md](./SCNT_표준승인_도입계획.md) (결정 D1~D11 원본)

---

## 1. 한 줄 요약

수시위험성평가의 **자체 승인 로직**(`STTS_CD` 30/40/50/60 + 공사팀장/안전팀장/현장소장 고정 3단계)을
**SCNT 표준 승인관리**로 대체하고, 다른 모듈도 붙일 수 있는 **재사용 표준**을 함께 세웁니다.

기존 방식의 근본 문제는 **승인선이 3단계로 하드코딩**돼 있다는 점입니다.
회사마다 결재 라인이 다른데 컬럼(`APPRV_C/BD/A_USER_NO`)이 3개로 고정돼 있어 확장이 안 됩니다.
SCNT는 승인라인을 데이터로 관리하므로 이 제약이 사라집니다.

---

## 2. 핵심 설계 — 옵션으로 두 엔진을 가른다

### 2.1 상호배타 구조

| 상태 | `SFAS_OPT_060` | `SFAS_OPT_060_003` |
|---|---|---|
| 기존 결재 사용 | `T` | `F` |
| **SCNT 표준승인 사용** | **`F`** | `T` |
| 승인 미사용 | `F` | `F` |

- `060` = **기존 결재 엔진** on/off (의미 그대로 유지)
- `060_003` = **NEW 승인(SCNT)** 사용여부 (신규)
- **둘 다 `T`는 불가** — admin UI에서 양방향 잠금으로 원천 차단

### 2.2 ⚠️ 이 설계의 대가 (가장 주의할 점)

SCNT 현장은 **`060 = F`로 저장**됩니다.
그래서 `060='T'`를 **"승인 활성"** 으로 읽는 기존 SQL이 SCNT 현장을 **"승인 없음"으로 오판**합니다.

```sql
-- 약 15~20 파일 / 40여 조건절을 일괄 수정해야 함
SFAS_OPT_060 = 'T'  →  (SFAS_OPT_060 = 'T' Or SFAS_OPT_060_003 = 'T')
SFAS_OPT_060 = 'F'  →  (SFAS_OPT_060 = 'F' And SFAS_OPT_060_003 = 'F')
```

빠뜨리면 **미승인 건이 목록에 노출되거나 상태 라벨이 공백**이 됩니다.
→ 상세 목록: [SfasRcpt_옵션060_영향목록.md](./SfasRcpt_옵션060_영향목록.md)

## 2.5 옵션을 바꾸면 기존 회차는 어떻게 되나 (소급 유지) ✅ 적용 완료

> 실무에서 가장 많이 물어보실 부분이라 따로 정리했습니다.

### 결론부터 — **기존 회차는 건드리지 않습니다**

기존 결재(060)를 쓰다가 SCNT(060_003)로 바꿔도, **이미 만들어진 회차는 원래 방식 그대로** 굴러갑니다.
옵션 변경 시점 **이후에 새로 만든 회차부터** SCNT로 진행됩니다.

| | 옵션 변경 전에 만든 회차 | 변경 후에 만든 회차 |
|---|---|---|
| 결재 방식 | **기존 결재 그대로** | SCNT 표준승인 |
| 상태 표시 | `공사팀장승인대기` 등 기존 문구 | `승인대기` 등 SCNT 문구 |
| 승인 버튼 | **그대로 뜸** (계속 승인/취소 가능) | 승인 팝업에서 처리 |

즉 **한 화면에 두 방식이 섞여** 보입니다. 회차마다 자기가 시작한 방식으로 끝까지 갑니다.

### 왜 이렇게 했나

옵션을 바꾸는 순간 **전부 SCNT로 갈아엎는 방식**도 있었는데, 그러면 이런 일이 생깁니다.

> 안전팀장 승인을 기다리던 회차가 있는데 옵션을 바꿈
> → 기존 승인 버튼이 사라지고, SCNT 기준으로는 아직 요청도 안 된 상태
> → **승인도 취소도 못 하는 상태로 멈춤**

승인 이력은 감사 성격이라 나중에 "이 회차가 어떻게 승인됐는지"가 바뀌면 곤란하기도 합니다.
그래서 **진행 중이던 건은 절대 끊기지 않게** 하는 쪽을 택했습니다. 옵션을 되돌려도 마찬가지입니다.

### 화면에서 보이는 상태값

승인이 붙으면서 상태 컬럼에 아래 값들이 나타납니다. **하나의 "상태" 컬럼**에서 회차에 따라 달라집니다.

**SCNT로 진행되는 회차**

| 상태 | 언제 |
|---|---|
| 작성중 | 아직 승인라인을 만들지 않음 |
| 요청대기 | 승인라인은 저장했고, 승인요청 전 |
| 승인대기 | 승인요청함 |
| 승인중 | 결재가 중간 단계까지 진행됨 |
| 승인반려 | 반려됨 |
| 승인완료 | 최종 승인됨 |

**기존 결재로 진행되던 회차**는 예전 문구(`공사팀장승인대기`·`안전팀장승인대기`·`현장소장승인대기`·`평가서승인완료`)를 그대로 유지합니다.

상태 컬럼 옆에 **단계 / 대기자** 두 컬럼이 추가되어, 지금 몇 단계이고 누구 차례인지가 목록에서 바로 보입니다.
(기존 결재 회차는 이 두 칸이 비어 있습니다)

### 승인 팝업은 언제 열리나

**SCNT로 진행되는 회차의 상태값을 클릭**하면 열립니다. 기존 결재 회차는 클릭해도 열리지 않고, 예전처럼 목록의 승인 버튼으로 처리합니다.

## 3. 데이터 구조

### 3.1 호스트 테이블 `TSF_ASSMNT_RECEIVE` (컬럼 4개 추가 — 반영 완료)

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `CFM_COMPANY_ID` | `NUMBER` | SCNT 승인요청 링크 |
| `CFM_PROJ_CODE` | `VARCHAR2(30)` | 〃 |
| `CFM_DEM_SN` | `NUMBER` | 〃 |
| `CFM_STS_CODE` | `VARCHAR2(10)` | **승인상태 캐시** |

**기존 `STTS_CD`는 그대로 둡니다.** 컷오버가 현장별이라 한 현장에 구/신 데이터가 공존하므로,
한 컬럼에 Case로 합치면 둘을 구분할 방법이 없습니다. (실제로 `STTS_CD`에 값 있는 건 1,491건 존재)

### 3.2 `CFM_STS_CODE` — SCNT 코드를 그대로 복사

숫자 코드로 번역하지 않고 **`TBASE_SANCTN_DEM.STS_CODE` 값을 그대로** 씁니다.

| 코드 | 표시명(공통코드 `SANCTN_STS_CODE`) |
|---|---|
| `REG` | 작성중 |
| `DEM` | 승인대기 |
| `PROG` | 승인중 |
| `REJ` | 승인반려 |
| `CMPL` | 승인완료 |

**이유**: Handler가 번역 없이 복사만 하면 되어 틀릴 여지가 없고,
표시명은 `SF_GetCommonCodeName()`이 처리하므로 문구가 바뀌어도 SQL을 안 고칩니다.

### 3.3 저장 vs 조회 구분

| 데이터 | 방식 |
|---|---|
| 상태(`CFM_STS_CODE`) + DEM 링크 3키 | **호스트에 저장** (Handler가 write) |
| 승인단계명 · 대기자 | **저장 안 함** — 조회 시 SCNT에서 주입 |

단계·대기자를 저장하면 SCNT와 **이중 소유**가 되어 정합이 깨집니다. CESC·DCMT도 동일 원칙입니다.

## 4. 화면 구성

### 4.1 외곽 목록 `SfasRegAtRiskasmtRcpt`

`060_003 = T`면 승인 관련 컬럼을 **세트 단위로 교대**합니다.

```
[기존 결재]  상태 | 공사팀장 | 안전팀장 | 현장소장
                        ↓  060_003 = T
[SCNT]       상태 | 단계 | 대기자
```

| 컬럼 | 노출 조건 |
|---|---|
| `STATUS` (레거시 상태) | `!060_003` |
| `CFM_STS_NAME` (상태) | `060_003` |
| `SANCTN_STEP_NAME` (단계) | `060_003` |
| `SANCTN_STEP_USER_NAME` (대기자) | `060_003` |
| `APPRV_C/BD/A_USER_NM` (승인선 3컬럼) | `060` → SCNT에선 자동 숨김 |
| `C_USER_NM` (공사팀장 지정) | `!060 && !060_003` |

> `C_USER_NM`은 이름이 "작성자"처럼 보이지만 실제로는 **직책코드 `'C'`로 조회한 공사팀장 지정**입니다
> (`SFCC_GetUserByDrCd(..., 'C', ...)`). 승인선을 SCNT가 관리하므로 SCNT 현장에선 숨깁니다.

**성능**: 목록 화면이라 행마다 SCNT를 조회하면 N+1이 됩니다.
그래서 키를 모아 **`selectSanctionDemandMap()` 1회 호출** 후 메모리 병합합니다.
(CESC는 행마다 호출하는 N+1 구조 — 그대로 따르지 않았습니다)

### 4.2 승인 팝업 `SfasPopRegRiskAssessmentConfirm` (신규)

목록에서 **상태 컬럼 클릭** 시 열립니다. 조회 전용이며, 승인 액션은 승인패널 wframe이 담당합니다.

- 표 상단: 평가서 요약 (옵션별로 행 표시/숨김)
- 하단: 내용 그리드 + 검토의견 그리드
- 우측: **승인패널** (단계 이력 + 승인/반려/취소 버튼)

**외곽 3컬럼 = 요약 / 팝업 승인패널 = 상세** 관계입니다.

## 5. 종합검토의견 — 승인과 분리

기존에는 종합의견이 **승인 액션의 산출물**이었습니다.
승인 버튼 → 의견 팝업 → 입력한 텍스트 1개가 **누가/어느 단계냐에 따라 갈려서** 저장:

```
STTS_CD=30 & 공사팀장 → SYNTH_CONSTR_OP
STTS_CD=40 & 안전팀장 → SYNTH_SAF_OP
STTS_CD=50 & 현장소장 → APPRV_CMT
```

승인취소하면 **내용이 지워지기까지** 했습니다.

### SCNT에서는

종합의견은 *"항목별 검토의견을 일일이 쓰기 힘드니 평가서 단위로 하나만 쓰고 퉁친다"* 는 용도이므로,
**승인과 완전히 분리**해 작성자가 **미리 채워두는 입력 항목**으로 둡니다.

| | 기존 (060) | **SCNT (060_003)** |
|---|---|---|
| 쓰는 시점 | 승인하면서 (결재자) | **미리, 본문에서** (작성자) |
| 검증 시점 | 각 결재 단계 | **승인요청 직전 1회** |
| 검증 범위 | 자기 것 1개 | **공사팀·안전팀 종합의견 둘 다** |
| 승인취소 시 | 내용 초기화 | **보존** |

```
옵션092(종합검토의견 사용) = T  AND  옵션060_002(작성검증) = T  이면
  → SYNTH_CONSTR_OP · SYNTH_SAF_OP 둘 중 하나라도 비면 승인요청 차단 (레거시 동형)
```
✅ **FE 게이트 구현 완료** — 팝업 `fnValidateSynthOp`가 request 분기에서 검증. 차단 문구 **"승인의견을 입력하세요."**(레거시 `SfasPopRegConfirmOpinion`과 동일). 
※ 규칙은 092만이 아니라 **092 && 060_002**(레거시 실제 동작 확인). BE 2겹은 미적용 — 코어 `validateBeforeDemand`가 **저장(createDemand) 시점**이라 "승인요청 전" 규칙과 타이밍이 어긋나고, FE 게이트로 충분하다고 판단(A안).

## 7. 설명 때 같이 보면 좋을 것

- **§2.2 SQL 일괄수정** — 범위가 가장 넓고 누락 시 증상이 조용해서, 리뷰가 가장 필요한 부분입니다
- **§3.2 코드 방식** — 숫자 번역 대신 SCNT 코드 복사를 택한 근거
- **§5 종합의견 분리** — 사용감이 바뀌는 부분이라 업무 확인이 필요할 수 있습니다

### 아직 확정 안 된 것

- **승인 단계 ↔ 종합의견 컬럼 매핑**: 기존엔 3단계 고정이라 단계별로 어느 컬럼에 쓸지 정해졌는데,
  SCNT는 라인이 커스텀이라 이 매핑이 성립하지 않습니다. 현재는 **역기록하지 않고 별도 항목으로 유지**하는 방향이며,
  필요해지면 승인자 직책 기준으로 매핑하는 방식을 검토합니다.
- **레거시 `STTS_CD` ↔ SCNT 상태 정합**: §2.2 SQL 수정 시 상태 버킷(`20/60`, `30~60`)이
  SCNT 현장에서도 성립해야 하는지 확인 필요.
