리포트 파일(`.crf`)은 바이너리라서 그동안 디자이너 화면으로만 열어 보고 고칠 수 있었다. 9월에 제조사 라이브러리(ClipReport Generator)로 `.crf` 를 텍스트로 뽑는 도구를 만들었고, 이번에는 한 걸음 더 나가 **"이 도구를 다른 개발자에게 넘기면, 그 사람이 AI 에게 요청해서 리포트를 원하는 대로 고칠 수 있나"** 를 확인했다.

한 줄 결론은 이렇다. **읽기와 분석은 된다. 직접 수정은 "파일 추가 서브섹션"이 없는 리포트만 기술적으로 되고, 그마저 아직 도구가 없다. 상시수시 위험성평가서처럼 첨부 PDF 를 붙이는 리포트는 저장하는 순간 파일이 깨진다.**

> 용어 — **Generator**: ClipReport 리포트 서버 jar 에 들어 있는 API. `.crf` 를 메모리 객체로 열고 저장할 수 있다.
> **FileImport**: 디자이너에서 "파일 추가 서브섹션"으로 보이는 칸. 출력할 때 바깥 PDF 를 페이지 사이에 끼워 넣는다.

## 1. 읽기는 이미 된다

Generator 의 `new CreateReport(경로)` 로 파일을 열면, 디자이너와 같은 파서가 만든 객체 트리를 들여다볼 수 있다. 암호를 푼 것이 아니라 제조사 파서를 빌려 쓰는 것이라 결과가 정확하다. 도구는 두 개다.

| 도구 | 뽑는 것 |
|---|---|
| `DumpSql` | 데이터셋별 SQL 원문 + 파라미터 |
| `DumpLayout` | 섹션 → 서브리포트(재귀) → 표시조건 → 표(열 너비, 셀 ↔ 필드 바인딩) |

다른 개발자에게는 **이 두 파일과 사용 가이드(README) 세 개만** 넘기면 된다. jar 는 리포트 서버 저장소에 이미 있고, 사내 라이선스라 따로 돌리지 않는다.

### 어디에 둘까

리포트 서버 저장소 안은 피한다. **그 저장소는 루트가 곧 웹앱 루트**라서, 거기 도구를 두면 `.java` 와 SQL 원문이 든 덤프가 배포본에 섞여 나갈 수 있다. 저장소 밖 개인 폴더에 두고 jar 만 그쪽 경로를 참조한다.

### Claude 말고 다른 AI 도 되나

된다. 출력이 평범한 UTF-8 텍스트라 ChatGPT · Gemini · Copilot 모두 같은 방식으로 쓴다. 정확도를 가르는 건 AI 종류가 아니라 두 가지다.

1. **표기 규칙을 알려 줬나.** `[IF ?:옵션 Equal 'T' → 숨김]` 은 "조건이 참이면 숨긴다"는 뜻인데, 모르면 AI 가 그럴듯하게 반대로 읽는다. 그래서 가이드에 "AI 에게 먼저 붙일 머리말"을 넣었다. 마지막 줄에 **"파일에서 근거 줄을 인용하고, 없으면 확인 안 됨이라고 답하라"** 를 넣는 게 중요하다. 이게 없으면 흔한 리포트 모양을 추정해서 답한다.
2. **파일이 통째로 들어갔나.** 가장 큰 리포트는 구조 덤프만 140KB 다. 채팅창에 붙여 넣으면 잘리기 쉬우니 첨부로 주거나, grep 으로 필요한 구간만 잘라 준다.

### 읽을 때 걸린 함정

| 함정 | 증상 | 대처 |
|---|---|---|
| JDK 8 | 실행은 되는데 SQL 의 한글 주석이 깨진다 | 출력 인코딩 옵션(`-Dstdout.encoding`)은 JDK 18 이상에서만 동작한다. 21 로 돌린다 |
| 읽기 실패가 조용함 | 경로가 틀려도 예외 없이 빈 리포트로 진행 | 출력 첫 줄 `datasets=N` 이 0 이면 실패 |
| Git Bash 경로 | 역슬래시 경로에 `*` 를 쓰면 **파일이 하나도 안 잡히는데 오류도 없다** | glob 은 `/` 경로로 돌리고 java 에는 `cygpath -w` 로 넘긴다 |

마지막 함정은 가이드에 처음 써 넣은 명령이 이랬다. **받는 사람처럼 빈 폴더에서 문서대로 따라 해 본 뒤에야** 잡혔다.

### 도구의 빈틈도 같이 넘긴다

`DumpLayout` 은 표 안에 박힌 서브리포트(예: 서명란 슬롯) 내부를 출력하지 않고, 블록이 어느 데이터셋을 쓰는지도 찍지 않는다. 이걸 모르고 쓰면 받는 쪽 AI 가 "서명란에 필드가 없다"고 단정한다. 고칠 수 있는 빈틈이지만(필요한 메서드가 jar 에 있다), 고치기 전이라도 **"알려진 한계"로 적어서** 넘겼다.

## 2. 쓰기 — 어디서 막히나

### 디자이너 쪽 우회로는 없다

디자이너는 Windows 네이티브(MFC) 프로그램이고, 리포트 디자인을 XML 같은 텍스트로 내보내는 기능이 없다(실행파일과 매뉴얼로 확인했다. 매뉴얼의 XML 은 데이터 소스 이야기다). 그러니 프로그램으로 `.crf` 를 쓰는 길은 **jar 의 Writer 하나뿐**이다.

### 원인은 FileImport 하나 — "하나만 빼고 다시"

9월에 이미 "저장하면 일부가 빠진다"는 걸 봤지만, Writer 가 전반적으로 불안정한지 특정 요소 탓인지는 몰랐다. 이번에 대조군 한 벌로 갈랐다.

| 상시수시 A 타입 | 결과 |
|---|---|
| 열어서 아무것도 안 바꾸고 저장 | 다시 열면 `EOFException`. 아예 안 열린다 |
| FileImport 2개만 메모리에서 지우고 저장 | 정상으로 열린다. 원본과의 차이는 지운 2줄뿐이고 SQL 949줄은 한 글자도 같다 |
| 두 저장본을 바이트로 비교 | **크기가 같고 2바이트만 다르다.** 둘 다 "이 섹션의 서브섹션 개수" 자리다(2 대 1) |

즉 Writer 는 **FileImport 의 내용은 0바이트로 건너뛰면서, 부모의 서브섹션 개수는 원래 숫자로 적는다.** 다시 읽을 때 리더가 없는 칸을 하나 더 찾는다.

### 증상은 위치에 따라 두 가지

| FileImport 위치 | 증상 |
|---|---|
| 리포트 맨 끝 | 🟠 **열린다. 그런데 FileImport 만 조용히 사라진다.** 출력물에 PDF 첨부가 안 붙는다 |
| 뒤에 다른 내용이 있음 | 🔴 **안 열린다.** 디자이너로 열면 **디자이너가 충돌해 꺼진다.** 대조군은 같은 방법으로 정상으로 열렸으니 파일 문제다 |

9월에 본 "열리는데 몇 줄 빠짐"은 맨 끝 케이스였다. 이번에 같은 결함이 "파일 파손"으로도 나온다는 걸 알았다. 운영 `.crf` 를 이 상태로 덮어쓰면 디자이너로도 못 열기 때문에, git 에서 이전 버전을 꺼내는 것 말고는 복구 방법이 없다.

**파일 크기 변화는 증거가 아니다.** FileImport 를 뺀 정상 저장본도 크기가 줄고(1.29MB → 1.09MB), FileImport 가 없는 제조사 샘플은 오히려 커졌다. 저장 형식 버전(`REX30` → `REX31`)이 바뀌기 때문으로 보인다.

### 전수 분류

리포트 서버의 `.crf` 455개를 모두 열어 분류했다.

| 구분 | 개수 | AI 직접 수정 |
|---|---:|---|
| FileImport 없음 | 384 | ✅ 그대로 저장 → 다시 열기 → 덤프 비교가 **384개 전부 원본과 같았다** |
| FileImport 있음 | 60 | ❌ 전부 안전보건 업무 쪽. TBM · 상시수시 · 최초정기 · 일일보고 등 자주 고치는 리포트다 |
| 아예 안 읽힘 | 11 | ❌ PDF 출력용 리포트들. 원인 미조사 |

FileImport 가 없는 리포트 하나로 SQL 에 주석 한 줄, 셀 문구, 열 너비를 바꿔 저장해 봤더니 **덤프 차이가 의도한 세 곳뿐**이었다. 다만 덤프에 안 나오는 서식 속성, 컨트롤 추가·삭제, 실제 서버 출력은 아직 확인하지 않았다.

## 3. 그래서 지금은

- **인계 범위는 읽기·분석까지.** 수정은 AI 가 무엇을 어떻게 바꿀지 알려 주고 사람이 디자이너에서 적용한다.
- FileImport 가 없는 384개를 직접 고치려면 쓰기 도구가 필요하다. AI 가 만든 수정안(JSON)을 적용해 임시로 저장하고, 다시 열어 **의도한 변경 말고 다른 차이가 하나라도 있으면 거부**한다. FileImport 가 있으면 저장 자체를 거부한다. 이 판정을 믿으려면 덤프가 촘촘해야 해서, 덤프 도구 보강이 곧 안전장치다.
- 60개는 제조사 수정을 기다리거나, 디자이너의 "기존 리포트 링크"(서브리포트를 경로만 저장하는 기능)로 PDF 블록을 별도 파일로 떼어 내는 방법이 있다. 후자는 아직 **검증하지 않은 가설**이다.
- 하지 않기로 한 것: 디자이너 화면을 AI 가 마우스로 조작하는 방식(취약하다), 바이너리 직접 편집, 제조사 Writer 코드 수정(난독화돼 있다).

### 제조사 문의는 이렇게

환경(jar · 디자이너 · JDK 버전), 증상 두 가지 표, 재현 코드 두 줄(`new CreateReport` → `saveReport`), "FileImport 만 빼면 정상", "두 저장본은 개수 자리 몇 바이트만 다름", "FileImport 없는 384개는 정상"을 적고, 수정 버전과 호환 jar 를 묻는다.

두 가지를 신경 썼다.
- **첨부는 제조사 샘플에 파일 추가 서브섹션을 넣어 재현한 파일**로 한다. 우리 리포트에는 회사 SQL 이 그대로 들어 있다.
- 비공개 내부 API 를 쓴다는 얘기는 넣지 않는다. 재현이 공개 API 만으로 되니, "지원하지 않는 사용법"이라는 답으로 끝날 여지를 줄인다.

문의 창구를 찾아보다가 더 중요한 사실을 알았다. 제조사 공지(2025-03 보안 패치)에 적힌 5.0 패치 버전이 **ver.308** 인데, 우리 서버 jar 는 **5.0.59** 다. 이 결함은 이미 고쳐졌을 수도 있다. 그래서 문의의 첫 질문은 "최신 패치에서도 재현되는가"가 된다. 패치는 유지보수 계약 고객에게만 제공된다.

## 4. 남기는 교훈

1. **원인을 좁힐 땐 "하나만 빼고 다시"** — FileImport 만 지운 대조군 한 벌이 범위를 가렸고, 바이트 비교로 메커니즘까지 나왔다.
2. **"다시 열린다"는 성공이 아니다** — 같은 결함이 위치에 따라 조용한 손실도 되고 파손도 된다. 검증은 원본과 전체 덤프를 비교해서 한다.
3. **크기 변화도 증거가 아니다** — 정상 저장본도 크기가 변한다. 대조군 없이 보면 오판한다.
4. **문서의 숫자는 원본이 바뀌면 낡는다** — 3주 전 "원본 결함 21벌"은 그 사이 조치로 0벌이 돼 있었다. 다시 돌리는 데 30초면 됐다.
5. **안내문의 명령은 받는 사람 입장으로 돌려 본다** — 오류 없이 아무것도 안 하는 명령은 써 본 사람만 잡는다.
