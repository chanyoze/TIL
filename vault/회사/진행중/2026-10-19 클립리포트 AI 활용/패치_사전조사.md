[1편](./crf_AI_읽기와_쓰기.md)에서 찾은 "파일 추가 서브섹션(FileImport) 저장 결함"을 제조사에 문의했더니, **최신 버전 5.0.400 에서는 재현되지 않는다**는 답이 왔다. 같은 답변에서 2025년 SQL Injection 보안 조치도 5.0.308 이상이어야 한다는 걸 알게 됐다. 우리 서버는 5.0.59 다. 그래서 버전업을 디렉터님께 제안하기 전에 **"올려도 사이드 이펙트가 없을까"** 를 검토하기로 했고, 이 글은 패치 파일을 받기 전까지 한 사전 조사다.

한 줄 결론: **엔진은 저장소와 같은 5.0.59 였지만, 그 밖의 파일은 서버에서 손으로 고친 것이 꽤 많았다. 패치는 저장소가 아니라 서버를 기준으로 해야 한다.**

> 이 글은 패치 파일을 받으면 이어서 갱신한다. 10-26 에 제조사 2차 회신 · Java 버전 · SQL Injection 영향 점검을 7절에 더했다.

## 1. 제조사 회신 요지

| 질문 | 답 |
|---|---|
| 최신 패치에서 고쳐졌나 | 최신 5.0.400 에서 동일 현상 없음 |
| 교체용 jar 를 받을 수 있나 | 유지보수 계약 고객에게 제공. 우리는 계약 중 |
| 우회 방법 | 없음. 서버 패치 필요 |
| SQL Injection 패치 대상인가 | 5.0.308 이상으로 올려야 함 |

버전업 근거가 두 개(AI 수정을 막는 저장 결함, 보안 조치)가 됐다. 패치 파일을 요청하면서 교체 파일 목록, 릴리스 노트, 라이선스 재발급 여부, 디자이너 호환(되돌릴 때 대비), 라이브러리 요구 버전을 함께 물었다.

메일을 쓰며 챙긴 점:
- 게시판은 **사내 공용 계정**으로 올리고 회신은 **담당자 메일**로 받는다. 그래서 본문에 "패치 파일도 이 메일로 보내 달라"고 적었다.
- 첫 문장에 게시판 문의 제목을 그대로 넣었다. 담당자가 어느 건인지 바로 찾게 하려는 것이다.
- AI 로 다듬은 초안은 "해결되었고"처럼 제조사 말보다 세게 바뀌어 있었다. 제조사가 한 말("재현되지 않음")로 되돌렸다.

## 2. 패치가 닿는 곳

| 저장소 | 역할 | 패치 영향 |
|---|---|---|
| **saas-report** | 리포트 서버 webapp. 엔진 jar · 설정 · 폰트 · 뷰어 JS · 진입 JSP · `.crf` 455개 | **직접 바뀜** |
| cip-defg-saas | URL 로 호출만 함. 뷰어 열기(`cips.report`), 공통 뷰어 팝업, PDF 를 받아 첨부로 저장(`makeAttachmentReport`) | 회귀 시험 대상 |
| 그 밖의 저장소 7개 | 참조 없음 | 없음 |

- `makeAttachmentReport` 는 서버끼리 PDF 를 받는데 **타임아웃이 5초로 고정**돼 있다. 새 버전에서 출력이 느려지면 여기서 먼저 깨진다.
- saas-report 의 배포 스크립트는 **`.crf` 만 서버로 복사**한다. jar · 설정 · JSP 는 서버에 따로 있다. 그래서 "저장소가 5.0.59 이니 서버도 그대로겠지"는 확인 안 된 가정이었다.

## 3. 서버를 직접 확인한 방법

서버 담당자에게 묻지 않고 확인하는 게 목표였다.

1. **sysinfo 페이지** — 저장소에 있던 `sysinfo.jsp` 가 서버에도 떠 있어서, 브라우저로 열어 JDK · 톰캣 · OS 를 확인했다. jar 목록은 안 나온다.
2. **AWS 콘솔 → EC2 → 연결 → Session Manager** — 키 없이 브라우저 셸로 들어간다.
3. **서버 안의 Jenkins 작업공간** — 빌드가 서버 안에서 돌아서, 서버에 저장소 사본이 있다. 이 사본과 실제 webapp 을 `diff -rq` 하니 **서버에서만 바뀐 파일이 한 번에 다 나왔다.**

셸에서 걸린 함정:

| 함정 | 증상 | 대처 |
|---|---|---|
| `sudo cd` | 아무 일도 안 일어남 | `cd` 는 셸 내장 명령이라 sudo 가 띄운 하위 셸에서만 이동하고 끝난다. 명령마다 `sudo` + 절대경로 |
| `sudo md5sum 폴더/*.jar` | "No such file" | `*` 는 sudo 가 아니라 현재 계정이 펼친다. 못 읽는 폴더면 실패 → `sudo sh -c "..."` |
| 인스턴스 착각 | 개발 경로가 없다고 나옴 | 처음엔 운영 서버로 들어갔다. 인스턴스 이름부터 확인 |

## 4. 개발 리포트 서버 실측

**환경**: Amazon Corretto **JDK 17**, Tomcat 9.0.55, Amazon Linux 2023, **ARM(aarch64, Graviton)**. JDK 17 에서 5.0.59 를 돌리려고 `--add-opens` 옵션 5개를 열어 두었다. ARM · JDK 17 지원 여부는 제조사에 묻지 않고 개발 서버에 올려 확인하기로 했다(7절).

**저장소와 같은 것**: 엔진 jar 두 개, pdfbox · fontbox · jai · commons-logging, 설정 파일 6개, 뷰어 JS 일부. 일부는 해시가 달랐지만 줄바꿈(CRLF)만 다른 거였다.

**서버에서만 바뀐 것**:

| 파일 | 차이 |
|---|---|
| JDBC 드라이버 | 저장소 `ojdbc14` → 서버 **`ojdbc8`** |
| 라이선스 | 2026-01 에 서버에서만 갱신 |
| DB 연결 설정 | 서버 값 (내용은 안 봄) |
| `Service.properties` | 로케일 `ko_KR` → **`en_US`** |
| `clipreport5.properties` | 임시 리포트 정리 스케줄러 꺼 둠, 비교 시각 12 → 23 |
| 폰트 | 태국 · 미얀마 · 몽골 · 중국어 등 **다국어 폰트 10개 추가** |
| JSP · web.xml | 공백 · 주석만 다름 → 동작 차이 없음 |

### clipreport5.js — 크기는 같은데 내용이 다른 파일

크기가 바이트까지 같은데 해시가 달랐다. 쫓아가 보니 이랬다.

- 서버 파일 맨 앞에 **UTF-8 BOM**(3바이트)이 붙어 있었다. 누군가 편집기로 열어 저장한 흔적이다.
- 압축 JS 는 전체가 한 줄이라 `cmp` 로 첫 차이를 찾으면, 그 뒤가 전부 밀려 73만 바이트가 다르게 나온다. `;` 마다 줄을 나눠 diff 하니 **바뀐 문장 3개**만 남았다.

| 변경 | 의미 |
|---|---|
| 저장 메뉴 순서에서 `jpg` 를 `cell` 뒤로 이동 (공백 3개 삭제) | 사내 요구. 공백 3개 삭제가 BOM 3바이트와 상쇄돼 크기가 같았다 |
| `isjpg` → `isJpg` (2곳) | **제조사 버그 수정.** 기본값은 `isJpg` 인데 읽고 쓰는 곳이 소문자라 JPG 메뉴 표시 설정이 안 먹었다 |

메뉴 순서는 뷰어에 공식 함수(`setReportSaveMenuOrder`)가 있었다. 제조사 JS 를 고칠 필요 없이 `report.jsp` 에서 한 줄로 지정하면 버전업 때도 유지된다.

## 5. 패치 원칙

| 구분 | 처리 |
|---|---|
| 엔진 · 라이브러리 jar | 새 버전으로 교체 |
| ojdbc8 · 라이선스 · DB 연결 설정 | **서버 것 유지** |
| 로케일 · 스케줄러 설정 | **서버 것 유지**. 새 키가 생기면 옮겨 넣기 |
| 다국어 폰트 | 유지 |
| JSP · web.xml | 새 버전으로 교체. 사내에서 넣은 코드는 저장소 JSP 기준으로 옮김 |
| 뷰어 JS | 새 버전으로 교체 → 메뉴 순서는 `setReportSaveMenuOrder`, `isjpg` 버그가 고쳐졌는지 확인 |
| 저장소 | 서버 수정분을 저장소에도 반영해 차이를 없앤다 |

저장소 파일로 서버를 덮으면 `ojdbc14` 로 돌아가 DB 연결이 깨질 수 있고, 갱신한 라이선스도 옛것으로 돌아간다.

## 6. 패치 파일을 받으면

- 운영 리포트 서버도 같은 방식으로 대조한다(이번엔 개발만 봤다).
- 받은 파일 목록과 릴리스 노트를 위 인벤토리와 맞춰 본다. JSP 가 쓰는 클래스가 새 jar 에도 있는지 확인한다.
- `.crf` 455개를 옛 jar 와 새 jar 로 각각 덤프해서 비교한다(1편의 crf-tools). FileImport 60개는 저장 왕복까지 본다.
- 로컬 톰캣에 옛 버전과 새 버전을 나란히 띄워, 대표 리포트의 뷰어 · 인쇄 · PDF 저장 · 첨부 저장을 비교한다.

## 7. 제조사 2차 회신과 SQL Injection 영향 (10-26)

제조사가 설치 파일을 보내기 전에 Java 버전을 알려 달라며, 패치 가이드 · 릴리스 노트 · 패치 전 확인 사항 문서 3개를 보내 왔다.

### 회신 요지

| 질문 | 답 |
|---|---|
| 라이선스 재발급 | 필요 없음. 서버 정보(IP · 코어)가 같으면 기존 라이선스 사용 |
| 기존 `.crf` 호환 | 상위 버전에서 열림. 다만 버전 차이가 커서 출력 위치 · 레이아웃이 달라질 수 있어 **미리보기 · 인쇄 · 파일 변환 검수 필요** |
| 동반 라이브러리 | 설치 파일에 들어 있는 것을 따르면 됨 |

### 문서에서 우리에게 걸리는 것

- **SQL Injection 필터가 기본으로 켜진다.** 리포트 매개변수 값의 `'` `"` `;` `#` `\` `--` `/*` 는 다른 글자로 바꾸고, `SELECT` · `OR` · `AND` 같은 단어가 있으면 예외를 낸다. 끌 수 있지만(`base.engine.sqlinjection=false`) 보안 조치가 버전업 이유 중 하나라 마지막 수단이다.
- **jQuery 가 1.11.1 → 3.7.1 로 바뀐다**(5.0.270부터). `report.jsp` · `report.html` 의 참조를 바꿔야 한다. 확인해 보니 `report.jsp` 가 쓰는 jQuery 는 키보드 페이지 이동 · 스크롤뿐이라 한 줄 교체로 끝난다.
- **뷰어 info 화면에 서버 엔진 버전이 안 나온다**(5.0.394부터 기본 숨김). 안 보여도 패치 실패가 아니다. 엔진은 jar 파일명, 뷰어는 `clipreport5.js` 로 확인한다.
- 옛 jar 를 `WEB-INF/lib` 에 남기지 말 것, 라이선스 파일을 덮지 말 것, 수정한 js 는 새 원본과 비교해 변경분만 옮길 것 — 5절 원칙과 같다.
- 릴리스 노트는 스스로 "부분 목록"이라 밝힌다. 제목은 5.0.400, 본문은 5.0.401 로 서로 다르다. 문서만 믿지 않고 실제 비교로 확인한다.

### Java 버전 회신

톰캣이 실제로 쓰는 java 를 보려고 PATH 의 `java` 대신 **톰캣 프로세스의 실행 파일**(`/proc/<pid>/exe`)을 확인했다. 개발 · 운영 리포트 서버 모두 **Amazon Corretto 17 · ARM(aarch64) · Amazon Linux 2023** 이었다. 세부 버전(17.0.19 / 17.0.20.1)만 달랐고, 제조사는 주 버전(1.8 / 17)으로 빌드를 나누니 상관없다.

운영 서버에는 Java 1.8 로 도는 톰캣이 하나 더 있었는데, 예전 제품을 쓰는 레거시라 대상이 아니다. 재기동할 때 리포트 톰캣만 내리고 올리면 된다.

회신은 짧게 했다. 서버 구성은 개발 · 운영으로 나누지 않고 "JDK 17 (Corretto) / Linux aarch64 / Tomcat 9" 한 줄로 적었다. ARM 지원 · JDK 17 옵션 · 정확한 버전 번호는 묻지 않았다. 지금 버전이 이미 같은 ARM 서버에서 돌고 있고, 나머지는 개발 서버에 올려 보면 알 수 있기 때문이다.

### SQL Injection 필터 영향 — 455개 전수

설치 파일이 오기 전에 오프라인으로 할 수 있는 가장 중요한 점검이라 먼저 했다.

**매개변수는 바인드가 아니라 문자열 치환이다.** ClipReport SQL 은 `'{parameter.PROJ_CODE}'` 처럼 값을 SQL 문자열에 그대로 끼워 넣는다. 그래서 필터가 값을 검사한다.

crf-tools 로 455개 SQL 을 뽑아 매개변수 자리 19,196곳을 문맥별로 나눴다.

| 문맥 | 판정 |
|---|---|
| 따옴표 없이 쓰인 숫자(회사 ID · 사용자 번호 등, 10곳) | 값이 숫자 → 안전 |
| 쉼표 · `^` 로 이은 목록 | 구분자가 검사 문자가 아님 → 안전 |
| 코드값 · 플래그 · 날짜 · 파일 URL | 고정된 값 → 안전 |
| **자유 텍스트**(현장명 · 회사명 · 사람 이름 · 검색어) | 데이터에 따라 다름 |

자유 텍스트는 화면이 `encodeURI` 로 인코딩한 짝 매개변수(`ENCODE_…`)를 같이 넘기고, SQL 이 `UTL_URL.UNESCAPE` 로 되돌리는 구조였다. 그런데 **`encodeURI` 는 `'` `;` `#` `-` 를 바꾸지 않는다.** 그래서 인코딩된 값도 필터를 그대로 맞는다.

그래서 실제 데이터를 셌다(개발 DB, 조회 전용).

| | 전체 | 특수문자 | `--` `/*` | `AND` · `OR` 등 단어 |
|---|---|---|---|---|
| 현장명 | 6,361 | 11 | 0 | 0 |
| 회사명 | 740 | 2 | 0 | 0 |

- **리포트를 에러로 막는 단어 검사에 걸리는 데이터는 0건.** 가장 걱정한 부분이 없었다.
- 13건은 글자만 바뀐다. 리포트 머리글에 찍히는 이름이나 그 이름으로 한 검색 결과가 달라질 수 있다. 무엇으로 바뀌는지는 문서에 없어 시험해 봐야 한다.
- 작은따옴표가 든 현장 1건은 **지금도 SQL 이 깨진다.** 패치 후엔 오히려 리포트가 뜬다.
- 사용자가 입력하는 검색어는 미리 셀 수 없다. 띄어 쓴 `AND` · `OR` 를 검색하면 에러가 날 수 있지만 드물다.

결론: **필터는 기본값 그대로 써도 될 수준이다.** 시험 항목에 "큰따옴표 든 현장명 표시"와 "검색어 `AND`" 두 가지를 추가했다. 운영 DB 수치는 아직 안 셌다.

## 8. 남기는 교훈

1. **배포가 일부만 옮기면 서버는 저장소와 따로 늙는다.** crf 만 배포하는 사이 1년 넘게 서버에서 손으로 고친 것이 쌓였다. 저장소만 보고 판단했다면 패치 때 DB 연결과 라이선스를 깼을 것이다.
2. **해시가 다르다고 내용이 다른 게 아니고, 크기가 같다고 내용이 같은 것도 아니다.** 줄바꿈 · BOM · 줄끝 공백을 걸러야 진짜 수정이 남는다.
3. **압축 JS 는 `;` 로 쪼개서 diff 한다.** 한 줄짜리 파일은 첫 차이 뒤가 전부 밀린다.
4. **서버 안 CI 작업공간이 기준 사본이다.** 담당자 없이도 드리프트 전체를 한 번에 볼 수 있다.
5. **제조사 코드를 고치기 전에 공식 설정 API 부터 찾는다.** 직접 고치면 버전업 때마다 다시 고쳐야 한다.
6. **보안 필터 영향은 문서가 아니라 실데이터로 잰다.** "특수문자를 막는다"만 읽으면 겁부터 나지만, 매개변수가 어디에 어떻게 쓰이는지 나누고 실제 값을 세면 걸리는 건 13건뿐이었다.
7. **`encodeURI` 는 SQL 특수문자를 지켜 주지 않는다.** `'` `;` `#` `-` 는 URL 에서 허용되는 문자라 그대로 남는다. 인코딩해서 넘기니 안전하겠지라는 가정은 틀렸다.
8. **서버의 java 는 PATH 가 아니라 프로세스에서 본다.** 한 서버에 Java 버전이 다른 톰캣이 둘 떠 있었다. `java -version` 만 쳤다면 엉뚱한 쪽을 봤을 수 있다.
