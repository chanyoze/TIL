11월 18일 오전, 첨부파일을 PDF 로 바꿔 주는 외부 변환 서버(PDF Gateway)가 응답하지 않았다. 변환만 안 되면 미리보기 하나 빠지는 정도였을 텐데, 실제로는 **첨부 업로드 자체가 실패**했다. 원인은 단순했지만(서버의 예약 Windows 업데이트), 그 과정에서 두 번 틀린 추측을 했고, 부가 기능의 장애가 핵심 기능으로 번지는 구조를 하나 찾았다.

## 무슨 일이 있었나

- 로그에는 `connect timed out` 이 반복됐다. 변환 서버 관리자 콘솔도 열리지 않았다.
- 처음 질문은 *"원격으로 들어가서 게이트웨이 시작 · 중지 스크립트를 돌리면 풀릴까"* 였다.
- 원인은 변환 서버에 예약해 둔 **Windows 업데이트**였다. 업데이트 중에 서버 자체가 내려가 있었고, 서버가 다시 올라오자 게이트웨이는 자동으로 기동됐다.

## 틀린 추측 두 번

| 추측 | 실제 |
|---|---|
| 확인 시점에 내 PC 에서는 포트가 다 열려 있었다 → "운영 서버에서 변환 서버로 가는 길이 막혔다" | 서버가 다운됐었고, 내가 확인했을 때는 **이미 복구된 뒤**였다 |
| 재기동으로 풀렸다 → "재부팅 뒤 게이트웨이가 자동으로 안 뜬다" | 자동 기동 구조였다. 서버 자체가 죽어 있었을 뿐이다 |

교훈은 두 가지다.

- **`timed out` 과 `refused` 는 다른 이야기다.** 타임아웃은 아무 응답이 없다는 뜻이라 서버나 네트워크 경로부터 본다. 거부(refused)는 서버는 살아 있고 포트에 프로세스가 없다는 뜻이라 그때 프로세스 재시작이 의미 있다.
- **"지금 정상" 은 원인 판정 근거가 아니다.** 확인 시점과 장애 시점이 다르면 회복된 상태를 보고 엉뚱한 원인을 세운다. 장애 시각에 무슨 일이 있었는지(업데이트 · 재부팅 이력)를 먼저 묻는 게 빨랐다.

## 왜 업로드까지 실패했나

업로드 처리는 한 트랜잭션 안에서 이렇게 흐른다.

1. 파일을 S3 에 올린다
2. 파일 정보를 DB 에 저장한다
3. PDF 변환을 요청한다 ← 여기서 예외

프로젝트는 서비스 구현체 전부에 *"예외가 나면 롤백"* 트랜잭션을 건다. 그래서 3단계 예외가 2단계 DB 저장까지 되돌렸고, 사용자는 업로드 실패를 봤다. S3 에는 파일이 이미 올라가 있어 DB 행 없는 파일만 남는다.

## 고치는 방향 — 새로 만들 게 거의 없다

코드를 따라가 보니 안전장치는 이미 있었다.

- 변환 상태 코드(미요청 · 처리중 · 완료 · 실패)
- 완료가 아닌 파일은 화면에서 아이콘을 눌러 **다시 요청**할 수 있다
- 처리중으로 남은 건은 새벽 스케줄러가 실패로 정리한다

그래서 조치는 **업로드 경로에서만 변환 실패를 잡아 로그로 남기고 넘어가는 것** 한 곳이면 된다. 요청이 못 나간 파일은 "미요청"으로 남아 사용자가 다시 요청할 수 있다.

```java
if(abIsConvertToPdf) {
	try {
		convertFileWithJfileGrpNo(asCompanyId, asJfileGrpNo);
	} catch(Exception e) {
		log.error("PDF 변환 요청 실패 — 업로드는 유지, 화면에서 재요청 가능", e);
	}
}
```

예외를 변환 함수 안이 아니라 **호출하는 쪽**에서 잡은 이유가 있다. 같은 변환 함수를 화면의 "다시 요청" 버튼도 쓰는데, 그 버튼을 누른 사람에게는 실패가 그대로 보여야 한다. 실패를 어디서 삼킬지는 **누가 그 실패를 알아야 하는가**로 정한다.

## 남은 것

- 요청에 실패한 파일을 "실패" 상태로 표시할지 정해야 한다. 표시하면 장애 중에 올린 파일을 사용자가 알아볼 수 있다.
- 운영 쪽에는 변환 서버 업데이트 예약을 업무시간 밖으로 옮기고 미리 공유해 달라고 요청한다.
